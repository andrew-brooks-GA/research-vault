# Security model

`research-vault` is a local Markdown toolkit. Seven features reach outside the vault (`refresh`, `capture --batch` over a URL list, the embedding endpoint behind `embed` and `search --semantic`, `export`, `teach serve`, the lab runs of `teach serve --labs` and the terminal of `teach serve --terminal`), and this document is the exhaustive contract for all seven. The README explains *when* to use them; this explains *what they guarantee*.

## Reporting a vulnerability

Email **andrew.brooks.aob@gmail.com** with details and a reproduction. Please don't open a public issue for a security report.

## Threat model in one line

A repository you open and a teaching workspace you serve, export or check are untrusted input. The hooks and commands read their binding (`.research-vault.json`), links and files without a trust step. The guarantees below apply to that input, which can still name programs Git runs as clean or process filters (Git processes) or supply the workspace's own `check.sh` and `setup.sh` scripts that `teach check` runs (Local writers). The features that reach outside the vault are off or conservative until you opt in per run. `refresh` and `export` never mutate entries. `teach serve` checks its state and attempt paths against the workspace before writing. With `--labs` it also runs the lab scripts a workspace pins, which write wherever they write, and with `--terminal` it starts a shell whose commands write wherever they write. With either flag, a page served from the workspace can carry its own script, which runs in the server's origin and, in a browser with the session cookie, can use the enabled lab and terminal routes as the page's controls do, so use these flags only with a workspace whose pages you trust (Lab runs and Terminal).

The path checks below compare resolved path names at the time of the check. A hard link to a file elsewhere passes these checks. A path change by another process between the check and the operation goes undetected by that check.

## Git processes

Every Git process started by the hooks, gate and repository scripts goes through `bin/lib/git.mjs` and runs without a shell. The wrapper passes `--no-optional-locks`, disables `core.fsmonitor`, sets `safe.bareRepository=explicit`, sets `core.hooksPath` to the wrapper file so it holds no hooks, disables `hook.post-index-change.enabled` and sets `GIT_NO_LAZY_FETCH=1`. The two hooks' calls time out after 3 seconds. Boolean `core.fsmonitor` needs Git 2.36 or later, implicit bare repository refusal needs 2.38 or later, `GIT_NO_LAZY_FETCH` needs 2.45.1 or later, and the hook event setting needs 2.55 or later. A repository's Git configuration can name clean or process filter programs that Git runs. Reading a split index still refreshes the shared index file's timestamp.

## Repository bindings

A binding can name a vault that resolves inside the folder holding `.research-vault.json`, or one of the user's own locations: `RESEARCH_VAULT_PATH`, the config pointer or the OS default. The plugin takes `RESEARCH_VAULT_PATH` as the user's own choice. Only an absolute binding path whose first two characters are each `/` or `\` is compared with those choices by normalized spelling. All other binding paths go through the resolved-path comparison. An unapproved or unresolvable vault named by the binding makes a command that uses it report the binding path on standard error and exit 2. The hooks skip work that depends on that vault. The Stop hook reports the skip. An explicit `--vault` takes precedence.

Loading the binding requires each `code.versions.<key>.file` to be a non-empty relative path and rejects absolute paths, drive specifiers and `..` segments. Before reading a versions file, the reader checks that its resolved path is inside the repository.

## Local writers

One local process writes your entries without a per-run prompt: the advisory `PostToolUse` hook re-runs `lint --fix` and a manifest rebuild on the vault after a vault-file edit. The entry walk used by lint, the hook, the manifest and search skips a linked type folder or entry file whose target is outside the vault or cannot be resolved. `lint` reports each skip as `WARN_ENTRY_LINK_SKIPPED`. The hook's entry, manifest and usage-log writes use the vault destination checks below. The hook opens no network connection, and the `lint` correctness gate does not depend on it.

The entry writer checks both the entry path and its temporary path against the vault root. The manifest, usage log, capture receipts and locks, compiled index, embeddings index, and `init` template copy and generated files also use vault destination checks. These are the resolved-path checks described under Threat model. A linked vault root and links that resolve inside the vault are supported by these checks. The claims ledger is checked against the root selected for that ledger, and evidence packets check their destinations against the packet output root. The Obsidian view requires its output directory to resolve inside the vault and outside the entry folders before writing. It refuses the directory if it cannot establish those locations. It also refuses a path whose normalized spelling matches the vault root or falls inside an entry folder before link resolution. These path checks apply to the output directory alone. `init --project` creates its binding exclusively and refuses an existing link at that name.

A second local process, `teach serve`, writes learner data, not entries: one attempt file in the workspace's `attempts/` per accepted `POST /attempt`, and `.teach-serve.json`. Its limits are in the next section. With `--labs` it also runs the lab scripts a workspace pins, which write wherever they write (Lab runs, below).

A fourth, `teach check` (`./check` in a teaching workspace), runs a checked task's `evidence/NNNN/check.sh` with the environment it was started with, and with `--start` each task's `setup.sh`. Unlike a lab script, neither is pinned by a hash: they are the workspace's own scripts, run when the learner runs `./check`. It writes `check: evidence/NNNN/check.sh` to standard error before each checker start, including under `--dry-run`, `--hints` and `--certify`. A problem after a task's announcement, including a failed checker start, adds a problem line on standard error. At `--certify`, a refusal before a task's announcement can follow `check:` lines for earlier tasks. If the announcement cannot be written, the checker still runs. It writes one attempt file in `attempts/` for each check it records and `.teach-certify.json` while a certification run is open; the scripts write wherever they write, and a background process a setup leaves keeps running. A single-task check checks `attempts/` before starting the checker when the result can be recorded. Certification checks `.teach-certify.json` and `.teach-certify.ending.json` before reading or changing either file, and refuses a link, a non-regular file or an unresolved destination with exit 2 and `error: <file>: cannot use as a regular workspace state file. Remove it by hand.` on standard error. At `--certify` the check of attempt destinations runs after the checkers and before the state file is renamed. A refusal from that check leaves the run open.

Attempt and record writers check that existing `attempts/` and `learning-records/` directories are real directories whose resolved paths match their expected locations in the workspace. They check resolved destinations before writing. `teach record supersede` and `teach lint --fix` refuse a record that is itself a link. `teach lint --fix` checks and reads every record before rewriting any. A refused destination makes the writing command exit 2 with the path and reason on standard error.

A third local write is the usage log, `_index/usage.jsonl` in the vault, appended by the pre-web hook, the post-edit hook and `search`: ids, facets and an outcome per event, never the fetched page, and free query text only when the repo's binding sets `usage.text` to `true`. Its path is under `_index/`, which the vault's `.gitignore` ignores, and nothing reads it but the vault's own reports. The append is refused when its directory or file resolves outside the vault or cannot be resolved. `search` reports the refusal on standard error and still prints its results. The hooks skip a refused append.

## Lesson server (`teach serve`)

`teach serve [workspace]` serves one teaching workspace to a browser so a lesson's quiz can record an attempt and, with `--labs`, run a lesson's lab. It runs until it is stopped.

- **Loopback only.** It listens on `127.0.0.1` on a port the operating system assigns (`listen(0, '127.0.0.1')`) and prints `serving <workspace> at http://127.0.0.1:<port>/`. It never listens on another interface.
- **Exact `Host`, before any work.** Every request, of any method, must carry `Host: 127.0.0.1:<port>` with the server's own port. Anything else, a missing `Host` included, is 403 before the path is read. A request whose `Host` is any other value is refused, for GET and POST alike.
- **Static reads from an allowlist.** The static path allowlist for `GET` and `HEAD` contains `lessons/`, `reference/`, `assets/` and `brand/`, plus `GLOSSARY.md` at the workspace root. For a file under one of those folders, the server checks that the folder resolves to its own place in the workspace and the file resolves inside that folder. The workspace root may itself be reached through a link. For `GLOSSARY.md` the server checks that it resolves inside the workspace and is a regular file at that name. `GET /` answers with an HTML index of the lessons and reference docs, and `GET /lessons.json` with the same list as JSON (title, URL, and each lesson's `PATH.md` line number, shape and closing `Project:` line). To build that list, the server looks for `lessons/`, `reference/`, `PATH.md` and the brand files. `GET /` also looks for the workspace's regular `README.md`. The lesson and reference listings, progress pages and quiz grading treat paths that fail their containment checks as absent. A brand configuration file that fails its containment check makes the brand invalid. If the brand is invalid at startup, `teach serve` prints `brand: brand/brand.json is invalid; run teach lint` on standard error. The server serves pages without the brand while it is invalid. Image and cast lookups use the static file checks, and the claims gate treats a task's requirements file outside its workspace as absent. `teach serve`, `teach export` and `teach next` skip a workspace binding that is linked outside the workspace. With a brand whose `dividers` key is set, `GET /dividers/<k>.html` answers with a generated page for the k-th group of lessons, built from the same list and the brand, and `GET /lessons.json` lists those pages among the lessons. `GET /` renders the `README.md` from Markdown above the index, with `&`, `<`, `>` and `"` of the source escaped, so raw HTML shows as text, and a link kept as a link only when its target is `http:`, `https:` or has no scheme. Everything else is 404 (without `--labs` or `--terminal`; with either, `GET /labs/open` also answers, and with `--terminal`, `GET /term/stream`, `GET /term/lessons/<lesson id>.html` and `GET /terminal/<file>`, below), including a decoded static path with a backslash, `NOTES.md`, `MISSION.md`, learning records, attempts, `evidence/`, `.teach-serve.json`, a directory, a path with a NUL byte and any path segment that starts with `.` (so `..` escapes, encoded or not). A path that does not URL-decode is 400. A method other than `GET`, `HEAD` or `POST` is 405. Every response carries `X-Content-Type-Options: nosniff`.
- **One write, `POST /attempt`.** A `POST` to any other path is 404, except, with `--labs`, the four lab routes below, which start a lab's scripts, and, with `--terminal`, the two terminal routes below, which type into a shell. Before the body is read, the request must carry `Origin` equal to the server's own `http://127.0.0.1:<port>`, `Content-Type: application/json` (optionally with `; charset=utf-8`), and, when `Content-Length` is present, a length of at most `ATTEMPT_BODY_MAX` (4096) bytes. Anything else is 403. A body sent without `Content-Length` is counted as it arrives and is refused with 403 once it passes 4096 bytes.
- **Validated body.** Malformed JSON or a body other than an object with a string `lesson` and an array `answers` gets 400. A workspace path whose real location changed or cannot be resolved gets 500 before the lesson id is checked. The lesson id must match `^\d{4}-[a-z][a-z0-9-]*$` and name an existing `lessons/<id>.html` that resolves inside the workspace's own `lessons/` folder. An invalid id or a lesson treated as missing, including when it fails that containment check, gets 400. A failure to read the lesson or parse its quiz data gets 500. The server then checks that `answers` holds one integer per quiz item, each an index of that item's options. Answers that fail this check get 400. A refused attempt destination or failed write gets 500. The server keeps running.
- **The server grades.** The client sends answers, never a score. The server grades them against the lesson's own quiz data through `writeAttempt`, the same function `teach attempt add` calls, and replies `{ "id", "score", "total", "wrong" }`.
- **Its other write.** Before listening it checks `.teach-serve.json`. A link, a non-regular file or an unresolved state path is refused with `teach serve: .teach-serve.json: cannot use as a regular workspace state file` on standard error and exit 2. Once the server is listening, it checks the name again. If a regular file is there, it unlinks the file without checking whose it is and checks the name once more. It then creates `.teach-serve.json` (`{ port, pid }`) exclusively. A failed path check or an `EEXIST` error at this stage closes the listener and gives the same refusal. On exit, including on `SIGINT` and `SIGTERM` (with `--labs` or `--terminal`, also on `SIGHUP`), it attempts to unlink only that name in the recorded real workspace directory and ignores a failure. It skips removal if that directory's real location has changed or cannot be resolved. The server's own writes are the state and attempt files. With `--labs`, the lab scripts it starts write wherever they write, and with `--terminal`, the shell does.

## Lab runs (`teach serve --labs`)

`teach serve --labs [workspace]` adds routes for the labs the workspace's `labs/labs.json` declares (LESSON-FORMAT.md, Labs), and runs a lab's scripts when a lab `POST` passes every check below. Use it on a single-user machine and only with a workspace whose pages you trust. A script runs with the rights of the user who started the server, and nothing here is a sandbox.

- **Off unless asked for.** Without `--labs`, `POST /lab/<action>` is 404 `not found`, as before; without `--labs` or `--terminal`, so is `GET /labs/open`, and no cookie is set. With `--labs`, an invalid `labs/labs.json` exits 2 before the server listens. The server checks that `labs/` resolves inside the workspace and that the manifest, if present, is a regular file whose resolved path is inside the workspace.
- **The lab address.** At start the server makes `t`, 64 hex characters from `randomBytes(32)`, and prints `labs: open http://127.0.0.1:<port>/labs/open?t=<t>` once in its terminal. `t` is not written to `.teach-serve.json`, a page, a response body or a log line.
- **Opening it.** Every `GET /labs/open` whose one `t` parameter equals `t`, compared with `timingSafeEqual` once the lengths match, answers 303 with `Set-Cookie: rv-labs-<port>=<session value>; HttpOnly; SameSite=Strict; Path=/`, to `next` when it is `/lessons/<lesson id>.html`, else to `/`. The session value, a second 64-hex value, is made at the first open and is the same at every later one while that server runs, so the same address works again after a browser restart or in a second browser. A wrong or missing `t` is 403 and sets no cookie. Anyone who reads `t`, in the terminal, an `open` command line, a transcript or browser history, can open the address while that server runs; `--labs` is meant for a single-user machine.
- **No framing.** With `--labs` alone, every response carries `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'`; with `--terminal`, with or without `--labs`, `X-Frame-Options: SAMEORIGIN` and `Content-Security-Policy: frame-ancestors 'self'`, so a page of the same server can frame a lesson; with neither flag, no framing header. Not probed: a browser takes a page on another port as another origin, so that page still cannot frame a page of this server. A page on another `127.0.0.1` port is same-site, so the browser sends it the lab cookie when it frames a lesson.
- **What a page shows of a lab.** Every lesson page `teach serve` serves, with or without `--labs`, and every lesson page `teach export` copies, reads `labs/labs.json` and, when it is valid and names the lesson's lab, shows the lab's cost line and the paths of its `up`, `verify` and `down` scripts, a path under `evidence/` or `labs/` included, though those directories are not otherwise served or copied.
- **Checks, in order.** `POST /lab/run`, `/lab/stop`, `/lab/reset` and `/lab/verify` are refused by the first check that fails:
  1. `Host` other than `127.0.0.1:<port>`: 403 `forbidden`.
  2. A path other than `/attempt` and the four: 404 `not found`.
  3. `Origin` other than `http://127.0.0.1:<port>`, a `Content-Type` other than `application/json` (optionally `; charset=utf-8`), a `Content-Length` over `LAB_BODY_MAX` (256), or a body without it that passes 256 bytes: 403 `forbidden`.
  4. No `rv-labs-<port>` cookie equal to the session value, compared as `t` is: 403 `no lab cookie; open the lab address teach serve printed`.
  5. A body other than a JSON object with exactly `lab`, matching `^[a-z][a-z0-9-]{0,39}$`: 400 `body must be {"lab": "<id>"}`.
  6. An invalid `labs/labs.json`: 500 `labs/labs.json is invalid; run teach lint`.
  7. An id the manifest lacks: 404 `no lab`.
  8. For verify, a lab with no `verify`: 404 `no verify`.
  9. Except for stop, no regular file `lessons/*.html` inside the workspace's own `lessons/` folder whose lab section stores the lab's current pin: 409 `no lesson stores this lab's current pin`.
  10. Except for stop, a script the action names (run: each check, then `up`; reset: `down`; verify: `verify`) whose SHA-256 differs from its pin: 409 `pin mismatch: <path>`.
  11. Except for stop, an `env` name that is unset in the server's environment, shorter than 8 characters or holds a line break: 409 `env <NAME> is unset, shorter than 8 characters or multi-line`.
  12. For run and reset, anything running; for verify, anything running other than this lab's `up`: 409 `busy: <id> <action>`, naming the running action.
  13. For stop, neither this lab's run nor its verify running: 409 `not running`. Reset's `down` cannot be stopped from the page.

  Checks 1 to 4 read no byte of the body. Checks 6 to 12 read files with synchronous calls, and the action takes its slot in the same turn, so two requests cannot both pass check 12. No refusal body holds a value from the request; a path or a variable name in one is the manifest's. Once the server has been sent `SIGINT`, `SIGTERM` or `SIGHUP`, a lab `POST` that passes check 5 is 503 `the server is stopping`. The server prints one line per lab request that passes check 5: `lab <id> <action>: <status> <body>` for a refusal, and `lab <id> <action>: 200 <final line>` once an action ends; it never prints a script's output.
- **What runs.** Run runs each of the lab's checks, then `up`; Reset runs `down`; Check my work runs `verify`; Stop runs no script. Each script is started by the one `spawn` call in `bin/lib/labs.mjs`: its absolute path, an empty argument list, `shell: false`, the workspace root as working directory, stdin ignored and `detached: true`, so it leads a process group of its own. Immediately before that call its path is checked against the manifest's path rules and its bytes against its `sha256`, for each check and again for `up` after the checks; a mismatch ends the reply with `lab: not started, pin mismatch: <path>` and starts nothing. The file is then run by its path, so a file swapped in after it was hashed still runs (What the pins do not stop, below). A file whose first two bytes are not `#!` is refused before that call, on every platform, and ends the reply with `lab: could not start: ENOEXEC`. A file the kernel will not execute ends it with `lab: could not start: <code>` (`EACCES` for one without the executable bit, on macOS 27.0.1 with node v22.23.4).
- **The environment a script gets.** `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG` and `LC_ALL` from the server's environment when set (`LAB_ENV_ALLOW`), plus the lab's own `env` names, and nothing else. On macOS 27.0.1, a `#!/bin/sh` script also saw `PWD`, `SHLVL` and `_`, which the shell sets. Anything else a tool needs is declared in `env`, and so redacted.
- **One action at a time.** Run and Reset start only when nothing runs; Check my work also starts beside this lab's running `up`, in a process group of its own. Two Run requests sent together got one 200 and one 409 `busy: <id> run`.
- **The reply.** 200, `Content-Type: text/plain; charset=utf-8`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, sent in chunks as lines arrive. Run first writes `lab: check <n> ok` or `lab: check <n> failed: <message>` for each check, whose own output is read and dropped, and ends with `lab: not started, <k> check(s) failed` when any fails. After a script's output has ended, the server writes one final line: `lab: exit <code>` (the signal's name when a signal ended the script), `lab: stopped`, `lab: stopped (processes remain)`, `lab: timed out after <t> s` or `lab: could not start: <code>`; for verify, `lab: verify pass` on exit 0, else `lab: verify fail (exit <code>)`, `(timed out)` or `(stopped)`. `POST /lab/stop` answers with the stopped line once every group it stopped is gone.
- **Stop.** `SIGTERM` to the process group; after `STOP_GRACE` (5 s), `SIGKILL` if a member remains; then at most `KILL_WAIT` (2 s) for the group to go, checked every 20 ms with `process.kill(-pgid, 0)`, and `lab: stopped (processes remain)` when it does not. The same sequence runs on the rest of a group whose leader exits, on a script that passes its time limit (the lab's `timeout` for `up`, `down` and `verify`, `CHECK_TIMEOUT` (10 s) for a check, which then counts as failed), and on a Run or Check my work whose page closes before its reply ends. A `down` whose page closes runs to its end. A script that ignored `SIGTERM` was ended by the `SIGKILL`. A process that leaves the group, such as one in a new session, is out of reach: one that held the output pipe kept running after the reply ended.
- **Output.** A reply carries at most `LAB_OUTPUT_MAX` (1 MiB) of script output, then `lab: output over 1 MiB not shown`; the rest is read and dropped while the script runs on.
- **Scripts in workspace pages.** A lesson, reference page, asset or brand file served from the workspace can carry a script in the same origin as the lab routes. In a browser with the lab cookie, that script can start a lab's scripts as the page controls can.
- **What the pins do not stop.** The server does not read the claims ledger, so a lab whose lesson stores the current pin runs from the page for whoever holds the session, whether or not that lesson has a verdict. A browser extension with access to the page or its cookies can read the stream and the cookie and drive the routes. Whoever can write the workspace can change a script, `labs/labs.json` and the lesson's pin together and get that script run: the pins catch drift, not a hostile writer, and no reviewer reads a script's bytes (the claims reviewer reads the lesson and the vault). The gap between the hash and the spawn is accepted: a file swapped in after it is hashed still runs. In one run on macOS 27.0.1 with node v22.23.4, a separate process renamed one of two scripts over `labs/up.sh` in a tight loop while `POST /lab/run` repeated for 6 s; of 868 requests, 51 ran the swapped bytes, 46 ran the pinned bytes, and 771 were refused with a pin mismatch.
- **When the server stops.** With `--labs`, `SIGINT`, `SIGTERM` and `SIGHUP` run the Stop sequence on every running group, `down` included, then exit; a second such signal exits at once. An `exit` handler sends `SIGKILL` to every group still running. A `SIGKILL` of the server runs no handler, so a running group outlives it; so does a process that left its group. Without `--labs` or `--terminal` the server keeps its two handlers, `SIGINT` and `SIGTERM`, each calling `process.exit(0)`.
- **Redaction.** The values of the lab's `env` names, as the server's environment holds them at the request, are replaced in each line of a script's stdout and stderr, after a streaming UTF-8 decoder has joined a character split across reads and before the line is cut at `\r`: every character inside a match of any value is marked, and each run of marked characters becomes one `[redacted]`, so values that overlap or nest leave nothing of either. A piece that then starts with `lab:`, once escape sequences, control characters other than tab, and zero-width and bidi characters before it are set aside, is sent with `> ` in front (the piece itself is not changed), so a script cannot write a line that reads as the server's; the widget takes its status only from the reply's final line. A partial line waits for its `\n`, and the last one is redacted at the end. A line over 65536 characters is dropped, with the rest of it up to the next `\n`, and `lab: a line over 65536 characters is not shown` is sent in its place. Not caught: a value the script transforms (base64), prints across two lines or with an escape sequence inside it; a secret not declared in `env`; what a script or a tool writes to its own files or logs. The server writes nothing about a run to disk, the widget stores nothing, and served pages are not redacted: at start `teach serve --labs` prints `warning: <path> holds the value of <NAME>` on stderr for each lesson or reference page whose bytes hold a declared value of 8 or more characters (a shorter value is skipped, as check 11 refuses it for a run), and `teach export` refuses such a copy (below).

## Terminal (`teach serve --terminal`)

`teach serve --terminal [workspace]` serves one shell to the lesson pages, so a learner can run a lesson's commands beside it. Whoever holds `t` or the lab cookie has a shell with the rights of the user who started the server. Use it on a single-user machine and only with a workspace whose pages you trust. The server provides no sandbox for the shell.

- **Off unless asked for.** Without `--terminal`, `GET /term/stream`, `GET /term/lessons/<lesson id>.html`, `GET /terminal/<file>`, `POST /term/input` and `POST /term/resize` are 404 `not found`, and every response is as without it.
- **python3.** At start the server runs `python3 -I -c "import pty"`. The check passes when Python accepts `-I` and imports `pty`. The helper itself needs Python 3.5 or later for `os.set_blocking`. If the check fails, the server prints `teach serve: --terminal needs python3 with its pty module` on stderr and exits 2 before it listens.
- **The address and the cookie are the lab's.** With `--terminal` the server makes `t` and answers `GET /labs/open` as under `--labs` (Lab runs, above), and `next` may also be `/term/lessons/<lesson id>.html`. Without `--labs` it prints `terminal: open http://127.0.0.1:<port>/labs/open?t=<t>` after the serving line; with both flags it prints the `labs: open` line only, and that one address opens both. `t` is not written to `.teach-serve.json`.
- **The shell.** One shell for the server, started by the first `GET /term/stream` that passes its checks and shared by every page that is open: `$SHELL -l`, or `/bin/bash -l` when `SHELL` is unset, in a pseudo-terminal that a `python3` helper (`pty.fork`) holds, with the workspace root as working directory. Both Python starts use `-I -c` from the filesystem root. Isolated mode keeps the working directory off the module search path, skips the user site directory and ignores settings such as `PYTHONPATH`. CPython still reads `PYTHONEXECUTABLE` and `__PYVENV_LAUNCHER__` at startup in isolated mode, so the plugin withholds both from each Python process. Only the forked child changes to the workspace before starting the shell. The child restores `PYTHONEXECUTABLE` to the shell's environment when the server had it. If it cannot enter the workspace or the helper fails to start, the stream ends and the server keeps running. The helper is spawned with `detached: true`, so it leads a process group of its own. A login shell runs the user's rc files, which can change the folder it starts in. Its environment is the server's, without any name that starts with `CLAUDE` and without `__PYVENV_LAUNCHER__`, with `TERM=xterm-256color`; unlike a lab script's, it is not an allow list. When the shell exits, open streams end, and the next stream request starts a new one.
- **`GET /term/stream`.** Needs the lab cookie, else 403 `no terminal cookie; open the address teach serve printed`. Answers 200 `application/octet-stream`, `Cache-Control: no-store`, with the kept output (the last 256 KiB, cut to start after a newline when it holds one), then the shell's output as it comes. A stream whose unsent output passes 4 MiB is cut off; the page opens it again and gets the kept output.
- **`GET /term/lessons/<lesson id>.html`.** Every path under `/term/lessons/` needs the lab cookie, else 403 `no terminal cookie; open the address teach serve printed`. With it, 404 `not found` unless the id matches `^\d{4}-[a-z][a-z0-9-]*$` and `lessons/<id>.html` is a readable file that resolves inside the workspace's own `lessons/` folder; else 200 `text/html; charset=utf-8` with a page the server builds: `/lessons/<id>.html` in a frame, and the terminal beside it under the workspace folder's name, HTML-escaped. The page carries no brand and no navigation bar. It checks that the lesson can be opened without reading its contents.
- **`GET /terminal/<file>`.** No cookie. Sends the named files of the plugin's `skills/research-teach/terminal/`: `terminal.mjs`, `xterm.mjs` and `addon-fit.mjs` as JavaScript, `terminal.css` and `xterm.css` as CSS, `LICENSE-xterm` and `LICENSE-addon-fit` as plain text. The name after `/terminal/` is compared whole with that list; any other name is 404 `not found`.
- **`POST /term/input` and `POST /term/resize`.** Each gets the lab `POST` checks in their order, before a byte of the body is read: `Origin` equal to `http://127.0.0.1:<port>`, `Content-Type: application/json` (optionally `; charset=utf-8`) and a `Content-Length` of at most 65536 bytes, else 403 `forbidden` (a body without it is refused once it passes 65536 bytes); then the lab cookie, else 403 `no terminal cookie; open the address teach serve printed`. Input takes exactly `{"data": "<text>"}` and sends the text to the shell unchanged: 200 `ok`, 409 `terminal not running` when no shell runs, 400 for any other body. Resize takes exactly `{"rows": <1 to 500>, "cols": <1 to 1000>}`, integers: 200 `ok`, 400 for any other body.
- **Pages of another origin.** A page on another `127.0.0.1` port is same-site, and its requests carry the cookie, so it can start the shell with the `GET`; not probed. Not probed: it cannot read the stream, since the server sends no CORS header, and it cannot type, since its `POST` fails the `Origin` check. Not probed: a page of another site sends no cookie, since the cookie is `SameSite=Strict`. The `Host` check answers 403 to any `Host` but `127.0.0.1:<port>`; that it stops DNS rebinding here is not probed. The `GET` has no `Sec-Fetch-Site` check, since starting a shell runs only the user's own rc files, no command the page chooses.
- **The cookie is not kept to one port.** A cookie is not kept to one port, so every server the browser opens on `127.0.0.1`, such as a `kubectl port-forward`, receives it; not probed.
- **Browser extensions.** Not probed: a browser extension with access to the page can type into the shell.
- **Scripts in workspace pages.** A lesson, reference page, asset or brand file served from the workspace can carry a script in the same origin as the terminal routes. In a browser with the lab cookie, that script can type into the shell as the page controls can.
- **When the server stops.** `SIGINT`, `SIGTERM` and `SIGHUP` send `SIGHUP` to the helper's process group before the server exits, and an `exit` handler sends it `SIGKILL`. Either closes the pseudo-terminal, which hangs the shell up; a background job the shell started stopped after such a `SIGHUP`. A process started with `nohup` or `disown` is expected to keep running; not probed. A `SIGKILL` of the server runs no handler.

## Static export (`teach export`)

`teach export [workspace] --out <dir>` writes a copy of one teaching workspace for a learner who opens it from disk with no server.

- **What it copies.** The pages and files `teach serve` returns from `lessons/`, `reference/`, `assets/`, `brand/` and `GLOSSARY.md`, read through the same `serveFile` (which serves `GLOSSARY.md` only when it is not a symlink, so a symlinked one is neither served nor copied), plus the plugin's `quiz.js` and `reading.html` and, when the workspace has no `assets/lesson.css`, the plugin's. An `.html` or `.htm` file the claims gate does not cover is left out. `MISSION.md`, `NOTES.md`, `PATH.md`, `GATE-LOG.md`, learning records, attempts and `evidence/` are not copied, and neither is any vault entry's body.
- **What leaves with the copy from the vault.** `sources.html` carries the title, `source_url`, date and summary of every vault entry a copied page cites. The command prints one `source <id> <url>` line per entry, so the author sees them before sending the copy. A title or summary is HTML-escaped, and a URL is a link only when it is `http:` or `https:`.
- **Paths in the copy.** The export checks that each static folder resolves to its own place in the workspace and its files resolve inside it. It checks the resolved paths of `PATH.md`, `README.md` and `GLOSSARY.md` against the workspace when present. A path outside its allowed place or one that cannot be resolved produces an `unservable "<path>"` line on standard output. The path is JSON-quoted with control and format characters escaped. The command prints `teach export: paths resolve outside their allowed locations or cannot be resolved; nothing written` on standard error and exits 1 before writing. Names starting with `.` under the static folders are skipped. An in-workspace link at `README.md` or `GLOSSARY.md` is omitted from the copy.
- **Gated pages only.** It refuses (exit 1, nothing written) while a lesson, reference doc or the `README.md` has no `PASS` or `MERIT` for its current content, unless `--skip-ungated` leaves those pages out.
- **Labs.** A lesson's lab section is copied as the page `teach serve` serves without `--labs`: its cost line, its step paths and the author's captured output, with no buttons. It refuses (exit 1, nothing written) with `secret <path>: <NAME>` when any file of the copy holds the value, 8 or more characters long, of an `env` name of a valid `labs/labs.json` that is set in the export's environment, and with `lab-manifest labs/labs.json: invalid; run teach lint` when the manifest is invalid and an exported lesson has a lab section.
- **Where it writes.** The export uses `--out` as its output root. It checks that `--out` is absent or an empty directory, refuses a symlink at that name, and requires it to be outside the vault and the workspace's `lessons/`, `reference/`, `assets/` and `brand/` (exit 2). A destination whose separation from one of those locations cannot be established is also refused. The input and `--out` checks run before the first write, so those refusals leave nothing behind. As it writes the copy, the writer checks each resolved destination against `--out` and uses the `wx` flag for each file to prevent overwrites. When a destination check or write fails there, the writer attempts to remove `--out` if it was absent before the run. With an existing `--out`, it attempts to remove the files and directories it recorded as created, in reverse order. A file whose write failed partway may remain in an existing `--out`. A removal can also fail. The command exits 2.
- **What an exported page runs.** The export adds one script, the plugin's `quiz.js`, loaded as a classic `defer` script, and removes none of a page's own. A lesson's navigation bar is written into the file, so it fetches nothing. A finished quiz is saved in the browser's `localStorage` under `research-vault-attempts:<key>`, and Export my results downloads the saved attempts as a file. In headless Chrome 157, a lesson of an exported copy opened from `file://`, answered and exported made three requests, all `file://`: the page, `lesson.css` and `quiz.js`. The results come back only when the learner sends the file and the author runs `teach attempt import` (below).

## Results import (`teach attempt import`)

`teach attempt import <file> [workspace]` records the attempts in a results file, the JSON that quiz.js's `resultsFile` builds when a quiz is taken with no server. The file comes from the learner, so the command treats it as untrusted input.

- **Read, not fetched.** It reads the one local path it is given, refuses a file over 1 MiB before reading it (exit 2), and opens no listener and no network connection.
- **Checked whole before any write.** The file must be JSON with exactly the keys `format`, `version`, `workspace` and `attempts`: `"format": "research-vault-attempts"`, `"version": 1`, `workspace` equal to the workspace directory's name passed through `slugify`, and a non-empty `attempts` array of objects with exactly the keys `lesson`, `answers`, `at`, `total` and `wrong`. Each lesson id must match `^\d{4}-[a-z][a-z0-9-]*$` and name an existing `lessons/<id>.html`, `answers` must be non-negative integers, and `at` must be in `toISOString` form and no later than this machine's clock. Any failure prints one line per problem, exits 1 and writes nothing.
- **Graded here.** Each attempt is regraded against the lesson's own quiz data. A lesson that fails the containment check is treated as having no quiz. One whose lesson has no quiz that parses, whose answers no longer fit the lesson, or whose grade differs from the file's `total` and `wrong`, is reported as `changed` and not written. Every attempt is decided before the first is written. The rest are written through `writeAttempt`, the function `POST /attempt` and `teach attempt add` call, so the score comes from the lesson, not the file, and the attempt file's name comes from the lesson number and `at`; `writeAttempt` never overwrites an existing attempt file. `writeAttempt` creates `attempts/` if it is absent. If a write fails after earlier attempts were written, those files remain. An attempt whose id is already in `attempts/`, or is recorded earlier in the same file, is skipped.
- **Printed escaped.** Every value from the file that a problem line or a `changed` line prints goes through `JSON.stringify`, which escapes a quote, a backslash and U+0000 to U+001F; U+007F to U+009F, U+200E, U+200F, U+202A to U+202E, U+2028, U+2029 and U+2066 to U+2069 are then written as `\uXXXX`. An array or object value is printed as `an array` or `an object`, never walked, so a deeply nested value cannot exhaust the stack. A `changed` line names the lesson only after its id has passed the lesson id pattern.
- **What it cannot check.** It cannot tell answers a learner chose on the page from answers typed into the file, and an attempt's date and id come from the file's `at`, the learner's browser clock.
- **What it writes.** The only planned writes are attempt files under the workspace's `attempts/`. The import checks the resolved paths of the directory and planned attempt files before starting writes. It checks each destination again before writing it. A refused destination exits 2 with the path and reason on standard error.

## Network refresh (`refresh`)

`refresh`, `capture --batch` over a URL list, `capture --fill`, `verify --quotes` and the embedding endpoint (`embed`, `search --semantic`) are the only features that open an outbound network connection, and all are off by default.

- **Double-gated.** It refuses — non-zero exit, including under `--dry-run` — unless you both invoke the `refresh` subcommand *and* set `RESEARCH_VAULT_ALLOW_NETWORK=1`. Either alone does nothing.
- **Hash-only.** It fetches the source URL and buffers the response solely to hash it: it computes the SHA-256 of the raw bytes and compares that to the entry's stored `content_hash`. It never parses, stores, or writes back the fetched bytes, and does no HTML-to-text conversion.
- **Never mutates.** It reports `confirmed`, `changed`, or `unreachable` and defers every edit to `verify`. Entries and the manifest are left byte-identical.
- **A file view on a code host is read as the raw file.** For `https://github.com/<owner>/<repo>/blob/<ref>/<path>` the fetcher requests the same path on `raw.githubusercontent.com`, for `refresh`, the URL-list ingest and `capture --fill` alike, so the hash is of the file and not of the site's page around it. The rewritten address passes the same checks below.
- **`capture --fill <id>` does store text.** It is the one command that fetches a page and writes its text into an existing source entry, and only for an entry that holds under 200 characters of text. It needs `RESEARCH_VAULT_ALLOW_NETWORK=1` and `--ack-data-egress`, refuses a blocklisted or non-https address, and uses the same fetcher and checks as `refresh`. With `--content-file <file>` it reads a saved `.html`, `.htm`, `.txt` or `.md` file in place of the network; that form copies a local file's text into the vault, so it is for a person to run and no skill gives it to an agent. `--discard` removes a text a fill stored.
- **`verify --id <source> --quotes <file>` may fetch and stores nothing.** It looks for each quote on one line of the source's stored text. With `RESEARCH_VAULT_ALLOW_NETWORK=1` it fetches the source's page once, through the same fetcher and checks, when the entry holds no stored text or the stored text lacks a quote, and compares against the page's text in memory. It writes verification rows only: the body and `content_hash` are never changed. Without the variable it opens no connection, and refuses a source that holds no stored text. A blocklisted or non-https address is not fetched.
- **`gate evidence --packet <dir>` copies entries out of the vault.** It writes the listed entries, with stored page text cut to excerpts, into a directory you name outside the vault, for one reviewer round. It refuses a destination whose separation from the vault cannot be established and checks each copy's destination against the packet directory. It opens no connection. The copy holds text of the pages the vault stored, so treat the directory as you treat the vault and delete it after the round.
- **SSRF-hardened:**
  - HTTPS only. Plaintext URLs and `https`-to-`http` redirect downgrades are refused.
  - Every resolved address must be public global-unicast. RFC 6890 private, loopback, link-local, CGNAT, ULA, documentation, multicast, and reserved ranges are rejected — including IPv4-mapped IPv6, alt-encoded numeric hosts, and the cloud metadata address `169.254.169.254`.
  - The socket is pinned to the pre-validated IP. No re-resolution, no connection pooling.
  - Redirects are re-validated per hop against every rule above.
  - A body-size cap and a timeout bound each request. No cookies or auth headers are ever sent.

## Network ingest (`capture --batch <url list>`)

`capture --batch` over a URL list (a file that is not `.json`, one URL per line, `#` comments) fetches each URL to create a source entry. It is the second outbound feature, and it is off by default.

- **Double-gated, like `refresh`.** It refuses unless you both pass a URL list to `capture --batch` *and* set `RESEARCH_VAULT_ALLOW_NETWORK=1`; a JSON plan and a Markdown directory never open a connection.
- **The same fetcher.** Every request goes through the `refresh` fetcher, so every rule in the previous section applies: HTTPS only, public addresses only, the socket pinned, redirects re-validated, a body-size cap and a timeout, no cookies or auth headers. One request per line, in order; there is no rate limit.
- **Writes entries.** Unlike `refresh`, it creates a source per URL with `content_hash` over the raw bytes, which is what `refresh` later compares against. The fetched text lands in the entry only under `--store-body --ack-data-egress`, the gate a single capture has, and it lands raw: no HTML-to-text conversion.

## Embedding endpoint (`embed`, `search --semantic`)

Optional, for a vault whose repo binding sets `"embedding": { "url": "...", "model": "...", "chunk": 800, "overlap": 100 }`. The plugin takes `RESEARCH_VAULT_EMBED_URL` from the environment as the user's own choice.

- **Checks, in order.** Before these checks, `search --semantic` can refuse its own arguments, and if either command fails to load the binding, it prints the binding's error prefixed with `error:` and exits 2. Once a command reaches the embedding gate's checks, it reports the first of these refusals on standard error and exits 1 before resolving the vault or collecting text to send. `<command>` is `embed` or `search`.
  1. The binding has no embedding block. `<command> refused: no embedding endpoint in .research-vault.json`
  2. `RESEARCH_VAULT_ALLOW_NETWORK` is not `1`. `<command> refused: set RESEARCH_VAULT_ALLOW_NETWORK=1 to send text to <address>`
  3. `--ack-data-egress` is missing. `<command> refused: --ack-data-egress is required (the text leaves this process for <address>)`
  4. The binding's URL contains user-info. `<command> refused: embedding endpoint <address> must not contain user-info`
  5. `RESEARCH_VAULT_EMBED_URL` and the binding's `embedding.url` do not match after parsing. Scheme and host case, a default port and an empty path make no difference. `<command> refused: set RESEARCH_VAULT_EMBED_URL to <address> to allow this embedding endpoint`
  6. The URL uses HTTP with a host other than `localhost`, an address in `127.0.0.0/8` or `[::1]`. `<command> refused: embedding endpoint <address> must use HTTPS or loopback HTTP`

  The binding loader requires an HTTP or HTTPS URL in an embedding block. The address shown in these lines is normalized, with user-info removed and control and format characters escaped.
- **What leaves the machine.** `embed` sends the window texts of every non-superseded entry (bodies included) to the endpoint, in batches of 64, one `POST` per batch; `search --semantic` sends the query, one `POST`. The request is `{ input, model }` as JSON, with `Authorization: Bearer <RESEARCH_VAULT_EMBED_KEY>` only when that variable is set. Nothing else is sent.
- **Where.** The request goes through Node's global `fetch` with redirects refused. The `refresh` fetcher's SSRF guard does not apply to the embedding request. An approved HTTPS host can resolve to a private address. Before the first request the command writes `embed: sending <n> windows of <m> entries to <address>` or `search: sending the query to <address>` on standard error.
- **Request failure.** A failed request or unusable response exits 1. After the sending line it writes one line on standard error, prefixed with `embed refused: ` or `search refused: `: `embedding endpoint request failed`, `embedding endpoint <status>`, `embedding endpoint returned invalid JSON`, `embedding endpoint returned no vectors for <n> texts`, `embedding endpoint returned <m> vectors for <n> texts` or `embedding endpoint returned an invalid vector`. It prints no response body.
- **One index written.** After the requests, `embed` checks its index destination against the vault and writes `_index/embeddings.jsonl` (a header line, then one line per window with its text and vector). The template's `.gitignore` ignores the index, which is safe to delete. `search --semantic` appends its usage-log line as `search` does. No entry is modified.

## Data export (`export`)

`export` is the only path that writes vault content to an external file, and it is conservative by default.

- **Metadata-first.** By default it emits only **answered questions** as `{input, output}` pairs, each with per-record metadata — no other entry types, never any entry body, never a `source` body. `--scope <types>` widens it to other types as `{input: title, output: summary}` records — the entry's `summary` field when present, empty otherwise; still no entry body.
- **Body egress is double-gated.** Including any entry body requires both `--include-bodies` *and* `--ack-data-egress`. `--include-bodies` without the ack refuses and writes nothing; `--ack-data-egress` alone is inert — the export proceeds but emits only the default metadata and `summary` records, no bodies. `--chunk` windows the same `output` the gate allows, so a body still needs both flags.
- **Deterministic and offline.** Output is stable, id-sorted JSONL for an external pipeline. `--out` requires a destination that can be established to be outside the vault. Nothing is sent over the network and the vault is never modified.

See [`docs/FINETUNING.md`](docs/FINETUNING.md) for the export format and intended pipeline.
