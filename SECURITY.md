# Security model

`research-vault` is a local Markdown toolkit. Six features reach outside the vault (`refresh`, `capture --batch` over a URL list, the embedding endpoint behind `embed` and `search --semantic`, `export`, `teach serve` and the lab runs of `teach serve --labs`), and this document is the exhaustive contract for all six. The README explains *when* to use them; this explains *what they guarantee*.

## Reporting a vulnerability

Email **andrew.brooks.aob@gmail.com** with details and a reproduction. Please don't open a public issue for a security report.

## Threat model in one line

Everything is local. The features that reach outside the vault are off or conservative until you opt in per run. `refresh` and `export` never mutate entries. Without `--labs`, `teach serve` writes only in the teaching workspace it serves; with it, it also runs the lab scripts a workspace pins, which write wherever they write.

## Local writers

One local process writes your entries without a per-run prompt: the advisory `PostToolUse` hook re-runs `lint --fix` and a manifest rebuild on the vault after a vault-file edit. It touches only local files inside the vault, never the network, and is convenience-only — the `lint` correctness gate does not depend on it.

A second local process, `teach serve`, writes learner data, not entries: one attempt file in the workspace's `attempts/` per accepted `POST /attempt`, and `.teach-serve.json`. Its limits are in the next section. With `--labs` it also runs the lab scripts a workspace pins, which write wherever they write (Lab runs, below).

A third local write is the usage log, `_index/usage.jsonl` in the vault, appended by the pre-web hook, the post-edit hook and `search`: ids, facets and an outcome per event, never the fetched page, and free query text only when the repo's binding sets `usage.text` to `true`. It stays under `_index/`, which the vault's `.gitignore` ignores, and nothing reads it but the vault's own reports.

## Lesson server (`teach serve`)

`teach serve [workspace]` serves one teaching workspace to a browser so a lesson's quiz can record an attempt and, with `--labs`, run a lesson's lab. It runs until it is stopped.

- **Loopback only.** It listens on `127.0.0.1` on a port the operating system assigns (`listen(0, '127.0.0.1')`) and prints `serving <workspace> at http://127.0.0.1:<port>/`. It never listens on another interface.
- **Exact `Host`, before any work.** Every request, of any method, must carry `Host: 127.0.0.1:<port>` with the server's own port. Anything else, a missing `Host` included, is 403 before the path is read. A request whose `Host` is any other value is refused, for GET and POST alike.
- **Static reads from an allowlist.** `GET` and `HEAD` serve files only from `lessons/`, `reference/` and `assets/`, each path checked with `isInsideVault` against that directory, plus the exact file `GLOSSARY.md`. `GET /` answers with an HTML index of the lessons and reference docs, and `GET /lessons.json` with the same list as JSON (title, URL, and each lesson's `PATH.md` line number, shape and closing `Project:` line); `GET /lessons.json` reads only `lessons/`, `reference/` and `PATH.md`, and `GET /` reads those and the workspace's `README.md`, which it renders from Markdown above the index, with `&`, `<`, `>` and `"` of the source escaped, so raw HTML shows as text, and a link kept as a link only when its target is `http:`, `https:` or has no scheme. Everything else is 404 (without `--labs`; with it, `GET /labs/open` also answers, below), including `NOTES.md`, `MISSION.md`, learning records, attempts, `evidence/`, `.teach-serve.json`, a directory, a path with a NUL byte and any path segment that starts with `.` (so `..` escapes, encoded or not). A path that does not URL-decode is 400. A method other than `GET`, `HEAD` or `POST` is 405. Every response carries `X-Content-Type-Options: nosniff`.
- **One write, `POST /attempt`.** A `POST` to any other path is 404, except, with `--labs`, the four lab routes below, which start a lab's scripts. Before the body is read, the request must carry `Origin` equal to the server's own `http://127.0.0.1:<port>`, `Content-Type: application/json` (optionally with `; charset=utf-8`), and, when `Content-Length` is present, a length of at most `ATTEMPT_BODY_MAX` (4096) bytes. Anything else is 403. A body sent without `Content-Length` is counted as it arrives and is refused with 403 once it passes 4096 bytes.
- **Validated body.** The body must be the JSON object `{ "lesson": "<lesson id>", "answers": [integers] }`. The lesson id must match `^\d{4}-[a-z][a-z0-9-]*$` and name an existing `lessons/<id>.html`, and `answers` must hold one integer per quiz item, each an index of that item's options. Anything else is 400 and no attempt file is written. A lesson whose quiz data does not parse, or a failed write, is 500.
- **The server grades.** The client sends answers, never a score. The server grades them against the lesson's own quiz data through `writeAttempt`, the same function `teach attempt add` calls, and replies `{ "id", "score", "total", "wrong" }`.
- **Its other write.** On start it writes `.teach-serve.json` (`{ port, pid }`) in the workspace and removes it on exit, including on `SIGINT` and `SIGTERM` (with `--labs`, also on `SIGHUP`). Besides that file and the attempt files, it writes nothing; with `--labs`, the lab scripts it starts write wherever they write.

## Lab runs (`teach serve --labs`)

`teach serve --labs [workspace]` adds routes for the labs the workspace's `labs/labs.json` declares (LESSON-FORMAT.md, Labs), and runs a lab's scripts when a lab `POST` passes every check below. Use it on a single-user machine: a script runs with the rights of the user who started the server, and nothing here is a sandbox.

- **Off unless asked for.** Without `--labs`, `GET /labs/open` and `POST /lab/<action>` are 404 `not found`, as before, and no cookie is set. With `--labs`, an invalid `labs/labs.json` exits 2 before the server listens.
- **The lab address.** At start the server makes `t`, 64 hex characters from `randomBytes(32)`, and prints `labs: open http://127.0.0.1:<port>/labs/open?t=<t>` once in its terminal. `t` is not written to `.teach-serve.json`, a page, a response body or a log line.
- **Opening it.** Every `GET /labs/open` whose one `t` parameter equals `t`, compared with `timingSafeEqual` once the lengths match, answers 303 with `Set-Cookie: rv-labs-<port>=<session value>; HttpOnly; SameSite=Strict; Path=/`, to `next` when it is `/lessons/<lesson id>.html`, else to `/`. The session value, a second 64-hex value, is made at the first open and is the same at every later one while that server runs, so the same address works again after a browser restart or in a second browser. A wrong or missing `t` is 403 and sets no cookie. Anyone who reads `t`, in the terminal, an `open` command line, a transcript or browser history, can open the address while that server runs; `--labs` is meant for a single-user machine.
- **No framing.** With `--labs`, every response carries `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'`; without it, neither. A page on another `127.0.0.1` port is same-site, so the browser sends it the lab cookie when it frames a lesson.
- **What a page shows of a lab.** Every lesson page `teach serve` serves, with or without `--labs`, and every lesson page `teach export` copies, reads `labs/labs.json` and, when it is valid and names the lesson's lab, shows the lab's cost line and the paths of its `up`, `verify` and `down` scripts, a path under `evidence/` or `labs/` included, though those directories are not otherwise served or copied.
- **Checks, in order.** `POST /lab/run`, `/lab/stop`, `/lab/reset` and `/lab/verify` are refused by the first check that fails:
  1. `Host` other than `127.0.0.1:<port>`: 403 `forbidden`.
  2. A path other than `/attempt` and the four: 404 `not found`.
  3. `Origin` other than `http://127.0.0.1:<port>`, a `Content-Type` other than `application/json` (optionally `; charset=utf-8`), a `Content-Length` over `LAB_BODY_MAX` (256), or a body without it that passes 256 bytes: 403 `forbidden`.
  4. No `rv-labs-<port>` cookie equal to the session value, compared as `t` is: 403 `no lab cookie; open the lab address teach serve printed`.
  5. A body other than a JSON object with exactly `lab`, matching `^[a-z][a-z0-9-]{0,39}$`: 400 `body must be {"lab": "<id>"}`.
  6. An invalid `labs/labs.json`: 500 `labs/labs.json is invalid; run teach lint`.
  7. An id the manifest lacks: 404 `no lab`.
  8. For verify, a lab with no `verify`: 404 `no verify`.
  9. Except for stop, no regular file `lessons/*.html` whose lab section stores the lab's current pin: 409 `no lesson stores this lab's current pin`.
  10. Except for stop, a script the action names (run: each check, then `up`; reset: `down`; verify: `verify`) whose SHA-256 differs from its pin: 409 `pin mismatch: <path>`.
  11. Except for stop, an `env` name that is unset in the server's environment, shorter than 8 characters or holds a line break: 409 `env <NAME> is unset, shorter than 8 characters or multi-line`.
  12. For run and reset, anything running; for verify, anything running other than this lab's `up`: 409 `busy: <id> <action>`, naming the running action.
  13. For stop, neither this lab's run nor its verify running: 409 `not running`. Reset's `down` cannot be stopped from the page.

  Checks 1 to 4 read no byte of the body. Checks 6 to 12 read files with synchronous calls, and the action takes its slot in the same turn, so two requests cannot both pass check 12. No refusal body holds a value from the request; a path or a variable name in one is the manifest's. Once the server has been sent `SIGINT`, `SIGTERM` or `SIGHUP`, a lab `POST` that passes check 5 is 503 `the server is stopping`. The server prints one line per lab request that passes check 5: `lab <id> <action>: <status> <body>` for a refusal, and `lab <id> <action>: 200 <final line>` once an action ends; it never prints a script's output.
- **What runs.** Run runs each of the lab's checks, then `up`; Reset runs `down`; Check my work runs `verify`; Stop runs no script. Each script is started by the one `spawn` call in `bin/lib/labs.mjs`: its absolute path, an empty argument list, `shell: false`, the workspace root as working directory, stdin ignored and `detached: true`, so it leads a process group of its own. Immediately before that call its path is checked against the manifest's path rules and its bytes against its `sha256`, for each check and again for `up` after the checks; a mismatch ends the reply with `lab: not started, pin mismatch: <path>` and starts nothing. The file is then run by its path, so a file swapped in after it was hashed still runs (What the pins do not stop, below). A file the kernel will not execute ends it with `lab: could not start: <code>` (`ENOEXEC` for a file with no `#!` line, `EACCES` for one without the executable bit, on macOS 27.0.1 with node v22.23.4).
- **The environment a script gets.** `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG` and `LC_ALL` from the server's environment when set (`LAB_ENV_ALLOW`), plus the lab's own `env` names, and nothing else. On macOS 27.0.1, a `#!/bin/sh` script also saw `PWD`, `SHLVL` and `_`, which the shell sets. Anything else a tool needs is declared in `env`, and so redacted.
- **One action at a time.** Run and Reset start only when nothing runs; Check my work also starts beside this lab's running `up`, in a process group of its own. Two Run requests sent together got one 200 and one 409 `busy: <id> run`.
- **The reply.** 200, `Content-Type: text/plain; charset=utf-8`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, sent in chunks as lines arrive. Run first writes `lab: check <n> ok` or `lab: check <n> failed: <message>` for each check, whose own output is read and dropped, and ends with `lab: not started, <k> check(s) failed` when any fails. After a script's output has ended, the server writes one final line: `lab: exit <code>` (the signal's name when a signal ended the script), `lab: stopped`, `lab: stopped (processes remain)`, `lab: timed out after <t> s` or `lab: could not start: <code>`; for verify, `lab: verify pass` on exit 0, else `lab: verify fail (exit <code>)`, `(timed out)` or `(stopped)`. `POST /lab/stop` answers with the stopped line once every group it stopped is gone.
- **Stop.** `SIGTERM` to the process group; after `STOP_GRACE` (5 s), `SIGKILL` if a member remains; then at most `KILL_WAIT` (2 s) for the group to go, checked every 20 ms with `process.kill(-pgid, 0)`, and `lab: stopped (processes remain)` when it does not. The same sequence runs on the rest of a group whose leader exits, on a script that passes its time limit (the lab's `timeout` for `up`, `down` and `verify`, `CHECK_TIMEOUT` (10 s) for a check, which then counts as failed), and on a Run or Check my work whose page closes before its reply ends. A `down` whose page closes runs to its end. A script that ignored `SIGTERM` was ended by the `SIGKILL`. A process that leaves the group, such as one in a new session, is out of reach: one that held the output pipe kept running after the reply ended.
- **Output.** A reply carries at most `LAB_OUTPUT_MAX` (1 MiB) of script output, then `lab: output over 1 MiB not shown`; the rest is read and dropped while the script runs on.
- **What the pins do not stop.** The server does not read the claims ledger, so a lab whose lesson stores the current pin runs from the page for whoever holds the session, whether or not that lesson has a verdict. A browser extension with access to the page or its cookies can read the stream and the cookie and drive the routes. Whoever can write the workspace can change a script, `labs/labs.json` and the lesson's pin together and get that script run: the pins catch drift, not a hostile writer, and no reviewer reads a script's bytes (the claims reviewer reads the lesson and the vault). The gap between the hash and the spawn is accepted: a file swapped in after it is hashed still runs. In one run on macOS 27.0.1 with node v22.23.4, a separate process renamed one of two scripts over `labs/up.sh` in a tight loop while `POST /lab/run` repeated for 6 s; of 868 requests, 51 ran the swapped bytes, 46 ran the pinned bytes, and 771 were refused with a pin mismatch.
- **When the server stops.** With `--labs`, `SIGINT`, `SIGTERM` and `SIGHUP` run the Stop sequence on every running group, `down` included, then exit; a second such signal exits at once. An `exit` handler sends `SIGKILL` to every group still running. A `SIGKILL` of the server runs no handler, so a running group outlives it; so does a process that left its group. Without `--labs` the server keeps its two handlers, `SIGINT` and `SIGTERM`, each calling `process.exit(0)`.
- **Redaction.** The values of the lab's `env` names, as the server's environment holds them at the request, are replaced in each line of a script's stdout and stderr, after a streaming UTF-8 decoder has joined a character split across reads and before the line is cut at `\r`: every character inside a match of any value is marked, and each run of marked characters becomes one `[redacted]`, so values that overlap or nest leave nothing of either. A piece that then starts with `lab:`, once escape sequences, control characters other than tab, and zero-width and bidi characters before it are set aside, is sent with `> ` in front (the piece itself is not changed), so a script cannot write a line that reads as the server's; the widget takes its status only from the reply's final line. A partial line waits for its `\n`, and the last one is redacted at the end. A line over 65536 characters is dropped, with the rest of it up to the next `\n`, and `lab: a line over 65536 characters is not shown` is sent in its place. Not caught: a value the script transforms (base64), prints across two lines or with an escape sequence inside it; a secret not declared in `env`; what a script or a tool writes to its own files or logs. The server writes nothing about a run to disk, the widget stores nothing, and served pages are not redacted: at start `teach serve --labs` prints `warning: <path> holds the value of <NAME>` on stderr for each lesson or reference page whose bytes hold a declared value of 8 or more characters (a shorter value is skipped, as check 11 refuses it for a run), and `teach export` refuses such a copy (below).

## Static export (`teach export`)

`teach export [workspace] --out <dir>` writes a copy of one teaching workspace for a learner who opens it from disk with no server.

- **What it copies.** The pages and files `teach serve` returns from `lessons/`, `reference/`, `assets/` and `GLOSSARY.md`, read through the same `serveFile` (which serves `GLOSSARY.md` only when it is not a symlink, so a symlinked one is neither served nor copied), plus the plugin's `quiz.js` and `reading.html` and, when the workspace has no `assets/lesson.css`, the plugin's. An `.html` or `.htm` file the claims gate does not cover is left out. `MISSION.md`, `NOTES.md`, `PATH.md`, `GATE-LOG.md`, learning records, attempts and `evidence/` are not copied, and neither is any vault entry's body.
- **What leaves with the copy from the vault.** `sources.html` carries the title, `source_url`, date and summary of every vault entry a copied page cites. The command prints one `source <id> <url>` line per entry, so the author sees them before sending the copy. A title or summary is HTML-escaped, and a URL is a link only when it is `http:` or `https:`.
- **Gated pages only.** It refuses (exit 1, nothing written) while a lesson, reference doc or the `README.md` has no `PASS` or `MERIT` for its current content, unless `--skip-ungated` leaves those pages out.
- **Labs.** A lesson's lab section is copied as the page `teach serve` serves without `--labs`: its cost line, its step paths and the author's captured output, with no buttons. It refuses (exit 1, nothing written) with `secret <path>: <NAME>` when any file of the copy holds the value, 8 or more characters long, of an `env` name of a valid `labs/labs.json` that is set in the export's environment, and with `lab-manifest labs/labs.json: invalid; run teach lint` when the manifest is invalid and an exported lesson has a lab section.
- **Where it writes.** Only under `--out`, which must be absent or an empty directory, not a symlink, and not inside the vault or the workspace's `lessons/`, `reference/` or `assets/` (exit 2). Every check runs before the first write, so a refusal leaves no directory behind. Each file is written with the `wx` flag, so none is overwritten, and a path that resolves outside `--out` stops the command. When a write fails part way, it removes what the run created (`--out` itself when it was absent) and exits 2. It writes nothing in the workspace outside `--out`, and nothing in the vault.
- **What an exported page runs.** The export adds one script, the plugin's `quiz.js`, loaded as a classic `defer` script, and removes none of a page's own. A lesson's navigation bar is written into the file, so it fetches nothing. A finished quiz is saved in the browser's `localStorage` under `research-vault-attempts:<key>`, and Export my results downloads the saved attempts as a file. In headless Chrome 157, a lesson of an exported copy opened from `file://`, answered and exported made three requests, all `file://`: the page, `lesson.css` and `quiz.js`. The results come back only when the learner sends the file and the author runs `teach attempt import` (below).

## Results import (`teach attempt import`)

`teach attempt import <file> [workspace]` records the attempts in a results file, the JSON that quiz.js's `resultsFile` builds when a quiz is taken with no server. The file comes from the learner, so the command treats it as untrusted input.

- **Read, not fetched.** It reads the one local path it is given, refuses a file over 1 MiB before reading it (exit 2), and opens no listener and no network connection.
- **Checked whole before any write.** The file must be JSON with exactly the keys `format`, `version`, `workspace` and `attempts`: `"format": "research-vault-attempts"`, `"version": 1`, `workspace` equal to the workspace directory's name passed through `slugify`, and a non-empty `attempts` array of objects with exactly the keys `lesson`, `answers`, `at`, `total` and `wrong`. Each lesson id must match `^\d{4}-[a-z][a-z0-9-]*$` and name an existing `lessons/<id>.html`, `answers` must be non-negative integers, and `at` must be in `toISOString` form and no later than this machine's clock. Any failure prints one line per problem, exits 1 and writes nothing.
- **Graded here.** Each attempt is regraded against the lesson's own quiz data. One whose lesson has no quiz that parses, whose answers no longer fit the lesson, or whose grade differs from the file's `total` and `wrong`, is reported as `changed` and not written. Every attempt is decided before the first is written. The rest are written through `writeAttempt`, the function `POST /attempt` and `teach attempt add` call, so the score comes from the lesson, not the file, and the attempt file's name comes from the lesson number and `at`; `writeAttempt` never overwrites an existing attempt file. An attempt whose id is already in `attempts/`, or is recorded earlier in the same file, is skipped.
- **Printed escaped.** Every value from the file that a problem line or a `changed` line prints goes through `JSON.stringify`, which escapes a quote, a backslash and U+0000 to U+001F; U+007F to U+009F, U+200E, U+200F, U+202A to U+202E, U+2028, U+2029 and U+2066 to U+2069 are then written as `\uXXXX`. An array or object value is printed as `an array` or `an object`, never walked, so a deeply nested value cannot exhaust the stack. A `changed` line names the lesson only after its id has passed the lesson id pattern.
- **What it cannot check.** It cannot tell answers a learner chose on the page from answers typed into the file, and an attempt's date and id come from the file's `at`, the learner's browser clock.
- **What it writes.** Only attempt files in the workspace's `attempts/`.

## Network refresh (`refresh`)

`refresh`, `capture --batch` over a URL list and the embedding endpoint (`embed`, `search --semantic`) are the only features that open an outbound network connection, and all are off by default.

- **Double-gated.** It refuses — non-zero exit, including under `--dry-run` — unless you both invoke the `refresh` subcommand *and* set `RESEARCH_VAULT_ALLOW_NETWORK=1`. Either alone does nothing.
- **Hash-only.** It fetches the source URL and buffers the response solely to hash it: it computes the SHA-256 of the raw bytes and compares that to the entry's stored `content_hash`. It never parses, stores, or writes back the fetched bytes, and does no HTML-to-text conversion.
- **Never mutates.** It reports `confirmed`, `changed`, or `unreachable` and defers every edit to `verify`. Entries and the manifest are left byte-identical.
- **SSRF-hardened:**
  - HTTPS only. Plaintext URLs and `https`-to-`http` redirect downgrades are refused.
  - Every resolved address must be public global-unicast. RFC 6890 private, loopback, link-local, CGNAT, ULA, documentation, multicast, and reserved ranges are rejected — including IPv4-mapped IPv6, alt-encoded numeric hosts, and the cloud metadata address `169.254.169.254`.
  - The socket is pinned to the pre-validated IP. No re-resolution, no connection pooling.
  - Redirects are re-validated per hop against every rule above.
  - A body-size cap and a timeout bound each request. No cookies or auth headers are ever sent.

## Network ingest (`capture --batch <url list>`)

`capture --batch` over a URL list (a file that is not `.json`, one URL per line, `#` comments) fetches each URL to create a source entry. It is the second outbound feature, and it is off by default.

- **Double-gated, like `refresh`.** It refuses unless you both pass a URL list to `capture --batch` *and* set `RESEARCH_VAULT_ALLOW_NETWORK=1`; a JSON plan and a Markdown directory never open a connection.
- **The same fetcher.** Every request goes through the `refresh` fetcher, so every rule in the previous section applies: HTTPS only, public addresses only, the socket pinned, redirects re-validated, a body-size cap and a timeout, no cookies or auth headers. One request per line, in order; there is no rate limit.
- **Writes entries.** Unlike `refresh`, it creates a source per URL with `content_hash` over the raw bytes, which is what `refresh` later compares against. The fetched text lands in the entry only under `--store-body --ack-data-egress`, the gate a single capture has, and it lands raw: no HTML-to-text conversion.

## Embedding endpoint (`embed`, `search --semantic`)

Optional, for a vault whose repo binding sets `"embedding": { "url": "...", "model": "...", "chunk": 800, "overlap": 100 }`. Without the block both commands refuse and nothing is written. With it:

- **Double-gated, plus the egress acknowledgement.** Each command refuses unless `RESEARCH_VAULT_ALLOW_NETWORK=1` is set *and* `--ack-data-egress` is given, before any request.
- **What leaves the machine.** `embed` sends the window texts of every non-superseded entry (bodies included) to the endpoint, in batches of 64, one `POST` per batch; `search --semantic` sends the query, one `POST`. The request is `{ input, model }` as JSON, with `Authorization: Bearer <RESEARCH_VAULT_EMBED_KEY>` only when that variable is set. Nothing else is sent.
- **Where.** To the binding's `url`, which the operator chose and which may be local, so the `refresh` fetcher's SSRF guard is not applied; the request goes through Node's global `fetch`.
- **One file written.** `_index/embeddings.jsonl` in the vault (a header line, then one line per window with its text and vector), ignored by the template's `.gitignore` and safe to delete; `search --semantic` also appends its usage-log line as `search` does. No entry is modified.

## Data export (`export`)

`export` is the only path that writes vault content to an external file, and it is conservative by default.

- **Metadata-first.** By default it emits only **answered questions** as `{input, output}` pairs, each with per-record metadata — no other entry types, never any entry body, never a `source` body. `--scope <types>` widens it to other types as `{input: title, output: summary}` records — the entry's `summary` field when present, empty otherwise; still no entry body.
- **Body egress is double-gated.** Including any entry body requires both `--include-bodies` *and* `--ack-data-egress`. `--include-bodies` without the ack refuses and writes nothing; `--ack-data-egress` alone is inert — the export proceeds but emits only the default metadata and `summary` records, no bodies. `--chunk` windows the same `output` the gate allows, so a body still needs both flags.
- **Deterministic and offline.** Output is stable, id-sorted JSONL for an external pipeline. Nothing is sent over the network and the vault is never modified.

See [`docs/FINETUNING.md`](docs/FINETUNING.md) for the export format and intended pipeline.
