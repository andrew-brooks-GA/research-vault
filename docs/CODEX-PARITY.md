## Hooks

Two open questions apply to all four rows. First, the plugin writes each hook as `"command": "node"` with an `args` array holding `${CLAUDE_PLUGIN_ROOT}/hooks/<file>.mjs` (2026-11-11-repo-lines-behind-codex-parity-matrix); the Codex hooks page shows `command` as one string and does not mention `args` (2026-11-11-codex-docs-hooks), so whether Codex runs that form is open question 2026-11-11-does-codex-accept-hooks-json-command. Second, the pages disagree on plugin hooks in the CLI. The hooks page says Codex "can also discover hooks bundled with enabled plugins" and tells CLI users to open `/hooks` to trust them (2026-11-11-codex-docs-hooks). The packaging page says "Lifecycle hooks are supported for plugins installed manually in Codex desktop" (2026-11-11-codex-docs-package-your-plugin). That is open question 2026-11-11-does-codex-cli-run-plugin-bundled. Judgment: hooks placed in a user's `~/.codex/hooks.json` or a trusted project's `.codex/hooks.json`, both locations the hooks page lists, would not depend on the second question. Every non-managed hook must be reviewed and trusted before it runs, `/hooks` can disable one, and a one-off invocation can pass `--dangerously-bypass-hook-trust` (2026-11-11-codex-docs-hooks).

## Decisions for the rest of issue 67

### 1. Which path replaces `${CLAUDE_PLUGIN_ROOT}`

Options the evidence allows: keep the variable in hooks, since Codex sets `CLAUDE_PLUGIN_ROOT` and `PLUGIN_ROOT` for plugin hook commands (2026-11-11-codex-docs-hooks). For skill and command text, put the CLI on `PATH` through the `bin` entry `package.json` already declares (2026-11-11-repo-lines-behind-codex-parity-matrix), or have the text derive the path from the skill's own location, which Codex lists with each skill (2026-11-11-codex-docs-build-skills). Judgment: the CLI on `PATH` for skill and command text, the variable for hooks; open question 2026-11-11-does-codex-expand-claude-plugin-root decides whether the variable could also stay in skill text.

### 2. Whether skill and command text is written without host-specific wording or generated per host

Issue 67 item 3 asks for one or the other (2026-11-11-research-vault-issue-67-codex-full). The Skills and Commands rows above show the scope: three skills hold host-specific names this page checks for (research-claims-gate, research-orchestrate, research-teach), the other six hold none, and six of the seven command files run the CLI through `${CLAUDE_PLUGIN_ROOT}` (2026-11-11-repo-lines-behind-codex-parity-matrix).

Option one is one text for both hosts. The six skills with no host-specific name need no change. The three that have one, and the six command files, get wording that holds on both hosts, with a short step per host where the mechanism differs: the reviewer and reader dispatch (decision 4), the interview dialog and the Workflow tool. What it costs, as this document judges it: every reader of those three skills sees both hosts' steps, and a step that no host-neutral wording covers stays host-specific in the shared text.

Option two is one source with a generated variant per host. What it costs, as this document judges it: a build step, a check that each generated copy matches its source, and two copies of every affected file in the package.

Judgment: option one, because the host-specific passages sit in three skills and the command files' CLI path, which decision 1 already replaces; generation is worth its build step only if those passages grow.

### 3. Where the Codex agent definitions live

Options: a project `.codex/agents/<name>.toml` or a personal `~/.codex/agents/<name>.toml` (2026-11-11-codex-docs-subagents-custom-agents); a profile file `~/.codex/<name>.config.toml` selected with `codex exec --profile` (2026-11-11-codex-docs-advanced-config); or the model and effort on the gate's own `codex exec` command line: `-m` for the model (2026-11-11-codex-docs-models) and a `-c key=value` override for the effort. The CLI reference says such overrides "take precedence for that invocation" and that the base command's global flags "Most propagate to commands" (2026-11-11-codex-docs-developer-commands-cli-reference), but no captured passage shows `-c` with `codex exec`. Each records the Codex model and effort in TOML or on a command line, none in a Claude agent file's frontmatter, so the matrix does not show that they can only be recorded in `agents/claims-reviewer.md`. Judgment: leave `agents/claims-reviewer.md` unedited and put the Codex definitions in files of their own, taking the reviewer's instructions from the body of the existing agent file. Editing that file would also change the reviewer hash each new ledger row carries, and docs/REFERENCE.md says that after a change to the agent file `gate status` prints `none (reviewer changed)` for a file whose passing rows all came from the earlier one (2026-11-11-repo-lines-behind-codex-parity-matrix). Whether a plugin can ship a custom agent at all is not established (open question 2026-11-11-does-codex-load-claude-code-plugin).

### 4. How a fresh-context reviewer starts

Option one is a custom-agent subagent. In the rust-v0.167.1 source the v1 spawn tool starts the agent "with only the initial prompt" unless the parent passes `fork_context` as true (2026-11-11-codex-source-rust-v0-167-1, 2026-11-11-spawn-agent-v1-handler-codex-source). The v2 tool's `fork_turns` "Defaults to `all`" (2026-11-11-codex-source-rust-v0-167-1), and the `multi_agent_v2` feature is off by default (2026-11-11-multi-agent-feature-defaults-codex-source). A subagent inherits the parent's sandbox (2026-11-11-codex-docs-subagents-custom-agents).

Option two is a separate `codex exec` run. With no subcommand it "runs a new non-interactive session" (2026-11-11-codex-exec-cli-flags-codex-source); continuing an earlier one takes `codex exec resume` or `codex exec fork` (2026-11-11-codex-docs-non-interactive-mode-codex, 2026-11-11-codex-docs-developer-commands-cli-reference). It runs in a read-only sandbox by default, `--ephemeral` keeps no session rollout files, and `-o` writes the final message to a file (2026-11-11-codex-docs-non-interactive-mode-codex).

Judgment: `codex exec`, which issue 67 already names for the case of no isolated subagent, with a prompt holding only the draft path, the vault path and the evidence list (2026-11-11-research-vault-issue-67-codex-full). The new session and the read-only sandbox come with the command, while a subagent's history depends on an argument the parent model chooses and its sandbox on the parent's. The skill then records the verdict with `gate record` to the same ledger, as the issue's acceptance criteria ask. The AGENTS.md page says Codex "builds an instruction chain when it starts (once per run" and shows a `codex exec` run that lists its active instruction sources (2026-11-11-codex-docs-custom-instructions-agents-md); how to stop that run loading AGENTS.md is open question 2026-11-11-can-codex-review-run-skip-agents.

### 5. The Codex enforcement point for the Stop gate

Options: the Codex `Stop` hook, whose output contract matches `stop-gate.mjs` but which runs only when loaded and trusted (2026-11-11-codex-docs-hooks, open question 2026-11-11-does-codex-cli-run-plugin-bundled); or the git pre-commit hook, which runs `gate staged --check` once a clone sets `core.hooksPath` to `.githooks` (2026-11-11-repo-lines-behind-codex-parity-matrix). Of tool hooks, the hooks page says "Treat tool hooks as a useful guardrail, not a complete enforcement boundary" (2026-11-11-codex-docs-hooks). Judgment: the pre-commit hook is the Codex enforcement point, and the plugin's docs say so, as issue 67 item 5 asks for the case where Codex has no lifecycle hook. The `Stop` hook ships too, as an earlier warning where the user trusts it.

### 6. Which model and reasoning effort each agent gets on Codex

The models page calls `gpt-6-astra` "Our most capable model for complex work across code, apps, and research" and lists it for the Codex CLI; it calls `gpt-6.1-sol` "Near-Astra performance for complex work at a lower cost than Astra" (2026-11-11-codex-docs-models). The subagents page gives its own starting points: "`gpt-6.1-sol`: Start here for demanding agents", "`gpt-6-luna`: Use for fast, narrowly scoped agents handling clear, repeatable, or high-volume work", and "For most tasks in Codex, start with `gpt-6.1-sol` when your signed-in account or workspace has access"; on effort it says "For explicit model settings, start with `high` for GPT-6 Luna or `low` for GPT-6 Astra." (2026-11-11-codex-docs-subagents-custom-agents). Judgment: `model = "gpt-6-astra"` and `model_reasoning_effort = "high"` for both claims-reviewer and lesson-reader, which is the strongest model at high effort that issue 67 asks for. ### 7. Whether the CI job's gate dispatch is stubbed or uses a secret

What the evidence says: `codex exec` "reuses saved CLI authentication by default", and in CI "it's common to provide credentials explicitly" (2026-11-11-codex-docs-non-interactive-mode-codex). The page says not to set `OPENAI_API_KEY` or `CODEX_API_KEY` as a job-level variable in a workflow that checks out or runs repository-controlled code, to use the Codex GitHub Action on GitHub Actions, and elsewhere to set `CODEX_API_KEY` "only for the Codex invocation that needs it" (2026-11-11-codex-docs-non-interactive-mode-codex). The current CI job runs the tests, `init`, `lint`, the drift and encoding checks and `lint:self`, and names no secret (2026-11-11-repo-lines-behind-codex-parity-matrix).

Judgment: stub the dispatch in the required job. A pull request then runs the Codex install, the capture, `check --check` and `gate record` without credentials, with a fake `codex` on `PATH` that returns a fixed verdict. A run against a real model, if wanted, is a separate optional job through the GitHub Action with the key scoped to it. The issue's acceptance criterion that the gate runs "on the planned model" is then met by hand, not in CI.
