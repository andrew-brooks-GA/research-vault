# Research persistence and recovery
<!-- evidence: 2026-11-17-capture-operation-lines-research-vault-issue 2026-11-17-probe-capture-verify-capture-operation-gate -->

The opt-in capture protocol separates validation-before-write from crash recovery. It is not an all-or-nothing transaction or a power-loss durability guarantee. Research verification, lint and the claims gate remain separate from successful persistence.

## Immutable operations
<!-- evidence: 2026-11-17-capture-operation-lines-research-vault-issue 2026-11-17-probe-capture-verify-capture-operation-gate -->

Create and retain one opaque operation key before the first attempt. Save the JSON-array plan and its referenced inputs; use a new key for a changed plan. Invoke capture with explicit absolute CLI, plan and vault paths and `--operation-id <key>`. Prefer argument arrays to shell interpolation. A relative `contentFile` resolves against the plan directory.

The v1 receipt stores the canonical vault identity, input and schema digests, frozen date, phase, manifest state, ordered input results and errors, without copies of source bodies. Object-key order does not affect the digest; array order and referenced file bytes do. A prepared receipt precedes artifact publication. Each destination is published exclusively; the code reports a differing collision as `DESTINATION_CONFLICT`, and a test asserts it. Source URL/version reuse returns the actual existing ID. A test shows a dependent reference to an uncreated alias failing validation; replan with the returned ID under a new key.

## Replay and repair
<!-- evidence: 2026-11-17-capture-operation-lines-research-vault-issue 2026-11-17-probe-capture-verify-capture-operation-gate 2026-11-17-trial-issue-72-items-1-6 2026-11-17-working-tree-lines-issue-72-item 2026-11-17-plan-reader-lines-issue-72-item -->

For an incomplete operation, run the original capture command again. In `bin/lib/capture-operation.mjs`, and in the tests of `test/capture-operation.test.mjs`, matching files published before their receipt update are reconciled against the prepared destination and fingerprint. The same code and tests show that a missing pending file can be published, that changed files or missing previously completed files require repair and are not overwritten or recreated automatically, and that a manifest failure retains created outcomes and replay can retry finalization without rewriting artifacts. An entry the operation reused and did not write is checked by other rules: a reused source must still be an active source at the planned URL and version, with the content hash and stored body the plan gives, so a verification row added to it since, which leaves its status, URL, version and content hash as they were, does not stop the replay (a test adds an `existence-check` row); any other reused entry must keep its bytes.

By the same code and tests, if initial receipt persistence fails, `recoveryStateCreated=false` and no artifact is published, and a later receipt replacement failure retains the previous readable receipt and stops publication. Inspect the structured report and disk before recovery. Errors carry an input index (`-1` when no single entry is at fault) or a phase name; `bin/lib/capture-operation.mjs` tags them with `receipt`, `prepared`, `lock`, `writing`, `reconciliation`, `manifest` or `finalization`. Validation reports one error for each entry that fails on its own; an entry that names a failed entry is reported as an unresolved reference, and nothing is written when any entry fails. A plan entry that is not an object, or whose `contentFile` cannot be read, gives one error, one for each such entry; when any entry cannot be read, the other entries are not validated. The code classifies three temporary I/O errors as retryable (`EINTR`, `EBUSY`, `EAGAIN`; a test confirms `EAGAIN`); permission denial, disk exhaustion and lock uncertainty require intervention.

A complete receipt is historical. Identical CLI replay returns `replay=true, historical=true` without writing artifacts or revalidating their current bytes. Supplied operation inputs must still match: a changed plan does not return historical success, and in a test neither does a missing input. Legitimate later authoring edits belong to the existing artifact. Current completion requires a separate disk/reference/manifest check.

## Writer lock
<!-- evidence: 2026-11-17-capture-operation-lines-research-vault-issue 2026-11-17-probe-capture-verify-capture-operation-gate -->

Opt-in writers use the vault's `.capture-operations/writer.lock` directory with an `owner.json` diagnostic naming the operation and process. A competing writer fails rather than stealing it. The code removes the lock directory of a writer that cannot write `owner.json` and reports `RECEIPT_IO` with phase `lock`, and a test asserts it. Interruption may leave the lock behind: inspect the diagnostic and confirm the original process is gone before explicitly removing that lock directory, then replay the original command. Never reclaim a lock just because it is old. Legacy and external writers outside this protocol are not coordinated by this lock.

## Research task recovery
<!-- evidence: 2026-11-17-capture-operation-lines-research-vault-issue 2026-11-17-quote-verify-gate-lines-research-vault 2026-11-17-skill-lines-research-vault-issue-77 2026-11-17-probe-capture-verify-capture-operation-gate 2026-11-17-network-egress-lines-research-vault-issue -->

The `research-orchestrate` skill is the reference flow. The session that runs it is the controller: its Recon and Research workers search, fetch and read without writing an entry, and inside the Workflow script only the Write step writes, one command at a time. After the script, the session's close-out writes too: `verify --answered-by` closes a question, and the gate's `capture --fill` stores page text. The CLI has no command that runs a research task; the skill drives it, and the recovery below is what the skill instructs, not a mechanism that enforces itself.

Sources are captured one `capture --type source` call each, outside the opt-in protocol and its lock. A repeated URL with the same subject version is refused with the existing id (`existing entry with same url`), so capturing the same sources again with the same URL and subject version creates nothing new. The same URL with another subject version, or with none where one was recorded, is captured as a new entry when its title gives an id that is free. A different page whose title gives a taken id is also refused with a message that begins `duplicate of`; that id belongs to the other page and must not be reused.

The authored plan is saved under `.research-tasks/<run key>/` in the vault and captured with `--operation-id <run key>-plan-<n>`. Keep that directory until explicit user cleanup; it and the capture receipts are outside artifact discovery by `walkEntries`. The skill's retry rule follows the report, read in this order. `LOCK_BUSY` stops the step, since the report of a blocked replay can carry `recoveryStateCreated` true as well. `RECEIPT_IO` and `INPUT_CHANGED` stop it too. Otherwise, when `recoveryStateCreated` is true, entries may be written, so the same command is run again unchanged; when it is false, that call wrote nothing, so the plan is corrected and captured as the next file under the next operation id. A plan file is never written over.

Each claim a Research worker returns carries one sentence quoted from its page, and the Write step checks the quotes of each source with `verify --id <source> --quotes <file>` and `--by-id`, so a row is an agent's. A quote found on one line of the source's text, or over adjacent lines with no blank line between them, adds one `quote-matched` row whose note begins with an eight-hex-digit hash of the quote; `bin/lib/quotes.mjs` adds no row for a quote whose hash is already on the source, so a resumed run does not add a second one. The row records that the words are on the page and no more: the Write agent judges each claim against the lines around its quote, and in the probe made `lint` kept `WARN_SOURCE_UNVERIFIED` on a source whose rows were `captured` and one `quote-matched` row for a quote found in its stored body; the code counts a `quote-matched` row as it counts `captured` (`bin/lib/manifest.mjs` line 19). A row for a quote found in the stored body is `inconclusive` and does not reset the entry's freshness. Closing a question with `verify --id <question> --answered-by <synthesis>` can be repeated: a second run on the same day leaves the question file unchanged. Closing it again by another synthesis adds that synthesis to `contributing` and, in the run made, replaced the answer summary with that synthesis's summary.

The controller's completion checks come after persistence, in the session: confirm the returned ids on disk, run lint, run the claims gate on the synthesis, and close only the questions a gated synthesis resolves. `bin/lib/gate.mjs` (line 293) adds the sources each listed note names to the entries it lists, and the gate's skill asks the user before it fetches and stores page text for a source that holds none (`capture --fill`); the skill tells a Workflow agent not to ask and to take the answer as no. The orchestrate skill asks the user once, before the run, whether the run may store page text, and its Write step runs `capture --fill` only when the answer was yes. Stored text makes a statement about a page checkable against the page; it does not make a draft pass. Keep evidence status, persistence, lint disposition, claims verdict and question closure distinct; show recovery details when work remains incomplete. None of this guards against another writer editing the same entries.

## Validation limits
<!-- evidence: 2026-11-17-capture-operation-lines-research-vault-issue 2026-11-17-skill-lines-research-vault-issue-77 2026-11-17-probe-capture-verify-capture-operation-gate -->

Deterministic tests exercise the opt-in capture protocol on isolated vaults, including interrupted publication, failed storage, competing writers and a lock whose owner file cannot be written. One test checks the skill's reference script: among other things, that it begins with the `export const meta` literal, that it parses, that no `agent` call opens with an object literal, and that every bare call outside its prompts is to a Workflow hook, a keyword, a name it defines or one of the built-ins `Map`, `Set`, `String`, `Number` and `Boolean`. They do not establish model adherence or universal reliability; a second test runs the skill's script with stub hooks, and neither test in `test/skills.test.mjs` runs it against real agents or the Workflow tool. No routing or performance improvement is claimed.
