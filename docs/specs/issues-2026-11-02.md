## Issue 10. Bulk ingest: capture a list of URLs / markdown in one pass

Original ask, in summary: `capture --batch <file>` (or `import`) over a URL list or markdown directory, with per-item dedup reusing capture's own, a summary report of what was captured, skipped as a duplicate and failed with reasons, and continue-on-error so one bad URL does not abort the run; network rate-limiting and the SSRF guard per fetch (2026-11-02-lines-behind-2026-11-02-rescoping).

What exists now. `capture --batch <plan.json>` is listed under `## [0.3.0] - 2026-07-07` in the CHANGELOG (2026-11-02-lines-behind-2026-11-02-rescoping). `runBatch` in `bin/commands/capture.mjs` reads a JSON array of entry specs, prepares every spec against the manifest and the specs before it, and collects three lists: `errors`, `skipped` for a duplicate, and `pending`. Any failure in that pass is an error: an ambiguous duplicate, an unresolved `sources`, `contributing_ids` or `related` reference, or an exception thrown while preparing the spec. If any error was collected, nothing is written. Otherwise the pending entries are written in order, a write failure stops the loop and is returned with the entries created so far, and the manifest is rebuilt once when anything was created. The result is `{ errors, created, skipped }` (2026-11-02-lines-behind-2026-11-02-rescoping). The research-capture skill describes this as validate-then-write (2026-11-02-lines-behind-2026-11-02-rescoping, skill line 26). `capture.mjs` does not fetch: a grep for `fetch` or `http` in it matches nothing, and its imports name neither `fetchsource.mjs` nor `ssrfguard.mjs` (2026-11-02-lines-behind-2026-11-02-rescoping). A source's content comes in through the CLI's `--content` or `--content-file` option, and `--content-hash` supplies a hash (2026-11-02-lines-behind-2026-11-02-rescoping, `capture.mjs` lines 203 and 210). The only outbound feature is `refresh`: `SECURITY.md` calls itself the exhaustive contract and says `refresh` is the only feature that opens an outbound connection, that it refuses unless `RESEARCH_VAULT_ALLOW_NETWORK=1` is set as well, that it is hash-only and never stores the fetched bytes, that it is HTTPS only, and that a body-size cap and a timeout bound each request (2026-11-02-lines-behind-2026-11-02-rescoping, `SECURITY.md` line 3 and lines 33 to 43). `fetchSource`, which `refresh` imports from `fetchsource.mjs`, has a response handler that resolves `{ status, hash }` with no body; it sends the `User-Agent` `research-vault-refresh` and caps the body at `MAX_BODY` with a `TIMEOUT_MS` of 15000; `refresh` calls it in a plain sequential loop, and a grep of both files for `setTimeout`, `sleep`, `delay` or `throttl` matches nothing (2026-11-02-lines-behind-2026-11-02-rescoping, `fetchsource.mjs` lines 6, 7, 50 to 67 and 76, `refresh.mjs` lines 1 to 4 and 35 to 52).

So the batch path, the dedup and the summary report exist. What remains is the input side, the failure policy and the fetch:

- A URL-list input that turns each line into a source spec with fetched content. This is `capture`'s first fetch, so `SECURITY.md` gains a second outbound feature and loses its "only feature" sentence; the `RESEARCH_VAULT_ALLOW_NETWORK=1` gate, the SSRF guard, the HTTPS-only rule, the body cap and the timeout apply as they do to `refresh`; `fetchSource` has to return the body, which today it only hashes; and `--store-body` inside the plan keeps needing the CLI-level `--ack-data-egress` (2026-11-02-lines-behind-2026-11-02-rescoping, skill line 26). No rate limit exists in either file today; one is new work if wanted.
- A markdown-directory input with a stated convention for where the source URL and author come from. Frontmatter first, the first link as the fallback, is the proposal; it is undecided.
- A continue-on-error mode. Today any error in the validation pass means nothing is written, which is right for a capture plan whose later entries reference earlier ones and wrong for a reading list where each item stands alone. The flag applies only to specs with no references to other specs in the plan.

Thin metadata at ingest is accepted; topics and subject can be filled by a later pass. Done when a URL list and a markdown directory each capture in one invocation, the JSON result names what was created, skipped and failed with the reason per failure, and a plan with one bad URL under the continue flag still creates the rest.

## Issue 12. Question to answer lifecycle: link syntheses to questions, surface long-open ones

Original ask, in summary: when a `synthesis` addressing a `question` is created, prompt to link them and flip the question's `state` to answered; surface long-open questions in `advise`, with "3 questions open >60 days" as the example; optionally suggest candidate answering syntheses by shared subject and topics (2026-11-02-lines-behind-2026-11-02-rescoping).

What exists now. `capture --answer-summary` writes the question's `answer_summary` field and the `WARN_ANSWERED_NO_SUMMARY` lint warning flags an answered question with no `answer_summary`; both are listed under `## [0.3.0] - 2026-07-07` (2026-11-02-lines-behind-2026-11-02-rescoping). The batch key is `answerSummary`: `specToOpts` spreads the spec as given and the question branch of `prepareEntry` reads `opts.answerSummary`, which is the key the research-capture skill names at line 23; the CHANGELOG line writes it as `answer-summary`, which the question branch does not read (2026-11-02-lines-behind-2026-11-02-rescoping, `capture.mjs` lines 96 to 100 and 125 to 136). The lint rule is marked advisory in its comment, its message says the entry exports nothing and names the flag, and `lint`'s `run` returns 1 only when violations exist, a return the CLI sets as the process exit code; warnings are printed on their own lines and do not count (2026-11-02-lines-behind-2026-11-02-rescoping, `lintrules.mjs` lines 158 to 161, `lint.mjs` lines 9 to 41, `research-vault.mjs` lines 30 to 33). The CLI passes `state` and `answerSummary` through with the other capture options (2026-11-02-lines-behind-2026-11-02-rescoping, `capture.mjs` line 217). `advise` returns nine keys, `stale`, `staleEvidence`, `orphans`, `sourcesWithoutNotes`, `unverifiedSources`, `missingSummaries`, `stubBodies`, `aliasable` and `quoteResidue`; the word `question` does not occur in `bin/lib/advise.mjs` (2026-11-02-lines-behind-2026-11-02-rescoping). The link already exists in one direction: a synthesis carries a `question` field and its `contributing_ids` may name a question, and the frontmatter schema gives a question a `contributing` field, which nothing in `capture.mjs` writes, since the only `contributing` strings in the file belong to the synthesis `contributing_ids` (2026-11-02-lines-behind-2026-11-02-rescoping, `frontmatter.schema.json` lines 7, 10 and 25, the `contributing` grep of `capture.mjs`). `capture` only creates entries: an id that already exists comes back as a `skipped` duplicate with the reason "supersede via verify, do not overwrite", so a batch cannot change an existing question (2026-11-02-lines-behind-2026-11-02-rescoping, `capture.mjs` lines 56 and 57).

So an answered question can carry its answer, lint catches one that does not, and a synthesis can point at its question. What remains is the other direction and the nudge:

- An `advise` key for open questions with their age, so a question left open for longer than a stated number of days is listed with the rest of the curation signals. The threshold is a constant to start, 60 days as the issue proposed. Manifest rows carry `state` but no creation date, and `created` does not occur in `manifest.mjs` (2026-11-02-lines-behind-2026-11-02-rescoping, `manifest.mjs` lines 28 to 46 and its `created` grep), so the age comes from the id's date prefix.
- A way to close an existing question: a `verify`-style command, or a flag on it, that sets `state` to answered, writes `answer_summary` and appends the synthesis id to `contributing`. This is new code; `capture` cannot do it. The research-capture and research-orchestrate skills then say to run it in the step that captures the synthesis, with the synthesis's `contributingIds` naming the question.
- Candidate matching by shared subject and topics stays optional and advisory; it is not in scope until the first two are in.

Done when `advise` lists open questions with their age, a question can be closed by one command that records its answer and the synthesis that gave it, and the two skills name that command in the synthesis step.

## Issue 13. Topic / taxonomy normalizer: apply alias merges across entries

Original ask, in summary: propose canonical topics and aliases building on `advise` detection; on confirmation, rewrite `topics` across all matching entries to canonical form; optionally maintain an alias map in `schema/taxonomy.json` so future `capture` normalizes on ingest (2026-11-02-lines-behind-2026-11-02-rescoping).

What exists now. The alias map is in the plugin's `schema/taxonomy.json` and holds two entries, `tdd` to `test-driven-development` and `ci` to `continuous-integration` (2026-11-02-lines-behind-2026-11-02-rescoping). A git grep for `topic_aliases` at 568d61b finds five consumers in `bin/`, `schema/` and `skills/` (2026-11-02-lines-behind-2026-11-02-rescoping): `capture` maps each `--topics` value through the map as it builds the entry, so a captured entry lands with canonical topics (`capture.mjs` line 62); `lint` warns `WARN_TOPIC_ALIAS` on any topic in the map, naming the canonical value (`lintrules.mjs` line 167); `advise` lists under `aliasable` every entry with a topic in the map (`advise.mjs` line 97); `matchRows` in `search.mjs` maps the query topic and each entry's topics through the map before comparing, `search --topic` goes through it (`search.mjs` lines 12 to 17 and 39 to 45), and `teach path candidates` passes the same map to the same function (`teach.mjs` line 113, `lesson.mjs` line 600). The ingest half of the original ask is therefore done. Nothing maps an existing entry's topics through `topic_aliases`: `fixVault`, behind `lint --fix`, strips a BOM and CR bytes, unwraps quote artifacts in every string slot, array items such as `topics[i]` included, and reserialises the frontmatter in schema order; it never consults `topic_aliases` (2026-11-02-lines-behind-2026-11-02-rescoping, `lintrules.mjs` lines 46 to 61 and 193 to 213). The map is not per vault: `loadSchema` reads the plugin's `schema/taxonomy.json` and merges a vault's `taxonomy_extensions` only when called with `vaultPath`, and `projectconfig.mjs` excludes map-valued taxonomy, `topic_aliases` named, from what a vault may extend (2026-11-02-lines-behind-2026-11-02-rescoping, `schema.mjs` lines 20 to 31, `projectconfig.mjs` lines 10 to 13). The vault's own `taxonomy.json` is not a place for it either: `init` copies the plugin file over it, on a first `init` and again on `init --refresh-docs`, and the generated vault `AGENTS.md` calls it a verbatim copy of the plugin's schema (2026-11-02-lines-behind-2026-11-02-rescoping, `init.mjs` lines 39 and 54, `agentsmd.mjs` line 116). Two of the five consumers would not see a per-vault pair even if one existed: `advise` and `search` call `loadSchema(repoRoot)` without `vaultPath`; `lint`, `fixVault`, `capture`'s `prepareEntry` and `teach path candidates` pass it (2026-11-02-lines-behind-2026-11-02-rescoping, `advise.mjs` line 83, `search.mjs` line 23, `lintrules.mjs` lines 65 and 194, `capture.mjs` line 23, `teach.mjs` line 102, `schema.mjs` lines 20 to 31).

So ingest normalisation, detection and read-time expansion are done. What remains:

- A per-vault alias map, since a vault's drift (`k8s` against `kubernetes`) is the vault's, not the plugin's. `taxonomy_extensions` learns a `topic_aliases` key that adds pairs and may not redefine a built-in, under the existing additive rule; the vault copy of `taxonomy.json` is out, because `init --refresh-docs` overwrites it.
- `advise` and `search` load the schema with `vaultPath`, so a vault-declared pair reaches every consumer.
- The apply step: `lint --fix` rewrites each aliased topic to its canonical value, deduplicating the list when the canonical value is already present. `lint --fix` today writes with no confirmation or dry run (2026-11-02-lines-behind-2026-11-02-rescoping, `lint.mjs` lines 27 to 31), and a topic rewrite changes meaning where the quote unwrap only changes form, so the rewrite sits behind a flag of its own, `lint --fix --topics`, which stands in for the issue's "on confirmation".
- A proposal step is deferred. `advise` names the entries today; naming new candidate pairs from title and topic similarity is fuzzy and waits for a vault that shows the need.

Done when a vault can declare an alias pair in `.research-vault.json`, `advise` lists an entry carrying the alias under `aliasable` before the fix, `lint --fix --topics` rewrites every such entry, and `aliasable` is empty afterwards.
