# Spec 20: path discovery, `teach path candidates` proposes lines from what the vault already holds

Round 1 (2026-11-01), on master at 5ac1646 (the repo lines this spec names are quoted in snippet 2026-11-01-spec-20-lines-at-research-vault; today's behaviour against the live vault and the vcluster teach workspace is recorded in experiment 2026-11-01-probe-what-teach-next-research-teach). Today a `PATH.md` is written from the mission interview alone: the research-teach skill's §2 interviews the learner, writes `PATH.md` and reads it back, and names no vault command; the vault is first searched in §3, whose step 0 captures the concept sources once per path and whose step 1 says "Search the vault before the web", both after the path exists and both run by hand, per lesson (snippet 2026-11-01-spec-20-lines-at-research-vault). `next` in `bin/commands/teach.mjs` calls `teachIndex(ws, { now })` and `pathLines(ws)` and resolves no vault path, so no teach command consults the vault, and the skill asks for no search when the path is written. On the vcluster mission the vault held 32 non-superseded entries on topic `vcluster`, lessons 0001 and 0002 cite 5 of them, and the 27 others include the six 2026-11-01 CLI sources on line 3's subject and the Standalone, private-node and Platform sources lines 6, 7 and 9 will need (experiment 2026-11-01-probe-what-teach-next-research-teach, P3, P6, P7). This spec adds one read-only verb that runs the vault's own search and traversal over the mission's terms and prints candidate lines with their evidence, for the path author to accept or reject. This spec is the executable list for the implementation; nothing here is implemented at 5ac1646.

## Decisions this spec designs within

Taken in evaluation 16 and spec 17 and not reopened here: no LLM extraction of concepts from the vault's prose, no community detection or hub analytics, no fuzzy dedup, and no concept graph over the vault's prose (evaluation 16 §5 "Not adopted" and §4.3 "What not to build", quoted in 2026-11-01-spec-20-lines-at-research-vault); the `PATH.md` line graph stays authored by the path author (evaluation 16 §4.3 item 2, quoted); machine proposals are proposed, never written, following the expert-acceptance pattern the educational-graph note reports (2026-11-01-educational-knowledge-graphs-building-prerequisite-relations); `teach next`'s `fringe:` and `inner:` lines and `lesson:` as the state (spec 17 D0 and D1) are unchanged; and the repo's own rule, "ESM only, no dependencies, no classes" (`AGENTS.md`, quoted in 2026-11-01-spec-20-lines-at-research-vault).

Four constraints set for this work and kept throughout, plus one of this spec's own, that candidates are grouped and sorted by rule and never ranked, scored or clustered by similarity: the path author stays the author (candidates are printed, `PATH.md` is never written by the command); the vault is the only source of candidates (no web fetch, no LLM extraction; every candidate is an entry `buildManifest` lists); the proposal is auditable (every candidate line names the entry ids and the `search` or `related` query that produced it, so the author can rerun the query); and nothing changes the manifest contract or adds a manifest key (the command reads `entries`, `edges` and `backlinks` as `related` does; snippet 2026-11-01-spec-20-lines-at-research-vault quotes `buildManifest`'s return).

## Design

### D0. Contracts the implementation keeps

1. **Read-only.** `teach path candidates` writes nothing: not `PATH.md`, not the manifest, not the ledger. The author edits `PATH.md` by hand after reading the output.
2. **The vault is the only source.** Candidates come from `buildManifest(vaultPath)` filtered with the filters `searchVault` applies and walked with `traverse` from `bin/lib/graph.mjs`. No fetch, no model call, no reading of lesson prose (`proseOf` in `bin/lib/lesson.mjs` is a module-level function without `export` at 5ac1646, quoted in the snippet's round 2 additions, and stays so), no new frontmatter field, no manifest key.
3. **Every candidate names its evidence.** A printed candidate carries the entry id, type and title, the reason it qualifies (D3) and the query that produced it in the CLI's own words (`search --topic vcluster`, `search --topic vcluster --text "private-node"`, `search --topic vcluster --body "backing store"`, `related 2026-10-27-vcluster-0-37-4-kind-what --depth 2`), so the author can rerun it. When several lines or terms match, every query that placed the candidate in its group is printed.
4. **Pure core.** `pathCandidates({ lines, floor, cites, manifest, topics, aliases })` in `bin/lib/lesson.mjs` takes `readPath`'s array, `missionFloor`'s two sets, the cited ids, the manifest object, the topic list and the taxonomy's `topic_aliases`, and returns the groups of D3; it reads no file. The command in `bin/commands/teach.mjs` gathers the inputs and formats the lines, as `next` does with `pathLines`.
5. **Nothing else changes.** `teach next`, `teach lint`'s violations and exit codes, `teach progress`, `teach serve`, the session brief, `readPath`'s shape, `searchVault`'s results for every existing flag, `relatedTo`, `traverse` and the manifest are untouched. `searchVault`'s in-memory filters (type, domain, series, topic, text) move into an exported `matchRows(rows, q, aliases)` that `searchVault` calls, so the candidates pass and `search` apply one test; `--body` and the superseded gate stay in `searchVault`.

### D1. The verb: `teach path candidates [--topic a,b] [workspace]`

The usage string becomes `usage: research-vault teach record add|supersede ... | attempt add ... | lint [--fix] [workspace] | next [workspace] | path candidates [--topic a,b] [workspace] | progress [workspace] | serve [workspace]` (today's string is quoted in 2026-11-01-spec-20-lines-at-research-vault, as is the `USAGE` constant of `test/teach.test.mjs` that restates it and changes with it). The workspace rule is the other verbs': the positional path, else the cwd, either holding `MISSION.md`, else usage and exit 2. The vault is resolved from the workspace as `lint` and `serve` do (`resolveVault({ flag: args.vault ?? null, cwd: ws })`, both quoted); a missing vault is `teach path candidates: no vault at <path>` on stderr and exit 2, the shape of `lint`'s message.

The topics are `--topic a,b` (a comma list, `csvList`), else the `defaults.topics` array of the workspace's `.research-vault.json` (`loadProjectConfig(ws)`, whose `findProjectConfig` walks up from the workspace to the nearest `.research-vault.json`; the skill's §0 says to set it to the topic). With neither, stderr says `teach path candidates: no topic (pass --topic a,b or set defaults.topics in .research-vault.json)` and the exit is 2. `--topic` is not a `BOOL` flag: it takes a value, as `search --topic` does.

### D2. The pool and the queries

Let the mission terms be the `Known terms` and `New to me` bullets of `MISSION.md`, lowercased as `missionFloor` returns them, plus every `terms:` value and `tool:` value of `PATH.md`. Let `slug(t)` be `t` lowercased with every run of characters that are not letters or digits replaced by one hyphen and leading or trailing hyphens dropped (`private node` gives `private-node`, `vcluster.yaml` gives `vcluster-yaml`, `vCluster Platform` gives `vcluster-platform`); this is not `slugify` from `bin/lib/ids.mjs`, which filters `STOPWORDS` and takes `words.slice(0, 6)` (quoted in the snippet's round 2 additions).

- **Vocabulary.** The topics in use are every topic on a non-superseded entry, as `manifest --topics` counts them (snippet 2026-11-01-spec-20-lines-at-research-vault quotes the loop), each passed through `topic_aliases` as `searchVault` does.
- **Pool topics.** The given topics, plus `slug(t)` for every mission term `t` whose slug, or whose slug with `s` appended, is a vocabulary topic. On the vcluster mission this adds `standalone`, `vcluster-platform` and `platform-agent` (P3) and, through the plural rule, `private-nodes` (the topic 2026-08-19-vcluster-private-node-architecture carries; P7); `control plane` adds `control-plane` when that topic is in the vocabulary (2026-08-19-vcluster-standalone-architecture carries it; P7). The header line prints every pool topic with its count, so the author sees what widened the pool.
- **Pool.** Every non-superseded entry whose alias-expanded topics include a pool topic (`matchRows` with `{ topic }`, once per pool topic, over one manifest). Entries outside the pool are never candidates, except through D3's third rule.
- **Term hits.** For each mission term `t`, the pool entries that `matchRows` returns for `{ text: t }` or `{ text: slug(t) }` (title, joined topics and summary, lowercased, substring), plus the pool entries whose body contains `t` lowercased (the test `searchVault` applies for `--body`, over pool entries' files only; the query printed is `search --topic <pool topic> --body "<t>"`). Each hit remembers which of the three queries produced it.

### D3. Candidates and the rule for what is printed

Let the cited set be every `data-cite` id in `lessons/*.html` and `reference/*.html`, as `teachIndex` collects them (`lessons[].cites`, `reference[].cites`). Three rules make an entry a candidate; an entry is printed once with every rule and query that applies:

1. **Uncited pool entry.** A pool entry not in the cited set. Reason `uncited`; query `search --topic <t>` for each pool topic that admits it.
2. **Mission term no line covers.** A mission term `t` is covered when some line names it in `terms:`, or `tool:` equals it, or `slug(t)` is a substring of `slug(<line title>)`. An uncovered `New to me` term is always printed, as `term "<t>": no path line covers it` followed by its term hits (each with its query), or `(no entry)` when the pool holds none, so the author sees the gap either way; it is also a lint warning (D5). An uncovered Known term is printed only when the pool holds at least one hit for it: the Floor needs no lesson, so a known term with no entry proposes nothing, while an entry the vault holds on a term no line teaches is still worth the author's look (the vcluster mission's Standalone, private node and Platform are Known terms whose lines 6, 7 and 9 cover them through their titles; the fixture's Known term `function` has no entry and is not printed).
3. **Linked note or synthesis.** `traverse(manifest, c, { depth: 2, direction: 'both' })` from every cited id `c`: a reached node whose entry is a `note` or `synthesis`, not `missing`, not cited. Reason `linked`; query `related <c> --depth 2`. Not restricted to the pool: reachability from a cited entry is the signal. On the vcluster workspace, P5's separate in and out walks from the five cited ids reached no note or synthesis, so this rule is expected to print nothing there; the first `both` walk is step 4's run. It is kept for the reason Problems 4 gives.

**Grouping, by the `PATH.md` line the candidate would follow.** A line's own terms are, in order of strength, its `terms:` values, then every mission term whose slug is a substring of the line title's slug, then its `tool:`; the tool comes last because a tool is often also the product's name and the workspace topic (`vcluster` here), so a `--text "vcluster"` hit through an entry's joined topics is true of every pool entry on that topic and says the least. A candidate matches a line when it is a `--text` hit (title, topics or summary) for one of these terms; `--body` hits are evidence for rule 2 and are printed as queries, but do not place a candidate: a term anywhere in a stored page is the weakest signal the command has, and title, topics and summary are what the capturer chose to say the entry is for. A summary hit does place: the disconnect reference, whose summary says its help text names `vcluster platform connect` (P7), lands on line 9 through `--text "vcluster platform"` under this rule, and the printed query tells the author why. A candidate is printed under the line of its strongest match, and among equals the highest-numbered line, formatted as `pathLines` formats a line (`N. <title> | terms: ... | tool: ... | after: ... | lesson: ...`), so a built line shows its `lesson:` and the author reads the entry as something that lesson did not cite, while an untaken line's group is the evidence the vault already holds for that lesson. Candidates matching no line go under `no line`, which is where a new line would come from. Groups print in line order, `no line` last, then the uncovered terms of rule 2, then `terms with no line: none` when there are none. Within a group, candidates sort by id. The header is `candidates for <workspace> | topics: <topic> <count>, ... | pool <n> | cited <n> (lessons <numbers>)`; with no candidate and no uncovered term the body is one line, `candidates: none`.

```
candidates for /home/u/vcluster | topics: vcluster 32, standalone 7, vcluster-platform 6, platform-agent 3, private-nodes 5, control-plane 2 | pool 46 | cited 5 (lessons 0001, 0002)
3. The vcluster CLI: create one, connect, see both sides without a hand-made tunnel | tool: vcluster | after: 2
  2026-11-01-vcluster-cli-reference-vcluster-connect-v0 [source] vCluster CLI reference: vcluster connect (v0.37) | uncited | search --topic vcluster; search --topic vcluster --text "vcluster"
7. Private nodes: real nodes joined to a virtual control plane | after: 6
  2026-08-19-vcluster-private-node-architecture [source] vCluster private-node architecture | uncited | search --topic vcluster; search --topic private-nodes; search --topic vcluster --text "private-node"
terms with no line: none
```

The connect reference's title and topics match no `terms:` value and no mission term in a title, so its tool match places it on line 3; the private-node source matches line 7's title term `private node` through the slug query (its title is "vCluster private-node architecture", P4 and P7), which outranks its tool match on line 3. With the workspace topic equal to the tool name, every pool entry on that topic that no stronger term places lands on the tool's line, so a `no line` group appears only through a second topic or a rule-3 candidate. The counts in this example are the shape of the output, not a prediction: the pool depends on which slugs are vocabulary topics when the command runs, and the first live run is step 4 of this session's plan, recorded in the workspace's `GATE-LOG.md`.

The §2 and §4 sentences are the two places the author is told to run it; nothing else in the skill changes.

### D5. `teach lint`: `WARN_PATH_TERM_UNPLANNED`

`lintPathTerms(lines, newTerms)` in `bin/lib/lesson.mjs`, pure over `readPath`'s array and `missionFloor(ws).newTerms`, returns one warning per `New to me` term that no line's `terms:` names: `{ code: 'WARN_PATH_TERM_UNPLANNED', file: 'PATH.md', message: 'New to me term "x" is on no line\'s terms: (PATH-FORMAT: every New to me term appears on a line); teach path candidates lists the vault\'s entries for it', warning: true }`. `lintWorkspace` pushes it when `readPath` is not null and `newTerms` is not null, beside `lintPath`. A warning, not a violation: a path is a plan in progress, the term becomes a violation only when a lesson uses it (`LESSON_TERM_NOT_INTRODUCED`), and warnings are advisory in `teach lint` (the skill's §4 step 6 says "Warnings are advisory" and `lint` in `bin/commands/teach.mjs` exits on `violations.length` after printing `warning <code>  <file>: <message>` for each; both quoted in 2026-11-01-spec-20-lines-at-research-vault). Known terms get no finding: the Floor needs no lesson. The fixture path lints clean under it (its `New to me` terms `fx` and `sextuple` are on lines 1 and 4; the fixture `MISSION.md` and `PATH.md` are quoted in 2026-11-01-spec-20-lines-at-research-vault), and so does the vcluster path (all seven `New to me` terms are on lines 2, 4, 5 and 9; P2).

### D6. How this relates to spec 19

Spec 19, the follow-up evaluation 16 §5 item 2 names for its §4.3 items 2 and 3 (quoted in 2026-11-01-spec-20-lines-at-research-vault; deferred by spec 17 D5; numbered 19 in this session's plan), proposes **edges between existing lines**: `after:` candidates derived from the lessons' own terms (which lesson introduces a term, which later lessons use it) and a `near:` offer on a repeated review failure. Its inputs are the workspace (lesson prose, `data-introduces`, attempts); its output is a change to a line that exists. This spec proposes **new lines, or evidence for a line, from the vault**: its inputs are the vault's entries and edges; its output is a candidate the author turns into a line or cites in a plan. The two share `readPath` and `missionFloor` and nothing else, and they answer different questions (2026-11-01-can-prerequisite-edges-between-teach-terms is spec 19's). Evaluation 16 and spec 17 D5 used the name `teach path candidates` for the edge pass; this spec takes that name for the line pass, because its output is candidate lines, and records here that spec 19's verb is `teach path edges` when it is written, so the two never share a verb. Spec 19 still waits for a live fringe mission; step 4 of this session's plan is that mission.

### D7. Not done here

No writing of `PATH.md`, `NOTES.md` or any file. No ranking, scoring, clustering or similarity over titles, summaries or bodies (evaluation 16's rejections stand); groups are by line match and sorted by id. No web fetch and no model call. No `related:` edge proposals between vault entries. No `--json` output until a reader needs it. No reading of lesson prose and no change to `proseOf`. No `--body` match outside the pool: bodies are read for pool entries only, so the command's cost is the manifest plus the pool entries' files (32 on topic `vcluster` alone, P6). No change to `teach next`, to `teach lint`'s violations or exit codes, to the session brief, to `GLOSSARY.md`, to `readPath`, to `pathFringe`, to `lintPath`, to `relatedTo`'s output, to `traverse`, to `buildManifest` or to the manifest file. No plural rule beyond the trailing `s` (`control-planes`, `private-nodes`); a topic the slug does not meet is a `--topic` value or a `topic_aliases` row. No measurement of precision: the first accept-or-reject pass is step 4's run, written into the workspace's `GATE-LOG.md` under lesson 0003's entry.
