## Design

### D1. The interview options

Line 41's "Why" options gain one example that is not software work: "a ticket, a design, a talk, a decision at work, or the model for its own sake". Line 43's depth options become "explain it with a diagram, apply it to a case (read an output or a document and say what it means), or do it unaided (configure or produce it from scratch)"; the three are the same three depths, each with the software reading in the parenthesis, so a `diagnose` lesson (LESSON-FORMAT.md line 49) still sits behind the middle one. Line 46's preference options become `diagram first`, `example first`, `try and predict`, `read`: `YAML first` was the one option naming a file format. Judgment: the options change wording, not the number or order of questions, so section 2's dialog procedure is untouched.

### D2. A step without a command

LESSON-FORMAT.md line 31 becomes "One real-world action and its observable result, with the command to run when the action is one; a step with no command states its expected result, and what a mismatch means, in prose, never in a `<pre>`". The mismatch clause is judgment: a prose step that names only success leaves the learner with nothing to do when the result differs. Line 97 gains the reason, as a second sentence: "so a step with no command keeps its expected result out of `<pre>`, or its first words are read as tools" (lines 280 to 296 are why). The lint does not change: read from the code's shape, `preLines` over a step with no `<pre>` yields nothing for `commandTools` to keep, and, in a lesson whose `example` runs no command either (a `project` lesson has no example block, line 50), the guard at line 438 skips the tool findings; D5's test asserts it. Line 39's rule, "In `step`, state the command exactly as the experiment's Result quotes it", is untouched: it applies when there is a command.

### D3. The project check

Line 50's last column becomes "the task itself; `step` is the check that proves the goal, a command and its expected output or the answer or artefact the learner shows, and the learner's run is the attempt". Line 61 becomes "`step` is the check that proves the goal: a command and its output, stated exactly as the reference run's Result quotes it, or the answer or artefact the learner shows, stated in prose; `sources` links the reference solution's snippet, when there is one, instead of printing it". The project row's "the learner's run is the attempt" keeps its words, and the skill's attempt command is not touched by this spec.

### D4. The Floor's example and the reader persona

MISSION-FORMAT.md line 22 becomes "One tool per bullet the learner runs daily, e.g. kubectl or a spreadsheet. Lessons may run only these and the tools earlier lessons taught". agents/lesson-reader.md line 12 drops "a working engineer": "Read the page as the person it is for, learning this topic for the first time, who knows the tools and terms the page itself says they know and nothing else." Lines 20 and 22 keep "any command", since a page with no command names none. No other line of the agent changes, and no ledger state depends on that file (the claims ledger's `reviewer` hash is of `agents/claims-reviewer.md`, docs/REFERENCE.md line 44).

### D5. The one check

A test in `test/lesson.test.mjs`, on a copy of the fixture workspace: `lessons/0006-project-fx.html` with its step's `<pre>` removed and the `<p>` replaced by "Write your prediction for fx(5) beside the number fx printed; the check passes when both are 30." is asserted by the test to lint with no finding. It pins D2's reading of the guard. Issue B's Done-when (2), quoted in the snippet, also asks that such a page pass the reader; the reader run on that edited copy and its verdict are recorded in the gate log, not here, since the fixture is a lint fixture and a live project lesson with a non-command check is the page that can pass the reader.

### D6. Not done here

The reading page's step sentence ("the command to run and what you should see", reading.html line 49) is issue #53 with the other label and reading-page wording, per the quoted CHANGELOG line. No lint rule for prose in a step: D2 makes it a format rule, since the lint cannot tell a sentence from a command once it is in a `<pre>`.
