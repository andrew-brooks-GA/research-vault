# Evaluation 16: graphify, and what a graph can do for research-vault

Written 2026-11-01 on `worktree-graphify-eval` from master at aa188e6 (0.8.0). This is a research and planning document, not a spec: it names the concepts in Graphify-Labs/graphify worth re-deriving for this plugin, judges each against three uses (the plugin's code and the projects that join it, the vault as a body of knowledge, and the teach workflow), and reports what the education literature says a graph can do for a learner. Nothing here is implemented. Every external claim is a vault entry; the synthesis is 2026-11-01-graph-helps-learner-by-exposing-ready and its evidence chain is listed at the end. The rule of this evaluation, set by the user: take the concept, not the code or the feature.

## 1. What graphify is, in the terms that matter here

graphify (0.9.100, 243 releases since April 2026, about 92k lines of Python, 27 tree-sitter packages) turns a folder of code, Markdown, PDFs and media into one NetworkX graph that an agent is told to query before it greps or reads. Code is parsed by tree-sitter at no cost; prose, papers and images go through LLM subagents in chunks; every edge carries a confidence tier (EXTRACTED, INFERRED, AMBIGUOUS) and a discrete score; Leiden communities, degree-ranked "god nodes", "surprising connections" and "suggested questions" are written into a GRAPH_REPORT; outputs include an HTML viewer, a wiki, an Obsidian export, Cypher for graph databases and an MCP server; PreToolUse hooks nudge the agent toward the graph; a `save-result` and `reflect` loop turns query outcomes into a LESSONS file (2026-11-01-graphify-labs-graphify-repository-at-0, 2026-11-01-graphify-s-transferable-concepts-research-vault).

Two facts frame everything below. First, graphify's edges are inferred from text, so most of its machinery (id normalisation across three producers, 1.8k lines of dedup with a growing list of false-merge guards, coverage self-reports from subagents, shrink guards) exists to keep inferred structure from drifting. The vault's edges are authored in frontmatter and lint-checked, so that problem does not exist here; the October synthesis reached the same conclusion for the previous generation of tools (2026-10-12-graph-representations-research-vault-expose-existing). Second, graphify's own worked reviews are the most honest evidence about its analytics: on a real three-service project six of the top-ten god nodes were test factories, 141 communities with cohesion 0.05 to 0.17 failed to recover the architecture, 752 isolates were mislabelled as documentation gaps and the suggested questions were graph-property meta-questions; httpx scored 5.7 out of 10 with fourteen inheritance edges silently dropped; the headline benchmarks are conversational-memory sets run on an external harness with an embedder, and the only code result has six questions (2026-11-01-graphify-s-transferable-concepts-research-vault).

## 2. Lens one: the plugin's code and the projects that join it

What exists today: code links (spec 15) attach a vault id in a comment to the column-0 declaration below it, hash that unit, pin it to a declared dependency version, and report per-symbol rows through `check --json`; the manifest and `check --json` are the integration contract pinned by `test/contract.test.mjs`; a project keeps its own code graph and joins on `id`; code-to-code edges are out of scope by decision.

| graphify concept | Problem it solves | Verdict for research-vault |
|---|---|---|
| Confidence tier on every edge, path confidence as the weakest hop, `also_seen` provenance on collapsed duplicates | A reader cannot tell a stated link from a guessed one | Adopt the rule, not the field. Authored links are EXTRACTED by construction and need no tier. The tier belongs only on machine-proposed links if a suggestion feature ever ships (see lens two), and `related` should report a multi-hop path's weakest link when it reports paths. |
| Resolver prefers no edge over a wrong one; a prose mention resolves only on a unique, qualified match | Name collisions produce false links | Already the plugin's stance for code links (column-0 only, unattached rows reported, no guessing). Keep it. The same rule bounds any future "which entry does this comment mean" helper: unique match or nothing. |
| Blast radius: reverse BFS over an allow-listed relation set, reporting the site where the dependency is made | "If this changes, what breaks" | The plugin already has the data: `check --json` rows join a symbol to an entry, and `related --direction in --rel sources,contributing_ids` gives the evidence chain. The missing operation is the composed one, "this source is superseded, which code symbols in which repos cite anything downstream of it". Spec 15 cut `--cited-by`; the right shape is an example script on the contract (like `examples/graph-dot.mjs`), not a new command, because the walk crosses the contract boundary into the project's own graph. |
| Edge-only joins across separately built graphs (`same_type_as`, repo-prefixed ids, never merging nodes) | Linking two repos without collapsing drifted copies | This is the graph-contract decision restated from the other side. No change. It confirms that a project with two repos citing one vault should join both `check --json` outputs on `id` rather than ask the plugin for a cross-repo index. |
| Stale-aware nudge hooks: PreToolUse context, softened wording when the index is older than the file, optional once-per-session deny that then downgrades, fail-open, 10 s timeout | Agents ignore the index | The plugin's hooks already inject context on edit and never block except the Stop gate. The transferable lesson is negative: graphify's changelog admits the model "routinely walks past" the soft nudge, and the deny had to be once-only. Do not add a PreToolUse read-guard. |
| Shrink guard and health gate before writing a derived index | A bad incremental run destroys the index silently | Cheap and worth taking for the manifest, `_index/` and `_obsidian/`: refuse to write a manifest with fewer entries than the last one unless the entry files are actually gone, and report dangling edges before writing. The manifest is rebuilt on every edit by the post-tool hook, so a bad rebuild would otherwise propagate instantly. |
| Build-commit freshness stamped into the output and the report | Knowing how old the index is | The manifest has `generated`; `check --json` has `generated`. Enough. |
| Prompt-hash-keyed cache and coverage self-report for LLM-derived artifacts | Partial LLM reads passed off as complete | Applies to the claims ledger: a verdict is keyed to the draft's content hash but not to the reviewer prompt. Add the agent definition's hash to the ledger row so a changed reviewer invalidates old verdicts. Small, in the spirit of the existing design. |
| Tree-sitter extraction of call, import and inheritance edges | A code graph | Out of scope by decision (2026-10-27). The Zig evidence stands: Graphify's own tree-sitter graph may or may not resolve comptime chains (2026-10-16-does-tree-sitter-zig-graph-resolve), and structure wins over grep only on relationship questions and mostly on cost (2026-10-16-accurate-zig-tutoring-keep-grep-over). A project that wants this runs graphify itself and joins on `id`. |

## 3. Lens two: the vault as a body of knowledge

What exists today: six entry types, seven typed link fields, a manifest with typed `edges` and `backlinks`, a bounded typed walk (`related`), `advise` with stale-evidence chains, orphans and sources without notes, a derived Obsidian view, substring search with no ranking.

| graphify concept | Problem it solves | Verdict for research-vault |
|---|---|---|
| Degree god nodes, Leiden communities with cohesion, surprising connections, suggested questions | Finding the core, the clusters, the bridges and the gaps | Do not adopt. The vault is ~760 entries at average degree ~1.3; the October note shows graph retrieval beats flat retrieval only on multi-hop questions past a corpus size the vault is far below (2026-10-12-graph-retrieval-beats-flat-only-multi), and graphify's reviews show degree and community analytics surface scaffolding on real corpora. The vault's declared `topics`, `domain` and `series` are the community structure, authored. The one cheap `advise` addition worth having is a degree listing by type with syntheses and index-like notes excluded, as a curation prompt for an over-cited source, with no claim that it is "core". |
| Work memory: query outcome files with frontmatter (`outcome: useful | dead_end | corrected`, `source_nodes`), deterministically scored with a 30-day half-life, "preferred" only after two distinct useful results, "contested" kept visible, kept in a sidecar and never steering traversal | Agents re-derive dead ends and forget which sources answered well | Adopt the concept in the vault's own terms. The vault already records outcomes as `question` entries (answered, with `answer_summary` and `contributing`) and as `verifications`. What it lacks is "this entry answered a question well" as a signal. The lightest form: a `--cited-in-answer` note on `verify` (a new `verification_method` value, `used-in-answer`), and an `advise` section listing entries never used in any answered question. No decay, no scoring, no steering of `search`; graphify itself refuses to let verdicts steer retrieval because of the feedback loop. |
| Constrained query expansion: dump the label vocabulary, let the model pick up to twelve terms only from it, print the expansion, stop when nothing matches | Synonym mismatch against a literal matcher | The vault's `search` is literal and unranked, so the gap is real, but the fix lives in the skill, not the CLI: `research-vault-usage` should tell the agent to read the topic vocabulary (a `manifest --topics` listing is a one-line addition) and choose search terms from it. Auditability comes free because the agent prints its search commands. |
| Token-budgeted BFS and DFS subgraph retrieval | Context bloat | `related --depth` is already bounded and returns rows, not bodies. On a corpus this size graphify's own numbers say the saving is about 1x. No change. |
| Page and heading structural nodes, `contains` and `references` edges from Markdown links and wikilinks, frontmatter parsed onto the page node | Section-level navigation without an LLM | The vault's unit is the entry, not the heading, and bodies are prose by design. Wikilinks or ids written inside bodies are not edges today (edges come from frontmatter only). That is a deliberate boundary and should stay: an id in prose is a citation to check, not an edge to traverse. No change. |
| Dedup via MinHash, Jaro-Winkler and community bonus, with an LLM tiebreak | Near-duplicate nodes | Do not adopt. Titles that differ by a word are usually distinct claims in a research vault, and `capture` already dedupes on URL and version, which is the honest key. |
| LLM extraction of concepts, `cites` and `semantically_similar_to` edges from documents, wrapped in untrusted-source guards | A semantic graph over prose | Do not adopt. The literature's dominant graph failure is incomplete LLM-extracted edges (2026-10-12-graph-retrieval-beats-flat-only-multi); the vault's value is that its edges are declared. A link suggestion that proposes `related` candidates and waits for the author is the most that fits, and it would carry the confidence tier from lens one. |
| Wiki export: index, one article per community, one per hub, each with an audit-trail section, regenerated destructively | A browsable summary layer | `_index/` and `_obsidian/` already play this role and are already derived and git-ignored. The MOC could gain a per-topic page listing entries and their one-line summaries, which is what graphify's community article is once communities are replaced by declared topics. Low priority. |
| Ambiguous edges damped in clustering and kept in a review queue | Uncertain links should neither distort structure nor be discarded | Maps onto `question` entries and `related`, which is how the vault already parks a conflict. No change. |

## 4. Lens three: the teach workflow, and what a graph does for a learner

### 4.1 What the education literature says

The research for this lens was run vault-first (nothing on graphs in education existed) and captured as nine sources, four notes, three questions and one synthesis. The findings, in order of weight:

- **The fringe is the operation.** Knowledge space theory models a learner as a state (the set of items mastered) in a family of feasible states; in a learning space a state is determined by its inner fringe (items whose removal leaves a state: what was just learned) and its outer fringe (items whose addition is a state: what the learner is ready to learn). ALEKS shows the learner the outer fringe and lets them choose; on hundreds of thousands of assessments an outer-fringe item is learned successfully about 93 percent of the time. A hand-written prerequisite DAG is the partial-order special case, so the operation needs no state enumeration (2026-11-01-outer-fringe-learning-space-ready-learn).
- **Building prerequisites is the cost; outcome evidence is thin.** A 120-paper systematic review finds educational knowledge graphs used for adaptive learning, curriculum planning, concept mapping and QA with no effect sizes and weak evaluation; the prerequisite papers agree annotation is the bottleneck and attack it with embedding-ranked candidates that an expert accepts one at a time, discovery from learner trajectories, or LLM-built graphs validated only in simulators (2026-11-01-educational-knowledge-graphs-building-prerequisite-relations).
- **Prerequisite-only paths block.** When a concept will not click, a strict prerequisite walk stalls; KnowLP's fix is a sideways move along similarity edges triggered when mastery gain falls below a threshold, and removing it costs up to half the final gain in its simulator. Practitioners separate hard from soft and logical from pedagogical dependencies, note cycles at fine granularity and mastery levels per concept, and warn that a goal-first crawl of a hundred prerequisites kills motivation (2026-11-01-prerequisite-only-paths-block-learners-practitioners).
- **Concept maps help the learner who draws them.** In the one quasi-experiment read, training in constructing maps beat training in studying them (d = 0.52) but not the control after correction, with "map shock" for untrained construction; the meta-analytic figures (g = 0.82 constructing, 0.37 studying, as summarised on the web) are unverified because the papers are paywalled (2026-11-01-concept-maps-help-when-learner-constructs, 2026-11-01-what-nesbit-adesope-2006-schroeder-et).

So: a graph helps a learner by computing what they are ready for and what they should review (the one use with outcome data, and that data is a vendor estimate), by keeping the author honest about prerequisites, and by being drawn by the learner as an activity. It does not help by being shown to the learner as a map, and it does not help a planner that ignores it.

### 4.2 What the teach workflow has and lacks

The inventory of `skills/research-teach` and `bin/lib/teach.mjs` found that every ingredient of a prerequisite structure already exists as text and none of it is traversed:

- `PATH.md` lines carry `terms:`, `tool:` and `after:`; `readPath` parses `after:` and `pathLine` in `bin/commands/teach.mjs` prints it, but `teach next` picks the first line with no `lesson:` in file order (lines quoted at aa188e6 in 2026-11-01-research-vault-aa188e6-lines-graphify-evaluation). Probed, not recalled: with line 1 declaring `after: 2` and both lines untaken, `teach next` chose line 1 and `teach lint` said nothing (2026-11-01-probe-teach-next-teach-lint-ignore).
- Concepts exist only as lowercase strings: `### Known terms` and `### New to me` in MISSION.md, `data-introduces` on lessons, GLOSSARY.md prose. `LESSON_TERM_NOT_INTRODUCED` enforces introduce-before-use by lesson number, which is a topological-order check on an implicit graph.
- Learning records (kinds understanding, prior-knowledge, misconception, mission-shift) link to a lesson, never to a term or a vault entry; attempts link wrong quiz items to records; `reviewDue` is a 21-day spacing rule. The learner's state is therefore recoverable (records plus Known terms) but not expressed as a set of terms.
- Mission criteria (`## Success looks like`) are parsed and printed; nothing links a criterion to a lesson or a term.

### 4.3 The design that follows

Keep the DAG at the granularity the format already has (a PATH.md line, which is one lesson with at most one new term set or tool) and make three changes, each small:

1. **Enforce and walk `after:`.** `teach next` computes the fringe: every untaken line whose `after:` lines are all taken, listed after review-due and review-failed records; the `path:` line becomes a `fringe:` list with the first entry as the default. `teach lint` adds `PATH_AFTER_FORWARD` (an `after:` that names a later or missing line) and `PATH_AFTER_CYCLE`. The skill's §4 text changes from "the first PATH.md line no lesson has taken" to "a line from the fringe, the first unless the learner or the records say otherwise". The inner fringe (the most recently taken lines whose terms no later lesson has used yet) is the pool a review lesson draws from, alongside review-due records. Cost: a few dozen lines in `teach.mjs` and `lesson.mjs`, a fixture with a branching path, one test. Measured by 2026-11-01-does-choosing-next-lesson-from-prerequisite.
2. **Propose term prerequisites, let the author accept.** A `teach path candidates` listing derived from the lessons on disk: for each tracked term, the lesson that introduces it and the lessons that use it, hence candidate `after:` lines the path does not yet declare. The agent proposes, the path author accepts by editing PATH.md. This is the ACE pattern (machine ranks, human labels) and keeps edges authored, which is the vault's rule for every other edge. Open question 2026-11-01-can-prerequisite-edges-between-teach-terms asks whether the markup is enough; the listing is cheap to build and answers it.
3. **A sideways field and a construction step.** `near:` on a PATH.md line names lines the learner may take instead when stalled, offered only when `reviewFailed` fires twice on the same record (the stall signal the attempt log already yields); and LESSON-FORMAT gains an optional `step` variant asking the learner to state how the new term connects to two known terms, recorded as a learning record of kind understanding. The first is the KnowLP sideways move at the granularity of a path; the second is the concept-map construction finding turned into an activity.

What not to build: a concept graph over the vault's prose, a rendered map for the learner, a mastery model beyond the existing records and spacing rule, or anything that enumerates states. The ALEKS loop (assess, pick from the fringe, practise to a target score, re-assess) is already the shape of the teach skill's lesson-quiz-attempt-review cycle; the fringe is the part missing.

## 5. Ranked plan

1. Spec 17, teach fringe: §4.3 item 1. Smallest change with the best-evidenced payoff; lands entirely in the teach code and skill text.
2. Spec 17 or a follow-up: §4.3 items 2 and 3, after one live mission on the fringe rule has been observed.
3. Hygiene from lens one and two, as a single small change: manifest shrink guard, reviewer-prompt hash in the ledger row, `manifest --topics` and the vocabulary rule in `research-vault-usage`.
4. An example script on the contract that walks a superseded entry outward to the code symbols citing it across the `check --json` of several repos, as the blast-radius demonstration. No new CLI surface.
5. Deferred until a real need: `used-in-answer` verification and the `advise` section for entries never used in an answer; a per-topic MOC page.

Not adopted, by decision or evidence: tree-sitter extraction and code-to-code edges; community detection, degree hubs, surprising connections and suggested questions; LLM extraction of concepts from vault prose; fuzzy dedup; an MCP server; a PreToolUse read-guard; graph.json as a system of record.
