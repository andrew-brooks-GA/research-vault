# Evaluation 16: graphify, and what a graph can do for research-vault

Written 2026-11-01 on `worktree-graphify-eval` from master at aa188e6 (0.8.0). This is a research and planning document, not a spec: it names the concepts in Graphify-Labs/graphify worth re-deriving for this plugin, judges each against three uses (the plugin's code and the projects that join it, the vault as a body of knowledge, and the teach workflow), and reports what the education literature says a graph can do for a learner. Nothing here is implemented. The synthesis is 2026-11-01-graph-helps-learner-by-exposing-ready and its evidence chain is listed at the end. The rule of this evaluation, set by the user: take the concept, not the code or the feature.

How to read the evidence. Every statement about graphify is as the two captured notes report it from a subagent's read of the repository at one commit (2026-11-01-graphify-s-transferable-concepts-research-vault, 2026-11-01-graphify-s-outputs-markdown-layer-analytics); nothing of graphify was run, and the notes carry capture-time verification only. ## 1. What graphify is, in the terms that matter here

graphify, read on 2026-11-01 (the source entry records 0.9.100; one captured note says 243 releases in seven months, 92k lines of Python and 27 tree-sitter packages, the other puts `wc -l` over `graphify/` at about 96k lines), turns a folder of code and Markdown into one graph, with networkx among its dependencies, that an agent is nudged to query before it greps or reads. As the notes report it: code is parsed by tree-sitter and prose goes through LLM subagents; every edge carries a confidence tier (EXTRACTED, INFERRED, AMBIGUOUS) and a discrete score; Leiden communities, degree-ranked "god nodes", "surprising connections" and "suggested questions" are produced, and a GRAPH_REPORT summarises them; outputs include a vis.js HTML viewer, a wiki, an Obsidian export, a canvas, Neo4j and FalkorDB Cypher and an MCP server; PreToolUse hooks nudge the agent toward the graph; a `save-result` and `reflect` loop turns query outcomes into a LESSONS file (2026-11-01-graphify-labs-graphify-repository-at-0, 2026-11-01-graphify-s-transferable-concepts-research-vault, 2026-11-01-graphify-s-outputs-markdown-layer-analytics).

Two facts frame everything below. First, graphify's prose edges are LLM-inferred, and the captured note reports id drift across three producers as its dominant bug class and seventy changelog mentions of dedup false merges, with subagents required to report lines read; the vault's edges are authored and lint-checked, so that class of problem does not arise here, which is the conclusion the October synthesis reached for the previous generation of tools (2026-10-12-graph-representations-research-vault-expose-existing). Second, graphify's own worked reviews, as the note reports them, are the most candid evidence about its analytics on two corpora: on a three-service project six of the top-ten god nodes were test factories, 141 communities with cohesion 0.05 to 0.17 did not recover the architecture, 752 isolates were mislabelled as documentation gaps and the suggested questions were graph-property meta-questions; httpx scored 5.7 out of 10 with fourteen inheritance edges silently dropped; the memory benchmarks were run on an external harness with an embedder, and the only code result has six questions (2026-11-01-graphify-s-transferable-concepts-research-vault).

## 2. Lens one: the plugin's code and the projects that join it

What exists today: code links (spec 15) cite a vault id from a code comment, and `check --json` rows carry an `id`; REFERENCE lists the keys of `.vault-manifest.json` and `check --json` as the integration contract, says a project joins a row's `id` to an entry's `id`, and names `test/contract.test.mjs` as what pins them and `examples/graph-dot.mjs` as the worked join; spec 15 D2 and D8 record that `--cited-by`, a persisted index and a cross-repo index were cut, and the 0.8.0 changelog words the boundary as "the plugin stays with research" (2026-11-01-research-vault-aa188e6-lines-cited-by, 2026-11-01-research-vault-aa188e6-lines-graphify-evaluation).

| graphify concept (as the captured notes report it) | Problem it solves | Verdict for research-vault |
|---|---|---|
| Confidence tier on every edge, path confidence as the weakest hop, `also_seen` provenance on collapsed duplicates | A reader cannot tell a stated link from a guessed one | Adopt the rule, not the field. Authored links are EXTRACTED by construction and need no tier. The tier belongs only on machine-proposed links if a suggestion feature ever ships (see lens two), and `related` should report a multi-hop path's weakest link when it reports paths. |
| A prose mention becomes an edge only on a path-qualified match or a bare name matching exactly one symbol; ambiguity yields no edge | Name collisions produce false links | Keep this rule for the plugin. It bounds any future "which entry does this comment mean" helper: unique match or nothing. |
| Blast radius: reverse BFS over an allow-listed relation set, reporting the site where the dependency is made | "If this changes, what breaks" | The plugin already has the data: `check --json` rows carry an `id`, and `related` walks `sources` and `contributing_ids` in either direction (2026-11-01-research-vault-aa188e6-lines-cited-by). The missing operation is the composed one, "this source is superseded, which code symbols in which repos cite anything downstream of it". Spec 15 cut `--cited-by`; the right shape is an example script on the contract, like `examples/graph-dot.mjs`, not a new command, because the walk crosses the contract boundary into the project's own graph. |
| Edge-only joins across separately built graphs (`same_type_as`, repo-prefixed ids, never merging nodes) | Linking two repos without collapsing drifted copies | This is the graph contract restated from the other side. No change. A project with two repos citing one vault joins both `check --json` outputs on `id` rather than asking the plugin for a cross-repo index, which spec 15 D8 declines. |
| Stale-aware nudge hooks: PreToolUse context, softened wording when the index is older than the file, an opt-in deny that fires once per session then downgrades, fail-open, 10 s timeout | Agents ignore the index | The plugin registers four hooks (PostToolUse on `Edit\|Write`, SessionStart, PreToolUse on `WebFetch\|WebSearch`, Stop) and no Read, Grep or Bash matcher (2026-11-01-research-vault-aa188e6-lines-cited-by). The Zig evidence stands: whether graphify's tree-sitter graph resolves comptime chains is an open question (2026-10-16-does-tree-sitter-zig-graph-resolve), and for Zig std tutoring the October synthesis found structural tools winning only on relationship questions and mostly on cost, with the accuracy difference unproven (2026-10-16-accurate-zig-tutoring-keep-grep-over). A project that wants this runs graphify itself and joins on `id`. |

## 3. Lens two: the vault as a body of knowledge

What exists today, as quoted at aa188e6 (2026-11-01-research-vault-aa188e6-lines-cited-by): six entry types; seven edge fields, six of which form backlinks; a manifest whose edges are built from frontmatter fields only; a bounded BFS over those edges shared by `related` and the stale-evidence check, with `sources` and `contributing_ids` as the dependency relations; a search that filters rows by exact facet and case-insensitive substring with no ranking and hides superseded entries; a capture that dedupes on normalized URL plus subject version; and git-ignored `_index/` and `_obsidian/` views. The October synthesis records the vault as a typed graph with authored, lint-checked edges whose stubs surfaced only three of seven edge fields at the time (2026-10-12-graph-representations-research-vault-expose-existing).

| graphify concept (as the captured notes report it) | Problem it solves | Verdict for research-vault |
|---|---|---|
| Degree god nodes, Leiden communities with cohesion, surprising connections, suggested questions | Finding the core, the clusters, the bridges and the gaps | Do not adopt. The October note put the vault at about 600 entries with average degree about 1.3 and reports, as indicative, that graph retrieval beats flat retrieval only on multi-hop questions and only past a corpus size far above that (2026-10-12-graph-retrieval-beats-flat-only-multi); graphify's own worked review of one corpus (rsl-siege-manager) reports degree and community analytics surfacing scaffolding. The vault's declared `topics`, `domain` and `series` are its community structure, authored. The one cheap `advise` addition worth having is a degree listing by type with syntheses and index-like notes excluded, as a curation prompt for an over-cited source, with no claim that it is "core". |
| Work memory: query outcome files with frontmatter (`outcome: useful \| dead_end \| corrected`, `source_nodes`), signed and time-decayed scoring with a 30-day half-life, "preferred" only after two distinct useful results, kept in a sidecar and never steering traversal | Agents re-derive dead ends and forget which sources answered well | Adopt the concept in the vault's own terms. The vault already has `question` entries and per-entry `verifications`; what it lacks is "this entry answered a question well" as a signal. The lightest form: a new value for `verifications[].method`, `used-in-answer`, and an `advise` section listing entries never used in any answered question. No decay, no scoring, no steering of `search`; the note reports graphify itself keeps verdicts out of traversal to avoid a feedback loop. |
| Constrained query expansion: dump the label vocabulary, let the model pick up to twelve terms only from it, print the expansion, stop when nothing matches | Synonym mismatch against a literal matcher | The vault's `search` is literal and unranked (2026-11-01-research-vault-aa188e6-lines-cited-by), so the gap is real, but the fix lives in the skill, not the CLI: the usage skill should tell the agent to read the topic vocabulary (a `manifest --topics` listing is a one-line addition) and choose search terms from it. Auditability comes free because the agent prints its search commands. |
| Token-budgeted BFS and DFS subgraph retrieval, with savings reported from 71.5x on a mixed corpus down to about 1x on httpx | Context bloat | `related` is a bounded BFS over manifest rows (2026-11-01-research-vault-aa188e6-lines-cited-by). graphify reports 71.5x on a 52-file corpus and about 1x on httpx; nothing is measured at the vault's size. No change. |
| Page and heading structural nodes, `contains` and `references` edges from Markdown links and wikilinks, frontmatter parsed onto the page node | Section-level navigation without an LLM | The vault's unit is the entry, not the heading, and the manifest builds edges from frontmatter fields only (2026-11-01-research-vault-aa188e6-lines-cited-by), so an id written in a body is a citation for `check`, not an edge to traverse. That boundary should stay. No change. |
| Dedup via MinHash and Jaro-Winkler with a community bonus and an optional LLM tiebreak | Near-duplicate nodes | Do not adopt. In the author's judgement, titles that differ by a word are usually distinct claims in a research vault, and `capture` already dedupes on URL and version, flagging a content change at the same key as ambiguous (2026-11-01-research-vault-aa188e6-lines-cited-by), which is the honest key. |
| LLM extraction of concept and entity nodes with `cites` and `semantically_similar_to` edges, wrapped in untrusted-source guards | A semantic graph over prose | Do not adopt. The October note reports the literature's dominant graph failure as incomplete LLM-extracted edges (2026-10-12-graph-retrieval-beats-flat-only-multi); the vault's value is that its edges are declared. A link suggestion that proposes `related` candidates and waits for the author is the most that fits, and it would carry the confidence tier from lens one. |
| Wiki export: index, one article per community and per hub, each with an audit-trail section, regenerated destructively | A browsable summary layer | `_index/` and `_obsidian/` already play this role and are git-ignored. `_index/` could gain a per-topic page listing entries and their one-line summaries, which is what graphify's community article becomes once communities are replaced by declared topics. Low priority. |
| Ambiguous edges halved in clustering and listed for review | Uncertain links should neither distort structure nor be discarded | The vault's `question` type and `related` field are the place for an uncertain link. No change. |

## 4. Lens three: the teach workflow, and what a graph does for a learner

### 4.1 What the education literature says

The research for this lens was run vault-first and captured nine sources, four notes, three questions and one synthesis. The findings, as the captured notes report them, in order of weight:

- **The fringe is the operation.** The note on knowledge space theory reports a learner modelled as a state (the set of items mastered) in a family of feasible states; in a learning space a state is determined by its inner fringe (items whose removal leaves a state) and its outer fringe (items whose addition is a state), and the outer fringe "tells us exactly what the student is ready to learn". ALEKS shows the learner the outer fringe and lets them choose; the note's figure for success on an outer-fringe item is about .93, a vendor estimate on ALEKS mathematics data, not independently replicated in the sources read. A hand-written prerequisite list is the partial-order approximation of such a structure (2026-11-01-outer-fringe-learning-space-ready-learn).
- **Building prerequisites is the cost; outcome evidence is thin.** The note reports a 120-paper systematic review finding educational knowledge graphs used for adaptive learning, curriculum planning, concept mapping and QA with no effect sizes and weak evaluation, and the prerequisite papers agreeing that annotation is the bottleneck, attacked by embedding-ranked candidates that an expert accepts one at a time, discovery from learner trajectories, or LLM-built graphs validated only in simulators (2026-11-01-educational-knowledge-graphs-building-prerequisite-relations).
- **Prerequisite-only paths can block.** The note reports KnowLP's argument that a strict prerequisite walk stalls when a concept will not click, its fix of a sideways move along similarity edges when mastery gain falls below a threshold, and an ablation in its simulator where removing that move drops the final figure on MOOCCubeX from 0.3589 to 0.1517 at step 20, more than half; one practitioner wiki page separates hard from soft and logical from pedagogical dependencies, notes cycles at fine granularity and mastery levels per concept, and warns that a goal-first crawl of about a hundred prerequisites kills motivation (2026-11-01-prerequisite-only-paths-block-learners-practitioners).
- **Concept maps help when the learner constructs them and has been trained to.** In the one quasi-experiment read, as the note reports it, training in constructing maps beat training in studying them (d = 0.52) but not the control after correction, and the authors warn of "map shock" for untrained construction; the meta-analytic record as that paper summarises it is mixed, and the effect sizes circulating on the web are unverified (2026-11-01-concept-maps-help-when-learner-constructs, 2026-11-01-what-nesbit-adesope-2006-schroeder-et).

So: a graph helps a learner by computing what they are ready for (the one use whose outcome figure comes from a large deployment, and that figure is a vendor estimate), and, on this evaluation's reading of the inner fringe, what a review should draw on; it keeps the author honest about prerequisites; and the evidence read favours the learner drawing the map over being shown one, with a mixed meta-analytic record behind that. It does not help a planner that ignores it.

### 4.2 What the teach workflow has and lacks

The quoted lines and the probe (2026-11-01-research-vault-aa188e6-lines-graphify-evaluation, 2026-11-01-research-vault-aa188e6-lines-cited-by, 2026-11-01-probe-teach-next-teach-lint-ignore) establish:

- `PATH.md` lines carry `terms:`, `tool:`, `after:` and `lesson:`; `readPath` parses `after:` and `pathLine` selects `path.find((x) => !x.lesson)`, the first line with no lesson, and returns it as a `path:` line with its `after:`. Probed: with line 1 declaring `after: 2` and both lines untaken, `teach next` chose line 1 and `teach lint` said nothing about the forward `after:`.
- The skill's §4 procedure tells the agent to build "the `path:` line naming the first `PATH.md` line no lesson has taken", after review-due and review-failed records, and one of its principles is the zone of proximal development.
- Tracked terms are the Floor's "New to me" terms plus every lesson's `data-introduces`, and the Floor's known terms are always allowed; `LESSON_TERM_NOT_INTRODUCED` fires when a lesson's prose uses a tracked term that neither the Floor nor this or an earlier lesson introduces, so introduce-before-use is enforced in lesson order, which is a topological check on an implicit graph.
- The teach index gives each lesson its `cites` and the records its quiz items name, attempts back-link the records in their `records` field, and review-due is computed against a `SPACING_DAYS` cutoff. Records link to lessons; nothing quoted links a record to a term or a vault entry.
- `teach next` prints the mission criteria; nothing quoted links a criterion to a lesson or a term.

### 4.3 The design that follows

Keep the DAG at the granularity the format already has (a PATH.md line) and make three changes, each small:

1. **Enforce and walk `after:`.** `teach next` computes the fringe: every untaken line whose `after:` lines are all taken, listed after review-due and review-failed records; the `path:` line becomes a `fringe:` list with the first entry as the default. `teach lint` adds `PATH_AFTER_FORWARD` (an `after:` that names a later or missing line; the missing-line case was not probed) and `PATH_AFTER_CYCLE`. The skill's §4 text changes from "the first PATH.md line no lesson has taken" to "a line from the fringe, the first unless the learner or the records say otherwise". The inner fringe (the most recently taken lines whose terms no later lesson has used yet) is the pool a review lesson draws from, alongside review-due records. Cost: a few dozen lines in `teach.mjs` and `lesson.mjs`, a fixture with a branching path, one test. Measured by 2026-11-01-does-choosing-next-lesson-from-prerequisite.
2. **Propose term prerequisites, let the author accept.** A `teach path candidates` listing derived from the lessons on disk: for each tracked term, the lesson that introduces it and the lessons that use it, hence candidate `after:` lines the path does not yet declare. The agent proposes, the path author accepts by editing PATH.md. This follows the expert-acceptance pattern the educational-graph note reports, and keeps edges authored, which is the vault's rule for every other edge. Open question 2026-11-01-can-prerequisite-edges-between-teach-terms asks whether the markup is enough; the listing is the first half of answering it, and the author's accept-or-reject pass with its precision is the second.
3. **A sideways field and a construction step.** `near:` on a PATH.md line names lines the learner may take instead when stalled, offered when the review-failed signal repeats on the same record (the note's proposal for a stall signal; the attempt log's `records` field is what it would read); and LESSON-FORMAT gains an optional `step` variant asking the learner to state how the new term connects to two known terms, recorded as a learning record of kind understanding. The first is KnowLP's sideways move at the granularity of a path; the second is the concept-map construction finding turned into an activity.

What not to build: a concept graph over the vault's prose, a rendered map for the learner, a mastery model beyond the existing records and spacing rule, or anything that enumerates states. By analogy, the ALEKS loop the note describes (assess, pick from the fringe, practise to a target score, re-assess) resembles the teach skill's lesson, quiz, attempt and review cycle; the fringe is the part missing.

## 5. Ranked plan

1. Spec 17, teach fringe: §4.3 item 1. Smallest change with the best-evidenced payoff; lands entirely in the teach code and skill text.
2. Spec 17 or a follow-up: §4.3 items 2 and 3, after one live mission on the fringe rule has been observed.
3. Hygiene from lens one and two, as a single small change: manifest shrink guard, reviewer-prompt hash in the ledger row, `manifest --topics` and the vocabulary rule in `research-vault-usage`.
4. An example script on the contract that walks a superseded entry outward to the code symbols citing it across the `check --json` of several repos, as the blast-radius demonstration. No new CLI surface.
5. Deferred until a real need: `used-in-answer` verification and the `advise` section for entries never used in an answer; a per-topic MOC page.

Not adopted: tree-sitter extraction and code-to-code edges (spec 15 D8, REFERENCE); community detection, degree hubs, surprising connections and suggested questions; LLM extraction of concepts from vault prose; fuzzy dedup; an MCP server; a PreToolUse read-guard; graph.json as a system of record.
