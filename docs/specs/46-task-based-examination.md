## Findings from research

Each finding is scoped as the vault entries scope it. Grader internals are not vendor-documented; the LLM evidence is from programming courses only; the solve-then-check gate is a proposal, not a measured result.

1. **Candidate reports say CKA, CKAD and Red Hat exams grade the end state of real machines by script, not the method.** The Linux Foundation's tips page says CKA and CKAD have 15 to 20 tasks in 2 hours, each on a named host reached by ssh; candidate reports say Red Hat exams are "graded by script with no human in the loop", with every system rebooted first so "a change that does not persist, or a node that does not boot, scores zero"; the vendor documents neither grader, and Red Hat reports per-objective percentages, never per-item results (2026-11-03-performance-based-exams-grade-end-state). Training-lab platforms use the same check in small form, "a verify script whose exit code passes or fails the step, with an optional hint for the learner" (same note). The note's own reading is the model this spec takes: "an environment seed, a prompt, and a set of state assertions run after a reset or reboot", each assertion "a read-only query (kubectl get -o jsonpath, systemctl is-enabled, a curl), never a check of shell history".
2. **Where method matters, OSCP+ adds a human-read report; the note reads the flag as the machine-checkable part.** OSCP+ scores per-machine flags (local.txt readable by an unprivileged user, proof.txt only by root or Administrator) entered in a control panel that does not say whether they are correct, and "points only count when a report a human reads shows each proof in an interactive shell with the target IP"; the report "must let a competent reader reproduce every attack", and "AI chatbots and LLMs are banned during the exam" (2026-11-03-offensive-security-exams-combine-flag-proofs). The synthesis reads this as "a flag is a cheap proof of access and the report is the proof of method" (2026-11-03-how-performance-based-certifications-grade-tasks).
3. **Two studies report LLMs writing programming tasks and their tests; one implies about one item in ten needs a fix.** GPT-4 test suites given a problem statement and a reference solution "were usually at least as comprehensive as the instructor's suites (26 problems, 25,000+ submissions)"; a pipeline that generated programming tasks with their tests had 89.5% rated functional and 92.5% solvable by experts; before LLMs, generated personalised security lab tasks for 207 students flagged 7 suspicious submissions (2026-11-03-llms-can-write-checkers-generated-variants). The note's caveat is the one this spec designs around: "All three are programming or intro-security courses. None measures an LLM writing Kubernetes or Linux state checks. The 89.5% figure implies a validation gate is mandatory."
4. **The vault found no published measurement of LLM-written checkers on Kubernetes or Linux state.** The synthesis found none, and its recommendation is explicitly "my proposal, not a measured result": generate each item as four parts, "setup, prompt, reference solution, checker", and "accept an item only if the checker fails on the fresh environment and passes after the reference solution runs, ideally after a reset"; use flags where access is the skill and a human-read report where method is the skill; "LLM grading of such reports is untested here" (2026-11-03-how-performance-based-certifications-grade-tasks). The open question names the failure modes a state checker has that a unit test does not, "eventual consistency, equivalent configurations (a label set by patch or by apply), and timing after a reboot", and what would answer it: about 50 CKA-style items, each checker run against a fresh environment, the reference solution and two or three wrong or alternative-correct solutions, counted against a human grader (2026-11-03-how-reliably-do-llm-written-state).

What the findings license, in one sentence: an end-state task with a read-only, exit-code checker, validated fresh-fails and solved-passes before a learner sees it, is consistent with how candidate reports say CKA, CKAD and Red Hat grade and is the one proposal the vault makes, with OSCP+ adding a human-read report for method; a machine-graded method task is not licensed by any entry this spec cites.

## Design

### D0. Contracts kept

1. No new lesson shape and no new vault entry type. The `project` shape (LESSON-FORMAT.md line 50), the three evidence kinds and the `snippet` plus `experiment` capture (SKILL.md line 58) carry the whole feature.
2. Attempts are "written by `teach serve` or `teach attempt add`, never edited" (SKILL.md line 25); a task result lands through `teach attempt add --result` exactly as a project run does today (line 112). No new verb.
3. The reader gate and the claims gate are unchanged. The validation claim is a "verified by running" claim and the reviewer already demands an experiment for one (claims-reviewer.md line 32).
4. The learner's machine runs state-changing scripts only when the learner runs them, or inside the item's validation run, which the skill already performs for every probe (SKILL.md line 58). Outside the validation run, the skill runs nothing but the read-only checker.
5. `ESM only, no dependencies, no classes`; a `COUPLINGS` row when two files share a name (AGENTS.md lines 17 and 18).

### D1. Where the learner opts in, and what `MISSION.md` records

The interview's depth item (SKILL.md line 43) gains one follow-up, asked only when the answer is "do it unaided", as its own dialog question in the same turn: "Where can a task be set up and torn down?" with the options `Docker or kind on this machine`, `a VM or a cluster of my own that I can reset`, `nowhere yet`. The answer is one bullet under `## Constraints` in `MISSION.md`: `Task environment: kind on this machine`, or `Task environment: none`. With `none`, every project lesson stays as it is today (the answer or artefact the learner shows, line 61), so a non-software mission is untouched by the rest of this spec. Judgment: `## Constraints` is the section for "anything that bounds the approach" (MISSION-FORMAT.md line 29), and one bullet keeps the file a compass (line 43). Since a checked task's step runs `bash` (D2), the tools item (line 45) then asks about `bash` like any other tool a lesson will run; a `never` there gets a `PATH.md` line, as the rule already says (judgment: placed before the first task, since the task's step runs it).

The skill being tested is the end state. `MISSION.md` records no method option in this slice (D5).

### D2. The task item: a project lesson with three scripts in its evidence folder

A checked task is a `project` lesson whose `evidence/NNNN/` folder holds, beside `PLAN.md` and `run.sh`, three scripts:

| File | Does | Run by |
|---|---|---|
| `setup.sh` | Creates the task's scope from nothing: a namespace, a kind cluster or a container named `teach-NNNN`, removing one left from an earlier run first, so running it again is the reset | the learner, before working; `run.sh` during validation |
| `check.sh` | Read-only state assertions over that scope, one per requirement in the task statement; prints `PASS` and exits 0 when every one holds, else one `FAIL: <requirement>, <hint>` line per unmet one and exits 1 | the learner, when done; the skill, via Bash, since it changes nothing; `run.sh` during validation |
| `solution.sh` | The reference solution, from the fresh scope to a passing state | `run.sh` during validation only |

The plan's six parts (LESSON-FORMAT.md lines 138 to 149) hold the item: the win is the mission criterion the task serves; the fact is the end state the task requires; the claims are exactly three lines, "the check fails on a fresh setup", "the check passes after the reference solution", "the check fails again after setup is rerun"; the probe is `run.sh`, which runs `setup.sh`, `check.sh` (exit 1 expected), `solution.sh`, `check.sh` (exit 0 expected), `setup.sh`, `check.sh` (exit 1 expected) and echoes each exit code; the step is the learner's run; the Elements are the lessons the task integrates. The three scripts and `run.sh` are captured as the one `snippet` and the log as the one `experiment`, per SKILL.md line 58, unchanged. The third claim is what makes "setup is the reset" true rather than hoped; it is this spec's rendering of the synthesis's "ideally after a reset".

The lesson page is a project page as the format already defines it (lines 50 and 61): `mission` states the task as the goal and `PASS` as the observable result; `prereq` names the lessons it assumes; `step` holds, in prose, the task statement (the names and values the checker asserts, in full, so the learner is graded on what the page said), then the two commands, each a bare `<pre>` line with no prompt and no output line, since `commandTools` reads every non-empty, non-comment `<pre>` line of `step` as a command (lesson.mjs line 287) and an output line `PASS` would be read as a tool named `pass`:

```
bash evidence/0004/setup.sh
bash evidence/0004/check.sh
```

then, in prose, that the second command prints `PASS`, stated as the experiment's Result quotes it, and one sentence ending in a citation of the experiment, "This check fails on a fresh setup and passes after the reference solution." `sources` links the snippet as the reference solution (line 61, already the rule). `scaffold` is unchanged. The task statement sits in `step` because `step` is already "One real-world action and its observable result, with the command to run when the action is one" (line 31); judgment, so that no new block and no stylesheet label is needed.

Where it renders: the served project page, under its `Project:` line in the index, as every project does; `scoreOf` shows the attempt's `result`, pass or fail (teach.mjs line 290). `evidence` is not in `STATIC_DIRS` (line 320); whether a GET of it returns 404 was not probed here and is one of D6's fixture checks. The solution is on disk, and the learner can read it. Judgment: this is a learning tool, not a proctored exam, and the one exam among the entries cited here that polices method, OSCP+, does it with a human and a ban on LLMs (finding 2), neither of which this skill has; the page says the solution is on disk and that reading it first turns the attempt into a read.

### D3. Grading: who runs what, and the safety boundary

The learner runs `setup.sh` and `check.sh` in their own terminal; that is the step. The skill may run `check.sh` through Bash when the learner asks it to grade, because the checker is read-only by rule; it never runs `setup.sh` or `solution.sh` on its own, except inside `run.sh` while validating the item, which is the probe run SKILL.md line 58 already has it perform. The result is recorded as today: `teach attempt add --lesson <id> --result pass` after a `PASS`, `fail` otherwise (line 112), by the skill after the learner reports the line or after the skill ran the checker itself. `writeAttempt` writes no body (teach.mjs line 148), so the hint is what the learner saw, not a stored field; a `fail` stays the corrected-misconception candidate line 112 makes it.

The safety boundary is three rules the skill states in the lesson plan and the lint partly enforces (D4):

1. Everything `setup.sh` and `solution.sh` create, change or delete lives inside the scope named `teach-NNNN` in the environment `MISSION.md`'s bullet names. A task that needs a cluster-wide object (a CRD, a ClusterRole) names it in the plan and the lesson says so before the setup command.
2. `check.sh` contains no command that changes state. For the tools this slice targets, that is no `kubectl` verb in `apply`, `create`, `delete`, `patch`, `replace`, `edit`, `scale`, `rollout`, `exec`, `cp`, `label`, `annotate`, no `docker` or `kind` verb in `run`, `rm`, `stop`, `kill`, `start`, `create`, `delete`, `exec`, and no `rm`, `mv`, `cp`, `tee` or redirection to a file (judgment: a list, advisory in the lint, since a heuristic over shell text is not a proof).
3. A check may wait, with a bound, as a design rule: a wait is a bounded poll of a read-only query (the note lists `kubectl get -o jsonpath` as one) and never a change, and which flag does that on each tool is the item author's to show in the validation run. This is how the open question's eventual-consistency case (2026-11-03-how-reliably-do-llm-written-state) is handled, and the bound is why a false fail costs the learner one rerun of `check.sh`, not a lost attempt: the skill records an attempt only when the learner says they are done, not on every run.

### D4. Validation: the lint checks the shape, the claims gate checks the run

`teach lint` can enforce that the item is complete and that the lesson claims validation; only the claims gate can check that the validation run happened and shows what the claim says. Two lint rules and one extension:

- `LESSON_TASK_INCOMPLETE`, a finding: for a `project` lesson whose `evidence/NNNN/check.sh` exists, each of `setup.sh` and `solution.sh` exists, a `step` `<pre>` line runs `check.sh`, and `sources` cites at least one entry of type `experiment` (the lint already resolves cited types for `WARN_MODEL_LAB_ONLY`, lesson.mjs lines 438 and 439). A `check.sh` with no `setup.sh` is a task with no reset; one with no `solution.sh` is one no run could validate; one with no experiment is one whose validation exists only on disk, which SKILL.md line 58 says is not evidence.
- `WARN_TASK_CHECK_MUTATES`, advisory: a `check.sh` line whose first word, or verb after `kubectl`, `docker` or `kind`, is in D3's list, named with its line. Advisory because the list is a heuristic.
- `commandTools` (lesson.mjs lines 282 to 298) also reads `solution.sh`'s non-comment lines, with the block name `solution.sh`, so `LESSON_TOOL_NOT_INTRODUCED` fires when the reference solution uses a tool neither in the Floor's Known tools nor taught by this or an earlier lesson (`data-teaches`): a task whose own solution needs an untaught tool is unfair by the skill's own rule (lines 458 to 468), and the step's commands name only `bash`.

The claims gate needs no change. The sentence in `step` ("This check fails on a fresh setup and passes after the reference solution") is a "verified by running" claim, so the reviewer requires an experiment (claims-reviewer.md line 32) and reads its Result for what the run printed (line 16): `run.sh`'s echoed exit codes, 1 then 0 then 1. A Result that shows 0 on the fresh scope is a checker that passes an empty environment, and the reviewer reports it `contradicted`; that is the synthesis's acceptance rule (finding 4) run by the gate that already exists. The evidence lives where every probe's does: the snippet and experiment in the vault, named in `PLAN.md`, cited from the lesson, and passed to the gate as the extra ids (research-claims-gate SKILL.md line 21).

What this does not establish, stated so the lesson does not overclaim: the validation proves the checker tells the fresh scope from the solved one, not that it rejects a wrong or partial solution. That is exactly the open question's "2-3 deliberately wrong or alternative-correct solutions", unmeasured in the vault, and the lesson's sentence is worded to the two states it ran.

### D5. Method-graded tasks: not in this slice

Out of scope, for two reasons the vault gives. The one exam in the vault's survey that grades method, OSCP+, does it with a human reader and a ban on LLMs during the exam (finding 2), and the synthesis says LLM grading of such reports is untested (finding 4). A `result: pass` written from the skill's reading of a write-up would be an attempt with no evidence behind its grader.

What the skill can do without claiming to grade: a `connect`-style prompt. The `connect` block is "a prompt answered in the terminal, not a quiz item: the skill judges the answer in conversation, against the plan's Fact, and records an understanding record when it holds" (LESSON-FORMAT.md line 60). After a `PASS`, a task may end with the same kind of prompt, "say how you got there and why each step was needed", judged in the terminal against `solution.sh`, recording `understanding` (LEARNING-RECORD-FORMAT.md line 52) when it holds and nothing when it does not. The attempt stays what the checker said; the record is the skill's judgment, labelled as such in the record. Whether to add this is an open question below, not a decision.

Reused with no change: the `project` shape and its `step` and `sources` rules; `PATH.md` `Project:` lines and the index grouping; `teach attempt add --result` and the progress page's pass or fail; `evidence/NNNN/` with `PLAN.md` and `run.sh`; the snippet and experiment capture and the gate's extra ids; the reader gate; the claims reviewer's experiment rule; `teach serve`'s `STATIC_DIRS`, which does not name `evidence`; the interview's depth and tools items; `MISSION.md`'s Constraints section.

The first slice is one task type, a shell-checked end state for a software mission with a task environment, and it is:

1. Text: SKILL.md item 3's follow-up question and the Constraints bullet (D1); SKILL.md line 31 and line 58 naming the three scripts, the three claims and the `run.sh` sequence (D2); LESSON-FORMAT.md's project rule (line 61) gaining a "Checked task" paragraph with the step form above and the three safety rules (D2, D3); MISSION-FORMAT.md's Constraints example gaining `Task environment: ...`; docs/REFERENCE.md line 32 gaining "checked tasks".
2. Code: `LESSON_TASK_INCOMPLETE`, `WARN_TASK_CHECK_MUTATES` and the `commandTools` extension (D4), one fixture (a project lesson with the three scripts, a Result showing 1, 0, 1), and one test per rule; a `COUPLINGS` row tying the three file names in lesson.mjs to LESSON-FORMAT.md.
3. `CHANGELOG.md` line under Unreleased.

Not in the first slice: any method grading (D5); a checker that posts its own attempt (the learner or the skill records it, D3); non-software tasks (a spreadsheet or document checked by script is possible in the same shape, with no environment bullet needed, and waits for a mission that asks); a reset verb (`setup.sh` is the reset, D2); Windows (the scripts are `bash`).

## Risks

- **Destructive setup.** A generated `setup.sh` that deletes outside its scope. Mitigation: rule 1 of D3, the `teach-NNNN` name, the learner running setup themselves after reading the page's sentence about what it touches, and the environment bullet naming only something the learner said they can reset. Residual: a kind cluster or VM named in the bullet is the learner's to lose; the interview option says so in its wording ("that I can reset").
- **Environment drift.** The learner's cluster differs from the one the item was validated on (a newer kubectl, a missing storage class). Mitigation: validation runs on the learner's machine, since the skill runs there, so the validated environment is the graded one until something changes between validation and attempt; the Result holds the run log verbatim (SKILL.md line 58), so what the validation run saw is on record. Residual: a change in between gives a false fail; the hint and a rerun cover it, and a persistent one is a `hypothesis-relevant` rerun line and a new validation, as for any probe.
- **False pass and false fail on eventual consistency.** Mitigation: bounded waits in the checker (D3 rule 3) and recording an attempt only when the learner says they are done. Residual: unmeasured; it is the open question's subject.
- **False pass on a partial or wrong solution.** The validation (fresh fails, solved passes) does not test this (D4's last paragraph). Mitigation: one assertion per requirement in the task statement, so a partial solution fails the assertions it missed and the FAIL lines name them. Residual: an assertion the author forgot passes silently; unmeasured.
- **The learner reads `solution.sh`.** On disk by design (D2). Residual: accepted; the attempt is for the learner, not a credential.
- **Non-software domains.** No environment, no checker; the project stays prose-checked. Residual: none in this slice; the feature does not apply.
- **The heuristic mutation list.** A read-only use of a listed verb warns wrongly, and a mutating command the list misses passes. Advisory for that reason.

## Open questions

1. Should the first task in a mission carry a `scaffold` (the project rule's "the mission's first project carries one")? A scaffold over `solution.sh` shows part of the solution before the attempt. Judgment leaning no for a checked task: the scaffold belongs on an unchecked project, and a checked task is the group's integration run. Decide when the first mission with tasks is built.
2. The "say how" prompt of D5: add it in slice two, or leave method entirely to the terminal conversation the lesson already invites?
3. Should the `teach-NNNN` scope name be a lint check over `setup.sh` (a finding when the script names no such scope), or stay a plan rule? Cheap to add; unclear it catches what matters.
4. The open vault question stays open: with about 50 items the measurement it names could be run on the skill's own output (each checker against the fresh scope, the reference solution and two or three wrong or alternative-correct solutions, counted against a human grader). The first slice gives the harness for it; whether to run it is a research decision, not a teach one.
5. Whether `run.sh`'s echoed exit codes are enough for the reviewer, or the plan should also quote the checker's FAIL lines on the fresh scope so a checker that exits 1 for the wrong reason (a tool missing) is caught. Judgment leaning the latter; it costs one `cat` in `run.sh`.

## Recommended first slice, in one paragraph

Offer it, as a property of a project lesson rather than a new kind of lesson: when the interview's depth answer is "do it unaided" and the learner names a task environment, the mission's project lessons become checked tasks, each with `setup.sh`, `check.sh` and `solution.sh` under its evidence folder, validated by the probe run the skill already performs, captured as the snippet and experiment it already captures, claimed in the lesson's step and checked by the claims gate it already runs; one lint finding for a task missing a part or an experiment, one advisory for a checker that looks like it writes, and the tool rule extended to the reference solution. Method grading stays out until the vault holds evidence that an LLM can grade a write-up.
