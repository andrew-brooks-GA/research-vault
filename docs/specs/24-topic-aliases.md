## Decisions

### D0. Contracts kept

1. The built-in pairs keep their meaning in every vault: a vault adds pairs and cannot redefine a built-in key, the additive rule the list fields already follow.
2. The vault copy of `taxonomy.json` stays a verbatim copy; the per-vault map lives in `.research-vault.json`, which `refreshDocs` does not write (it writes `AGENTS.md` and `taxonomy.json` only).
3. `lint --fix` without `--topics` writes exactly what it writes today. The topic rewrite is opt-in because it changes meaning where the quote unwrap changes form.
4. No manifest key, no frontmatter field, no new lint code: `WARN_TOPIC_ALIAS` and `aliasable` already name the entries.
5. The proposal step (new candidate pairs from title or topic similarity) stays deferred, as the issue says.

### D1. `taxonomy_extensions.topic_aliases`

`validateTaxonomyExtensions` accepts one map-valued key, `topic_aliases`: its value must be an object whose keys and values are non-empty strings, else `invalid .research-vault.json: taxonomy_extensions.topic_aliases must be an object of non-empty strings`; the key is copied into the returned map. The six list fields keep their checks, and any other key is still `not extensible`; `EXTENSIBLE_TAXONOMY_FIELDS` stays the list of list-valued fields, and the comment above it names `topic_aliases` as the one map-valued extension.

`applyTaxonomyExtensions` merges `extensions.topic_aliases` onto `taxonomy.topic_aliases` into the copy, built-ins first. A vault key that is already a built-in key throws `invalid .research-vault.json: taxonomy_extensions.topic_aliases.<key> redefines a built-in alias`, whatever its value; the input taxonomy is not mutated. A vault pair is one hop: `k8s` to `kubernetes` maps `k8s`; nothing follows the canonical value through another pair.

### D2. Every consumer on the vault's schema

`advise` calls `loadSchema(repoRoot, { vaultPath })` and `searchVault` calls `loadSchema(repoRoot, { vaultPath })`, so the five consumers all see a vault-declared pair. Discovery is keyed on the vault (the nearest `.research-vault.json` above it), as for the list fields.

### D3. `lint --fix --topics`

`run` in `lint.mjs` reads the flag as `manifest` does, `'topics' in args`, and passes `{ topics: true }` to `fixVault(vaultPath, repoRoot, opts)`. With it, `fixVault` replaces `entry.data.topics` by each topic mapped through `schema.taxonomy.topic_aliases` (the merged map, so built-in and vault pairs both apply), deduplicated in first-occurrence order, before the reserialisation; a changed list makes the file count as fixed through the existing `out !== raw` test. Without it, `fixVault` is unchanged. The output line stays `fixed <n> file(s)`.

### D4. Documents that restate the behaviour

- `docs/REFERENCE.md`: the extensions section gains a `topic_aliases` object in the example and one bullet (a map-valued `topic_aliases` of vault pairs that may not redefine a built-in key; `volatility` and `stage_by_folder` stay non-extensible); the `lint` row gains `--fix --topics` (rewrite each aliased topic to its canonical value and deduplicate); the `advise` row is unchanged.
- `commands/research-lint.md`: when `WARN_TOPIC_ALIAS` is among the warnings, offer `lint --fix --topics`.
- `skills/research-librarian/SKILL.md` line 15: `lint --fix --topics` rewrites them.

- `CHANGELOG.md`: one line under `## [Unreleased]`, `### Added`.
- Not changed: the generated vault `AGENTS.md`, `commands/research-init.md` (no line of it holds `taxonomy_extensions` or the word `extension`), and the plugin's `taxonomy.json`.

### D5. Tests

1. `test/projectconfig.test.mjs`: `validateTaxonomyExtensions` accepts `{ topic_aliases: { k8s: 'kubernetes' } }` and returns it; rejects an array value, a non-string value and an empty key, with the D1 message.
2. `test/schema.test.mjs`: `applyTaxonomyExtensions` merges a vault pair after the built-ins without mutating the input, throws the D1 message on `{ tdd: 'anything' }`, and `loadSchema` with the config hook of the existing discovery test sees the pair.
3. `test/lintfix.test.mjs`: on a temp vault inside a directory holding a `.research-vault.json` with the `k8s` pair, an entry with topics `[k8s, kubernetes, tdd]` becomes `[kubernetes, test-driven-development]` under `fixVault(dir, root, { topics: true })` and is untouched under `fixVault(dir, root)`; through `run` with `{ vault: dir, fix: true, topics: undefined }` the same.
4. `test/advise.test.mjs`: the same vault lists the entry under `aliasable` before the fix and nothing after.
5. `test/search.test.mjs` (its imports are quoted in 2026-11-02-lines-behind-issue-13-topic-alias, round 1 additions): on that vault, `searchVault(dir, { topic: 'kubernetes' })` returns the entry while it still carries only `k8s`, which needs the vault pair, since `matchRows` expands the entry topics through the map before comparing.
