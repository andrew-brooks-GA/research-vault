## Decisions this spec designs within

Taken before the spec and not reopened here: the link is a vault entry id in a comment next to the code it justifies; the unit is the declaration that follows the comment; the gate blocks a change to code linked to a stale or superseded entry and the reviewer checks the linked code against the entry; code re-checks on a change of the pinned dependency's version, not on elapsed time, and the taxonomy for that composes with `volatility` rather than replacing it; the feature is opted into once, when `init --project` binds a project-specific vault inside the repo, and is off everywhere else; existing vaults are not modified; the first language is chosen from the vault; no dependency, so detection is per-language regex that says what it cannot see.

Two consequences the reviews made explicit, recorded here so they are not read as drift: a link that carries no pin has no version to compare, so it follows the entry's time rule (the two existing wow_forever comments are such links until someone pins them); and a `code` block written by hand into an existing binding is an accepted opt-in, since the decision allows a project to add the block later by hand.

## Problems

1. A citation in code is invisible to the plugin's discipline. `bin/lib/citations.mjs` treats fenced blocks and inline spans as examples, not citations, so a vault id in markdown code is `skipped`; a Lua file is not markdown, so today `check 'addons/**/*.lua'` on wow_forever reads its `--` comment lines as prose and reports the two hand-written ids as `ok` (`check: 16 file(s); 2 ok, 0 stale, 0 uncovered`). Nothing attaches the id to the symbol it justifies, nothing hashes that symbol, and nothing gates an edit to it. The two comments are `addons/QuestRouter/Core/Decay.lua` line 5, above `local TABLES = {` on line 6 (the Classic decay multipliers the vault snippet 2026-10-23-forever-xp-probe-addon-one-session says the in-game probe should confirm or replace), and `addons/QuestRouter/Game/Pin.lua` line 4, above `local function clearPin()` on line 5 (the clear half of the call sequence in the snippet 2026-10-23-wow-forever-set-clear-user-waypoint; the set half is `pinWorld`, lines 12-18).
2. The vault's freshness rule is time. `staleness` in `bin/lib/stale.mjs` compares `last_verified` to `refresh_after_days` of the entry's `volatility` tier; `schema/taxonomy.json` gives `stable` 1095 days, `slow` 365, `fast` 90, `volatile` 0. Code written against `C_Map.SetUserWaypoint` is not wrong after 90 days; it is wrong when the client's API changes. Of the 21 Forever sources in the vault that carry a `subject.version`, 18 say 1.60.1 (with build 70532, 70425, 70009 or none), the addon's `.toc` declares `## Interface: 16001`, and nothing relates the two.
3. A superseded entry is still `ok` to `check`. `checkCitations` in `bin/commands/check.mjs` returns `stale` or `ok` from `staleness` alone; `verify --result outdated --superseded-by` sets `status: superseded`, but `outdated` is not in `CONFIRMING_RESULTS` (`bin/lib/manifest.mjs`), so `last_verified` does not move. Probed: a source superseded on its capture day is still `1 ok` to `check` (experiment 2026-10-27-probes-second-claims-gate-round-spec). This spec fixes it for code rows, where the decision requires it, and leaves prose rows as they are.
4. The gate's unit is a `data-block`. `unitHashes` in `bin/lib/gate.mjs` splits a lesson by `parseBlocks` and falls back to one unit, `all`, for anything else, so a code file would be re-verdicted whole on every edit.
5. `.research-vault.json` has no place for code. `parseProjectConfig` in `bin/lib/projectconfig.mjs` reads `vault`, `defaults`, `references`, `gates`, `capture` and `taxonomy_extensions`; a hand-added `code` key is dropped silently (probed: the parsed object has no such key). `scaffoldProjectConfig` writes `vault`, `defaults`, `references` and `capture`. `init --project --code-links x` today ignores the flag and writes the standard file (probed).

## Design

### D1. Comment syntax and extraction (`bin/lib/codelinks.mjs`)

One new ESM module, no dependencies, no classes, exporting `LANGS`, `extractCodeLinks(text, lang)`, `unitText(text, lang, declLine)`, `codeUnitHashes(text, lang)`, `readVersions(cfg, repoRoot)` and `checkCodeLinks(links, entries, schema, versions, now)`. `bin/lib/citations.mjs` exports `ID_RE` so the link regex is built from it, not copied. Tests are D6.

**The link.** A vault id on a comment line of its own, optionally glued to a pin:

```
-- Step pin sequence per 2026-10-23-wow-forever-set-clear-user-waypoint@wow=16001
function ns.PinRoute(route, continent)
```

`LINK_RE = new RegExp(`(${ID_RE.source})(?:@([a-z][a-z0-9-]*)=(\\S+))?`, 'g')`: group 1 the id, group 2 a key of `code.versions`, group 3 the pinned version, with trailing `.,;:)` trimmed from the version the way `trimTrailing` in `bin/lib/citations.mjs` trims `.,;:` and a backtick from a URL. The `@key=version` qualifier follows the SWHID shape of `key=value` qualifiers after an identifier (source 2026-10-27-swhid-specification-v1-2-section-6, note 2026-10-27-stable-ids-that-superseded-never-reused), with `@` because `@` is not an id character. Prose around the token is free, so the two existing comments in wow_forever are links already, unpinned. Several ids on one line, or several comment lines above one declaration, are several links to the same symbol; Go likewise allows a repeated `//go:embed` above one declaration, there to avoid very long lines (source 2026-10-27-go-embed-package-docs-go-embed).

**Attachment.** From the comment line, skip following lines that are blank or comments; the first other line must be a column-0 declaration, and its name is the symbol. This is the `//go:embed` rule, only blank lines and `//` comments between directive and declaration (source 2026-10-27-go-embed-package-docs-go-embed), and the Rust outer-doc-comment rule (source 2026-10-27-rust-reference-comments-outer-doc-comments). That is also the whole answer to "the declaration is not on the next line": blank and comment lines may intervene, anything else may not, and a link that reaches no declaration is `unattached`: reported, never dropped, as the Rust reference does not allow an outer doc comment with no item to receive it. The fix for an `unattached` row is to move the comment above the declaration whose unit holds the code (column-0 statements belong to the declaration above them, D4), or to write one link per declaration. A `for:<symbol>` override was in round 1 and is cut: the sixteen files have two indented function declarations and neither is cited, and the override needed its own regex, lookup rule and hash rule; it returns when a real nested citation appears (D8).

**Lua table.** `LANGS.lua`:

```js
comment: /^\s*--(?!\[=*\[)(.*)$/,
decl: /^(?:local\s+)?function\s+([A-Za-z_][\w.:]*)\s*\(|^(?:local\s+)?([A-Za-z_][\w.]*)\s*=(?!=)/,
```

`comment` matches a whole-line short comment and captures its text; the lookahead excludes a line that opens a long comment, `--[[` or `--[=[` (the manual: a comment followed by a long bracket is a long comment that runs to the matching close). `decl` matches `function a.b:c(`, `local function f(`, `local X =` and `ns.X =` at column 0, not `x == 1`, and captures the name in whichever group matched; probed on those inputs in 2026-10-27-probes-second-claims-gate-round-spec and, for `local function` and the two real files, in 2026-10-27-code-links-extractor-prototype-run-wow. Run on the sixteen addon files at ddc5f47 it matches the 105 lines of the count above; run on `Pin.lua` and `Decay.lua` it attaches the two existing comments to `clearPin` and `TABLES` (experiment 2026-10-27-code-links-extractor-prototype-run-wow).

**What it cannot see**, stated in the module header and as negative rows in D6, each probed in 2026-10-27-probes-second-claims-gate-round-spec or in the `Pin6` file of 2026-10-27-code-links-extractor-prototype-run-wow: an end-of-line comment after code (`local x = 1 -- see 2026-...`) is not a comment line and yields no link; an id inside a long comment `--[[ ... ]]`, single or multi-line, yields no link; the inner lines of a long string `[[ ... ]]` look like ordinary lines, so a `-- <id>` inside one is a link and a column-0 `x = 1` inside one is a declaration (the `go generate` scanner has the same blind spot for directive-shaped lines inside multiline strings and documents it; source 2026-10-27-go-command-docs-go-generate-directive); an indented declaration is not a symbol, so a citation above it is `unattached`; `local a, b = f()` and a bare `local pending` are not declarations, so a link above them is `unattached`; an anonymous function assigned to a field, `t.f = function() end`, is seen as the assignment and the symbol is `t.f`; a re-export alias `ns.GrayLevel = grayLevel` is a declaration whose unit is that one line, so the link belongs above `local function grayLevel`; a string literal on a declaration line is not inspected, so `local s = "function fake("` declares `s` and nothing else. The two existing comments are `--`, which is not a LuaCATS `---` annotation (source 2026-10-27-lua-language-server-wiki-annotations-luacats); whether a `---@` tag would be better is open (question 2026-10-27-does-luals-warn-unknown-tag-should).

**Generalisation.** One table per language, as git has one `xfuncname` pattern per language for hunk headers and ships none for Lua (source 2026-10-27-gitattributes-docs-diff-driver-xfuncname-regex). The extractor is language-agnostic; a language is `{ comment, decl }` plus its sample table and negative rows (D6), and none other than Lua ships here. For Zig, zig_book's files open their column-0 declarations with `const` (35), `pub fn` (32), `test` (4), `fn` (3) and `pub const` (2) (snippet 2026-10-27-spec-15-code-links-gate-round), and a Zig `comment` pattern must exclude `///` doc-comment lines the way Lua's excludes a long-comment opener, so a link in a doc comment is not seen. JavaScript and Go rows are not sketched here; they are written from their language references, with their own sample tables, when a project needs them.

### D2. Reverse index: computed by `check`, never stored

`check` already reads every file `references.globs` names; with a `code` block it also reads `code.globs` and extracts links. A code row carries file, line, symbol, id, key, pinned version and status, so "which code depends on entry X" is a filter on `check --json` (code rows join the existing `rows` array with `symbol`, `line`, `key` and `version` fields) or, without the CLI, `grep -rn <id> addons/`. The vault's question, "which code cites me", is the same command run from the repo root, because the feature exists only when the vault lives inside the repo (D7): the vault belongs to the one repo that cites it, and that repo is on disk next to it. A `--cited-by <id>` flag was in round 1 and is cut as a flag with no consumer, the reason spec 14's "Not done here" gives for its own `--json` and `--mermaid` (quoted in snippet 2026-10-27-spec-15-code-links-gate-round).

Persisting the index was considered twice and dropped. In the project, it would be a committed file that drifts from the comments the moment one is edited outside the hook; spec 14 D1 chose "computed on every run, never stored" for the dependency graph for the same reason. In the vault, it would be a write into entries or a sidecar for every code edit, which the decision forbids for existing vaults and which would make the vault's own `lint` depend on a repo outside it. The code is the index. A shared vault cited by several repos has no single place to run the command from and is out of scope.

### D3. Re-check policy: the pin selects the rule

**Where versions come from.** The `code` block declares them:

```json
"code": {
  "globs": ["addons/**/*.lua"],
  "versions": {
    "wow": { "file": "addons/QuestRouter/QuestRouter.toc", "pattern": "^## Interface:\\s*(\\d+)" }
  }
}
```

`readVersions(cfg, repoRoot)` reads each `file` and applies `pattern` as a JavaScript regex with the `m` flag to the whole text; the first capture group of the first match is the key's declared version. `parseProjectConfig` checks that `pattern` compiles and has a capture group; a `file` that is missing or that the pattern does not match is a configuration error (`check` exits 2 with `versions.wow: pattern matched nothing in <file>`), not a row per link. One generic mechanism, no per-format readers, because a `.toc`, a `go.mod` `require` line and `build.zig.zon` hold the version on one line, and `package-lock.json` nests it under `packages[<path>].version`. For the first target it is the `## Interface:` line of `addons/QuestRouter/QuestRouter.toc` (`## Interface: 16001` at ddc5f47, snippet 2026-10-27-research-vault-wow-forever-lines-cited); the note 2026-10-27-where-project-s-installed-dependency-version reports, from an unstored fetch of the TOC format page (source 2026-10-23-wow-toc-format-reference-warcraft-wiki has no stored body), that a `.toc` may list several interface numbers comma-separated, and the pattern yields the first; the number is the client version the addon declares it targets, not the client actually running, and whether the Forever client raises it between builds is open (question 2026-10-27-does-wow-forever-client-change-interface). For other ecosystems, in words rather than untested regexes: npm's `package-lock.json` holds the installed version per path under `packages` (source 2026-10-27-npm-package-lock-json-format-packages), preferred over `package.json` because under Renovate's default range strategy an in-range update changes only the lockfile (source 2026-10-27-renovate-configuration-options-lockfilemaintenance-rangestrategy-fetchchangelogs); a `go.mod` `require` line gives a minimum, and the selected version may be higher (source 2026-10-27-go-modules-reference-go-mod-require; question 2026-10-27-which-version-should-go-code-link); zig_book's `build.zig.zon` carries `.minimum_zig_version = "0.17.0"`, and its template comment describes a dependency's `.hash` field as the source of truth (snippet 2026-10-27-spec-15-code-links-gate-round). `docs/REFERENCE.md` documents the `.toc` example and describes the others in a sentence each.

**The taxonomy.** The re-check policy has two values, `version-change` and `time`, and the link's pin selects between them; no field is added to any entry, the project binding or `schema/taxonomy.json`. Round 1 proposed a `recheck` list with a third value, `both`, in `schema/taxonomy.json`; the reviews showed it had no user (one key, using the default), that `time` on a pinned link means the same as not pinning, and that `init --refresh-docs` copies `schema/taxonomy.json` into every existing vault (`refreshDocs`, `bin/commands/init.mjs`), so the list would have written a changed file into vaults the decision says are not modified. The composition with `volatility`, per link:

- A link pinned to key K (`@K=v`) follows `version-change`: stale iff the declared version of K differs from `v`. It is not time-stale, whatever the entry's `volatility`, with one exception: an entry whose tier is `volatile` (`refresh_after_days` 0, "always re-check") stays always-stale, because that tier is not a calendar, it is a statement that the fact changes without a version. The entry's `volatility` otherwise governs every prose citation of it, unchanged.
- An unpinned link (`<id>` alone, the two existing comments) follows `time`, exactly as prose; it carries no version to compare. Pinning is how an author opts a link into `version-change`, and D5 says when to pin.
- Any link to an entry with `status: superseded` is stale, with `superseded_by` named; editing the id is the fix.

An existing vault sees nothing: no field, no taxonomy value, no entry rewrite, and `lint` is unchanged. `lint --check` on a vault whose entry carries a field the schema does not know was probed anyway (clean, and `lint --fix` keeps the field; experiment 2026-10-27-code-links-baseline-probes-today-s), so an optional entry field remains available to a later spec. `generateAgentsMd` reads four taxonomy keys by name (`volatility`, `stage_by_folder`, `artifact_purpose`, `domain`), and a grep for the iteration forms `Object.keys(t)`, `Object.entries(t)`, `of t)` and `in t)` finds none (snippet 2026-10-27-spec-15-code-links-gate-round), so the golden is untouched by this spec.

**Statuses** of a code row are today's three plus one: `ok`, `stale`, `uncovered` (no entry for the id) and `unattached`. `stale` carries its reason in the tag, where today's rows carry the entry id and volatility: `(time)`, `(superseded by <id>)`, `(wow 16001 -> 16002)` for a pin that differs from the declared version, `(no key wow in code.versions)` for a pin whose key is undeclared. `tally` in `bin/commands/check.mjs` gains the one key, `--check` exits 1 on `stale + uncovered + unattached > 0`. Round 1 had eight status words; each would have been a new tally key, a new term in the exit expression and a new line format.

**Who does what.**

- `check`: it always loads the binding now (today it loads it only when no positional glob is given). A file matching `code.globs`, whether named positionally or found through the globs, goes through `extractCodeLinks` and `checkCodeLinks` only, never through `extractCitations`, in `check`, in the hook and in `evidenceFor`; otherwise the time rule would judge every pinned link through the prose path, which round 1 missed. With no positional globs and a `code` block, the fallback is `references.globs` plus `code.globs`. Output: one line per non-`ok` code row in today's shape with the symbol added (`STALE     addons/QuestRouter/Game/Pin.lua:20 ns.PinRoute  2026-10-23-wow-forever-set-clear-user-waypoint  (wow 16001 -> 16002)`), the summary line gains `, <n> code link(s)`, and when a `code` block exists one footer line `versions: wow=16001` so an author can copy the value (round 1's `--versions` flag is cut; a flag not in `BOOL` in `bin/lib/args.mjs` takes the next token as its value, so `--versions` would have swallowed the glob after it). Without a `code` block, byte-for-byte today's output.
- The post-edit hook (`citationWarnings` in `hooks/post-tool-use.mjs`): the watched set gains the `code.globs` files and the `versions` files. An edit to a code file reports its non-`ok` code rows as `additionalContext`, never blocking, with the same closing line as today. An edit to a versions file reports every link whose pin differs from the version now read from that file; the hook stores nothing between runs, so that comparison is the only one it can make, and it is enough to show the blast radius of a `.toc` bump before the Stop hook does. The versions file itself is never fed to `extractCitations`. The hook is a convenience; `check --check` is the enforcement where a project runs it.
- The Stop hook (`missingGates` in `hooks/stop-gate.mjs`): linked code files join `gatedFiles` (D4), so a code file changed this session whose linked unit has no `PASS` or `MERIT` for its current hash blocks the turn with the same reason text as today, "Gated drafts changed without a claims verdict for their current content:" and one line per file. Second, new: when a `versions` file's mtime is at or after `since` and any link pinned to a key read from it differs from the declared version, the turn blocks with one line per such link (`- <file>:<line> <symbol>: pinned wow=16001, declared 16002; re-verify <id> and move the pin, or capture the new version and replace the id`). This is what makes `version-change` enforced in the first target, whose CI workflow runs luacheck and the addon's own tests and not the plugin (its `ci.yml` is quoted in snippet 2026-10-27-spec-15-code-links-gate-round); it is about five lines in `missingGates`. Staleness of a changed unit blocks through the gate skill's step 0 (D4). An untouched unit linked to a stale entry does not block; it shows in `check`, in the hook and in CI if the project runs `check --check` there.

### D4. Gate: a linked symbol is a unit

`unitHashes(content, lang)` in `bin/lib/gate.mjs` gains a language argument. Its callers in the plugin are `changedUnits` and `recordVerdict` in the same file (a `grep -rn unitHashes bin hooks test` is in snippet 2026-10-27-spec-15-code-links-gate-round; the only other callers are three calls in `test/gate.test.mjs`); both have `repoRoot` and `filePath`, load the binding with `loadProjectConfig(repoRoot)` and pass `LANGS[<ext>]` only when `cfg.code` exists and the file matches `code.globs` (`path.matchesGlob`), else `null`; the test calls pass nothing. With a language, the units are `codeUnitHashes(text, lang)`: one unit `sym:<name>` per distinct declaration that has at least one attached link (a second declaration of the same name in the file gets `#` appended until the key is free; several links above one declaration are one unit), hashed over `unitText`. Without a language, or when a code file has no attached link, the function is today's function and the file is one unit, `all`; round 1 returned `{}` for an unlinked code file, which `gateStatus` would have passed "by unit" forever once any row existed.

`unitText` is the lines from the first line of the contiguous comment block above the declaration to the line before the next column-0 declaration's own leading comment block (or the end of file), trailing blank lines trimmed, joined with `\n`, with the `=<version>` of every pin removed before hashing, sha256 as `contentHash` does today. The prototype run (experiment 2026-10-27-code-links-extractor-prototype-run-wow) shows what the hash sees: moving the whole `ns.PinRoute` block to the end of `Pin.lua` leaves `sym:ns.PinRoute` at the same hash; editing `pinWorld`, a neighbouring function, leaves it unchanged; editing a line inside `ns.PinRoute` changes it; changing only the pin from `@wow=16001` to `@wow=16002` leaves it unchanged; adding a pinned link above the next function, `ns.TogglePin`, and then bumping that pin leaves both `sym:ns.PinRoute` and `sym:ns.TogglePin` unchanged. The pin is outside the hash because a `.toc` bump followed by moving every pin would otherwise cost one reviewer round per linked file, and the check that matters at a bump is on the entry, not the code: D5 says re-verify the entry at the new version before moving the pin, and if the API did change, the new version is captured as a sibling and the old entry superseded, which makes the link `stale (superseded by ...)`, forces the id to change, changes the unit's text and so reopens the unit for the reviewer. Hashing the raw run of lines is the ccache direct-mode trade (the source and include files hashed directly; cheap; a reformat changes the hash; source 2026-10-27-ccache-manual-4-14-input-hash), not the Unison trade, where a definition is identified by a hash of its syntax tree with names stored separately, which needs a parser (source 2026-10-27-unison-docs-each-definition-identified-by; note 2026-10-27-hashing-definition-independent-its-position-unison). Two costs, stated in the module header: because a Lua body ends at its matching `end`, the unit runs to the next declaration, so a column-0 statement between two declarations belongs to the unit above it (an event handler's `f:RegisterEvent` lines belong to the `local f = CreateFrame(...)` above them, which is where the link goes); and a file-header comment contiguous with the citing comment is part of the unit (`Decay.lua` lines 3-5 above `TABLES`), so editing the header re-gates `TABLES`.

`gatedFiles` includes a `code.globs` file only when `extractCodeLinks` finds an attached link in it. `gateStatus` is unchanged: a row for the exact file bytes satisfies it, else every unit covered by some `PASS` or `MERIT` row satisfies it (`by unit`), else the uncovered units are listed; the ledger row shape is unchanged. The first gate round on a file is a bootstrap: with no rows yet, the first edit anywhere in `Pin.lua`, even outside every unit, blocks on `sym:clearPin` until that unit has a verdict; after that, an edit outside every unit passes by unit.

**What the reviewer is handed.** `gate evidence <file> --changed` on a code file prints the entry lines as today, then `changed units: sym:ns.PinRoute`, then one line per changed unit: `unit sym:ns.PinRoute addons/QuestRouter/Game/Pin.lua:20-26 ok` (the range of its text and the worst status of its links, with the stale reason when there is one). The claims-gate skill's step 0 for a code file is read from those lines, not from a whole-file `check --check`: a changed unit with a non-`ok` link stops the gate; an untouched unit's stale link does not, which keeps "an untouched unit does not block" true for a file that holds both. The prompt shape is unchanged (draft path, vault path, the evidence output verbatim). `agents/claims-reviewer.md` gains one paragraph: a `sym:` unit is a code symbol; read the named line range and open the file only to locate it; its claims are the comment's citation and what the code says about the cited entry's subject (a function name and arity, a default value, a limit, a call sequence, an event name); every other symbol in the file carries its earlier verdict or is not gated. Evidence for a code claim is what the agent file already says: a `snippet` for what the code says (the name, the signature, the shape of the call), an `experiment` for what it does (what it prints, which error fires, what a version reports), a `source` or `note` for what the documentation says the API is. A code unit whose call does not match the signature the entry quotes is `contradicted`; a call to an API the entry does not mention is `unsupported` for that call. The reviewer does not compare the pin with the entry's `subject.version`: both existing links cite snippets, which carry no `subject` (`schema/frontmatter.schema.json` lists `subject` under `source` and `note` only; snippet 2026-10-27-spec-15-code-links-gate-round), and the pin's scale (Interface 16001) is not the vault's (the waypoint snippet's signatures are "from the forever branch at 1.60.1 build 70532"); round 1 asked for that comparison and it could only have been a guess.

**MERIT for code.** The same `GATE-LOG.md` entry as for prose, naming the file, the unit and the entry, with the finding and the reason it stands. The expected case in wow_forever: the reviewer asks for an experiment of the in-game call (`C_Map.SetUserWaypoint` returning true), which cannot run on the research machine; the decision records that the snippet's signature matches the call and that the behaviour claim stays with the snippet's own "not yet run in-game" note, and the unit is recorded `MERIT`. A `PASS` needs every claim `supported`; nothing is softened for code.

### D5. Authoring: when the skill fires for code and what it writes

`skills/research-authoring/SKILL.md` gains a section, "Code", that opens by saying it applies only when the binding has a `code` block and the file matches `code.globs`. Two triggers: a declaration being written or changed because of a vault entry (a call sequence from a snippet, a constant from a source, a formula from an experiment), and a version being changed in a `versions` file. What it tells the agent:

1. Search the vault first, as the skill already says; the entry's id is what goes in the comment. Capture first if nothing covers the fact, as today.
2. Choose the key: the entry of `code.versions` whose file declares the dependency the symbol calls (`wow` for a symbol that calls the client API; none for a pure formula such as `TABLES`). Read the declared version from the `versions:` footer of `check`, and write the link as the last comment line above the declaration: `-- <why, in a few words> <id>@<key>=<version>`, or `-- <why> <id>` when no key applies, in which case the link follows the time rule. One link per declaration the entry justifies: a sequence that spans two functions gets two comment lines, which is what the existing `Pin.lua` header should become (one above `clearPin`, one above `pinWorld`).
3. Run `check <file>`; the new row must be `ok`.
4. On a versions-file change (`## Interface: 16002`): for each link the hook or `check` reports, re-verify the entry against the new version (`verify --method tool-probe` or `--method refetched-source`; both are in `schema/taxonomy.json`'s `verification_method`). Confirmed: move the pin to `16002`; the unit's hash does not change and no gate round follows. Changed: capture the new version as its own entry, supersede the old one (`verify --result outdated --superseded-by <new>`), replace the id in the comment, and the gate reopens the unit. Never move a pin without the verify step; the pin says "checked at this version".

### D6. Maintenance: what keeps the links true

In the spirit of spec 14: derived, tested, failures that double as checklists.

- `test/codelinks.test.mjs`: a sample table of one input string per supported form and the link or symbol each must yield (`function ns.X(`, `local function f(`, `local T = {`, `ns.X = function`, `a.b:c(`, a re-export alias, a pinned link, a pinned link with trailing punctuation, two ids on one line, two comment lines above one declaration, a blank line between comment and declaration), and one negative row per "cannot see" item in D1 (end-of-line comment, long comment, indented declaration, id in a string, `x == 1`, `local a, b =`, bare `local x`), run through `extractCodeLinks`. No count floors. The hash invariants are one test built from one inline Lua string, not stored fixtures: base, moved block, neighbour edit, body edit, pin bump, a second pinned declaration below and its pin bump, asserting equal or not equal to the base hash; the eight probe files of the prototype experiment are the record, not the fixture.
- `checkCodeLinks` rows for each status and reason in D3, `readVersions` on a `.toc`, a comma-separated `.toc` and a missing file, `parseProjectConfig` accepting the block on a relative vault and rejecting it on an absolute, empty, `..` or absent `vault` with the message D7 specifies, and rejecting a `pattern` with no capture group.
- Rename of a symbol: the unit id and its text change, so the ledger has no row for it; the Stop hook names the file and `gate changed <file>` names the unit. A deleted link comment: the unit disappears, the file leaves `gatedFiles` if it was the last, nothing else to do. A moved file: `ledgerKey` is the repo-relative path (`bin/lib/gate.mjs`), so verdicts do not follow a rename, the same as for every gated draft today; the fix is one gate round, and the spec accepts it rather than keying the ledger by hash. A removed entry: the vault never deletes, it supersedes; the row says `stale (superseded by <id>)`; the fix is editing the id. A moved vault entry: ids are filenames and never move. A `pattern` that stops matching after a `.toc` reformat: a configuration error that fails `check` and the hook, not a silent `ok`.
- `scripts/deps.mjs` `COUPLINGS` rows, as the `## Rules` of `AGENTS.md` require for a dependency through anything other than a path: `bin/lib/codelinks.mjs` ↔ `agents/claims-reviewer.md` (the `sym:` unit name and the `unit` line format), `bin/lib/codelinks.mjs` ↔ `skills/research-authoring/SKILL.md` (the `<id>@<key>=<version>` form). `LINK_RE` is built from the exported `ID_RE`, an import edge the graph derives, so no row.
- Statuses are the checklist: every non-`ok` row names its own fix in its tag (`-> 16002` means verify and move the pin or replace the id; `superseded by X` means replace the id; `unattached` means move the comment above the declaration whose unit holds the code).

### D7. Opt-in surface and the absent state

**The flag.** `init --project --vault <relative dir> --code-links '<glob>[,<glob>]'` writes the standard binding plus `"code": { "globs": [...], "versions": {} }` and prints one line saying where to add a `versions` key. `init` builds the body and runs it through `parseProjectConfig` before writing, so the one rule lives in one place with one message: a `code` key with `vault` absent, empty, absolute (`path.isAbsolute`) or containing a `..` segment throws `invalid .research-vault.json: code links need a project-specific vault inside the repo (a relative vault path); this binding points at <vault>`, and `init` prints that and exits 1; a `--vault ../Research --code-links ...` is caught the same way. The relative path is what `resolveVault` resolves under the config file's directory (`bin/lib/resolve.mjs`: "A relative vault … is relative to the config file's directory"). `code.globs` must be an array of strings; `code.versions` an object of `{ file, pattern }` with `pattern` compiling and holding a capture group. Two limits, stated: a relative path that is a symlink out of the repo passes the parse-time rule, so `check` and the hooks also refuse code rows (exit 2, one line) when `realpath(vault)` is not under the repo root; and `--code-links` goes through `csvList`, the same splitter `init --project --globs` uses, so a brace glob with a comma must be two globs. A malformed `code` block throws from `parseProjectConfig` like a bad `defaults.volatility` does today; `resolveVault` reads the binding (`readProjectConfig`) on every command run without `--vault`, so such a command in that repo fails at the binding read until the file is fixed, and the Stop hook's `catch` writes its `systemMessage` ("research-vault: stop-gate skipped (...)") instead of a decision. That is today's contract for the file and this spec keeps it.

The returned config carries `code` only when the block is present; every consumer tests `cfg.code` and does nothing without it. Removing the block removes every behaviour; the comments the author wrote are ordinary comments again, and `check` on a Lua glob reads them as it does today. The `--vault` flag still overrides the binding on every command, as it does today; code rows are then judged against whatever vault the flag names.
