# Reference

The README explains what research-vault is. This page is for looking things up. It is a command overview with the flags you'll actually reach for. Running `research-vault` with no arguments prints the command list.

## Scope

research-vault is for *external* facts: documentation, API behaviour, tool-version claims and the decisions you made because of them. It is not a code indexer beyond the comments that cite the vault, and does not replace the agent's view of your repo. Without Node, an agent can still read a vault by globbing and grepping the folders; the CLI is the checked path.

## Releases

`.github/workflows/release.yml` runs after the `ci` workflow completes. Only a successful push run on `master` in `andrew-brooks-GA/research-vault` can release; pull-request runs cannot. Checkout and the release target use that CI run's `head_sha`. `package.json` and `.claude-plugin/plugin.json` must carry the same non-empty version. The plugin's entry in `.claude-plugin/marketplace.json` must match that version only when it carries a version; an absent marketplace version is accepted and logged. After that check, an existing `v<version>` release ends the job successfully; otherwise the job creates it using the nonempty matching section of `CHANGELOG.md`. This check runs after every eligible CI completion, even when `package.json` did not change.

GitHub uses the default branch's copy of a `workflow_run` workflow. Changes on another branch therefore need their first live verification after reaching `master`.

## Where the vault lives

Tooling and vault data are separate by default. The vault is discovered in order:

1. `--vault <path>` flag
2. a repo's `.research-vault.json` (project binding, subject to the discovery rule below)
3. `$RESEARCH_VAULT_PATH`
4. the config pointer `init` writes when it sets the default vault (first `init`, or `--set-default`)
5. the OS default: `$XDG_DATA_HOME/research-vault` (else `~/.local/share/research-vault`) on Linux, `~/Library/Application Support/research-vault` on macOS, `%LOCALAPPDATA%\research-vault` on Windows

Run `init --project` at the root of a repo to write `.research-vault.json` there, and commit it. From then on:

- **Discovery.** The CLI finds the nearest binding by walking up from the working directory. A relative `vault` is relative to the binding's folder. An acknowledged binding may name a vault anywhere; run `research-vault trust` in that project to approve it (`init --project` acknowledges the binding it writes). Otherwise the vault must resolve inside that folder or to one of the user's own locations (`RESEARCH_VAULT_PATH`, the config pointer or the OS default). An unacknowledged binding naming an outside vault that is not one of those choices is refused without falling back. A command whose bound vault is refused reports the binding path on stderr and exits 2. The hooks skip work that depends on that vault; the Stop hook reports the skip and does not block. `--vault` bypasses vault discovery, but `check`, `embed` and `search --semantic` still load the binding and exit 2 if it is not valid JSON; plain `search` ignores that binding error and exits 0. The plugin takes `RESEARCH_VAULT_PATH` as the user's choice. Absolute binding paths whose first two characters are each `/` or `\` are compared with those choices by normalized spelling; other paths use resolved locations, including missing tails after an existing prefix. With no `vault` in the binding, discovery continues with the environment variable, config pointer and OS default. For discovery the binding selects the vault; what an agent does with it comes from the vault's `AGENTS.md`.
- **`research-authoring`.** When a citation is about to land in prose you're writing in the repo, the skill tells the agent to search the vault first, check a found entry's freshness, capture what the vault is missing, and run `check` on the file after writing.
- **`check`.** Audits the repo's docs against the vault; each citation is `ok`, `stale` or `uncovered`. `check --check` exits non-zero so CI can fail on stale or uncovered citations, or on a glob that matches no file.
- **Gate.** Lessons, reference docs and the `README.md` of every teach workspace (a directory holding `MISSION.md`) found under the repo are gated, plus any file matching the optional `gates.globs` array in `.research-vault.json`, for example `"gates": { "globs": ["docs/**/*.md"] }`. The `research-claims-gate` skill records each `PASS` or `MERIT` verdict with `gate record` in `.research-vault-ledger.jsonl` at the repo root, keyed to the file's content hash and to a hash per unit, so an edit that changes a unit needs a new verdict for that unit, while an edit that leaves every unit's hash unchanged keeps the earlier verdict (`(by unit)`). `gate evidence` ends with a `review hash: <hash>` line, the sha256 of what a row for the file would store (its content hash and every unit hash, so an image, a loaded script or a requirements file too), and the skill records with `gate record <file> <verdict> --expect <hash>`, which exits 1 with one line on stderr and appends nothing when that hash has changed since; a row recorded without `--expect` carries `"manual": true`, which no verdict check reads, so it and every earlier row count as before. The row also carries `reviewer`, the sha256 of the plugin's `agents/claims-reviewer.md`, and counts only while that hash is absent (no reviewer hash was recorded) or equal to the installed reviewer's; after a change to the agent file, `gate status` prints `none (reviewer changed)` for a file whose passing rows all came from the earlier one. When the changed units of a file with no verdict cite ids the bound vault does not hold, `gate status` and `gate staged` also print how many, as in `none (2 cited ids not in this vault)` or `none (reviewer changed; 2 cited ids not in this vault)`, and the Stop hook's line for that file begins with the count: a reviewer reading those units here finds no entry for those ids until the evidence is rebuilt in this vault. A lesson's units are its `data-block` elements (the fact block per paragraph, the quiz per item; every repeated block, including fact and quiz, gets a whole-inner-HTML `<name>#N` unit with the first available `#2`, `#3`, … suffix that is not a real block name), `rest` for all remaining page markup and text (including block tags and attributes, and canonical quiz JSON with items replaced by markers), `script:<src>` for each loaded local script in the served workspace folders `lessons/`, `reference/`, `assets/` and `brand/` (the resolved workspace-relative path plus file bytes, or a distinct missing-file marker with the path; repeated tags get suffixed names too) and one `img:<src>` per `<img>`, hashed over its `<figure>` and the image file's bytes (a change to the file alone reopens only that unit, and a caption or alt change also reopens the data-block holding the figure, or for a `fact` block the paragraph holding it (a figure between `fact` paragraphs also reopens `rest`); a changed image file leaves its page without a verdict in `gate status`, a staged image file puts its page, when git tracks it, in front of `gate staged`, also when the file is gone from the working tree though not when its deletion is staged, and a changed one puts its page in front of the Stop hook only while the file still exists, so the hook does not see a deleted one); a Markdown file's (a path ending in `.md`, cut this way whatever HTML it quotes, `data-block` attributes included) are its ATX (`#`) heading sections (`sec:<slug>`, `sec:preamble` before the first heading) and each table row of one (`sec:<slug>/<first-cell slug>`, so a one-row edit reopens only that row), and `gate evidence --changed` prints `unit sec:<slug> <file>:<start>-<end> prose` for each changed one so the reviewer reads only those, and lists only the citations inside those units, plus `--extra` (a changed row with none takes those of its section's lines outside rows; a changed unit with none, or no changed unit, gives the whole file's); a file with neither is one unit, `all`. A script unit is satisfied when a passing row covers its hash or its bytes equal the plugin's current `skills/research-teach/<path>` copy; a passed older workspace copy remains satisfied after a plugin upgrade. An exact-page-byte legacy row without a script hash leaves that script pending unless it equals the current shipped copy. Local script files also select their pages: for `gate staged` (pages git tracks) when staged, present in the working tree or not, and for the Stop hook when they exist and changed. A checked task's lesson hashes its `step` unit over the block and the bytes of `evidence/NNNN/requirements.json`, where NNNN is the lesson's number. A requirements file that resolves outside the workspace or cannot be resolved is treated as absent. An edit to that file reopens only the `step` unit and leaves the lesson without a verdict in `gate status`, unless the lesson's passing row was written before rows held a hash per unit. A staged requirements file that resolves inside the workspace puts its lesson, when git tracks it, in front of `gate staged`, present in the working tree or not, and a changed one puts it in front of the Stop hook only while it exists and resolves inside the workspace. Unless a binding or versions-file refusal causes it to report a skipped gate without blocking, the Stop hook blocks a turn that leaves a changed gated file without a `PASS` or `MERIT` verdict for its current content (a row for those exact bytes while no image it references or requirements file of the lesson has changed, a requirements file change aside for a row written before it held that unit, and each local script has bytes passed in a row or equal to the plugin's current copy, or every unit covered by some row or that script exemption). After an edit to a gated file or one matching `references.globs`, a hook reports its uncovered or stale citations without blocking, unless a binding or versions-file refusal makes it skip that advice; an edit inside the vault runs `lint --fix` instead, so this applies to files outside the vault. `gate status <file> --check` exits 1 when the current content has no passing verdict; `gate staged --check` does the same for the staged content of every gated file staged in git, one line per file, for a pre-commit hook (the plugin repo ships one in `.githooks/`), and a page whose referenced image, loaded local script or requirements file differs between the index and the working tree, or is untracked, has no verdict there, and its line reads `none (<repo-relative path>: staged and working copies differ)`. With no `.research-vault.json` in the working directory or above it, `gate staged` (with or without `--check`) prints `staged gated files: none (no .research-vault.json binding here, so nothing is gated)` to stdout and exits 0. An entry of that name that cannot be read (including a broken link), invalid binding JSON, a refused vault, a git repository that cannot be inspected, or a staged file git cannot read still reports an error on stderr and exits 2. A vault entry outside any bound repo can be gated too; its ledger lives in the vault.
- **Embedding endpoint.** `"embedding": { "url", "model"?, "chunk"?, "overlap"? }` (defaults 800 and 100) turns on `embed`, which writes the disposable index `_index/embeddings.jsonl` from every non-superseded entry's windows, and `search --semantic`; both need `RESEARCH_VAULT_ALLOW_NETWORK=1`, `--ack-data-egress` and `RESEARCH_VAULT_EMBED_URL` matching `embedding.url` after URL parsing. The endpoint must use HTTPS or loopback HTTP and have no user-info. Requests refuse redirects. After argument checks (`search --semantic`) and binding loading (an error exits 2), the embedding gate reports its first refusal on stderr and exits 1, in this order: no embedding block, missing network opt-in, missing acknowledgement, user-info in the URL, missing or mismatched endpoint approval, then non-loopback HTTP. These checks precede vault discovery and text collection. The plugin takes the approval variable from the environment as the user's choice; URL parsing ignores scheme and host case, a default port and an empty path. See [SECURITY.md](../SECURITY.md#embedding-endpoint-embed-search---semantic) for the exact diagnostics. Without the block, both refuse (`no embedding endpoint in .research-vault.json`) and no index is written.
- **Lab.** An optional `"lab": { "docs", "uses", "bypass" }` block, each a non-empty array of non-empty strings, for example `"lab": { "docs": ["LAB.txt"], "uses": ["lab/lib.sh"], "bypass": ["kind create cluster"] }`. `docs` lists the files that explain the repo's lab, relative to the directory holding `.research-vault.json` (an absolute path or a `..` segment is rejected); `uses` and `bypass` are literal strings, not patterns. With the block, `teach lint` reads every `.sh` file under the workspace's `labs/`, `evidence/` and `lessons/` and reports the advisory `WARN_LAB_BYPASSED` for a file that holds a `bypass` string on a non-comment line, quoted strings read as empty, and no `uses` string outside a comment or an `echo` line, unless the file is under `evidence/NNNN/` or `lessons/files/NNNN-` and `evidence/NNNN/PLAN.md` has a line starting `own environment: <reason>`; a script under `labs/` is never silenced (LESSON-FORMAT.md has the rule). Plugin version 0.11.0 is the first that reads the block; 0.9.0 (the older version run) drops it silently, as it drops a misspelled key. A malformed block throws `invalid .research-vault.json: lab ...` (`lab must be an object`, or `lab.<field> ...`): a CLI command that resolves its vault from the binding exits 2, while the hooks catch the error and carry on.
- **Usage log.** `_index/usage.jsonl` in the vault, one JSON object per line: a `queried` event from the pre-web hook (the tool, the outcome `url-hit`, `hits` or `no-match`, the ids surfaced) and from `search` (the `--type` and `--topic` facets, the outcome, the ids returned), and a `cited` event per id a watched file newly cites, from the post-edit hook (the file's repo-relative path and the id; the log itself is the record of what was already logged). An append requires the log and its directory to resolve inside the vault. Ids, facets and the outcome are always written; free text (the pre-web terms, the `--text` value) only when the binding sets `"usage": { "text": true }`. The template's `.gitignore` already ignores `_index/`; if a vault's `.gitignore` lacks the line, add it. `advise` reads the log for its usage section and skips a line that is not JSON.

### Code links

A vault id on a comment line of its own, above a column-0 declaration, cites that entry for the symbol below it. The id may carry a pin, `<id>@<key>=<version>`, naming a key of `code.versions` and the version the code was checked against:

```lua
-- Sleep-mode call order per 2026-03-03-sleep-mode-api@sdk=0.20
function ns.Sleep(frame)
```

Blank and comment lines may sit between the comment and the declaration; several ids on one line, or several comment lines above one declaration, are several links to the same symbol. A link whose next non-blank, non-comment line is not a column-0 declaration is `unattached`: reported, never dropped.

**Opt-in.** `init --project --vault <relative dir> --code-links '<glob>[,<glob>]'` writes the standard binding plus a `code` block, and a `code` block written by hand into an existing binding is the same opt-in. The block is accepted only on a relative `vault` inside the repo: an absolute, empty, `..` or absent vault is rejected with `code links need a project-specific vault inside the repo (a relative vault path); this binding points at <vault>` (`(none)` when the vault is empty or absent). Without the block, `check`, the gate and the hooks take today's code path and the comments are ordinary comments. Windows cmd.exe keeps single quotes, so there write `--code-links "src/**/*.js"`; a glob that starts or ends with a quote is refused by `init` and `check` with exit 2.

```json
"code": {
  "globs": ["src/**/*.lua"],
  "languages": {},
  "versions": {
    "sdk": { "file": "package-lock.json", "pattern": "\"node_modules/sdk\": \\{\\s*\"version\": \"([^\"]+)\"" }
  }
}
```

- **`versions`.** Each key names a `{ file, pattern }`. The binding rejects an empty or absolute `file`, a drive specifier or a `..` segment. Before reading, `check` follows links and requires the file to resolve inside the repository. The pattern is a JavaScript regex applied with the `m` flag to the whole file; the first capture group of the first match is the declared version. An out-of-repository or unresolved file makes `check` print `error: versions.<key>: <file> resolves outside the repository` on stderr and exit 2; the post-edit hook skips its stale-link advice if this reader fails. A file that is missing or that the pattern does not match is a configuration error (`check` exits 2 with `versions.<key>: cannot read <file>` or `versions.<key>: pattern matched nothing in <file>`), not a row per link. `package-lock.json` nests the installed version under `packages[<path>].version`. One-line forms: the `## Interface:` line of an addon `.toc`; a `go.mod` `require` line, which declares a minimum version while the selected version may be higher; a `.minimum_zig_version` line in `build.zig.zon`. `check` prints the values it read as a footer, `versions: sdk=0.20`.
- **`languages`.** A language is `{ comment, decl }`, two regex sources: `comment` matches one whole comment line and captures its text in group 1; `decl` matches one column-0 declaration line and captures the symbol name in its first non-empty group. Each must compile and hold a capture group, else the error names the field (`code.languages[".py"].decl: pattern has no capture group`). The plugin ships rows for `.lua`, the JavaScript and TypeScript family (`.js`, `.mjs`, `.cjs`, `.jsx`, `.ts`, `.mts`, `.cts`, `.tsx`), `.py`, `.go`, `.rs`, `.zig`, `.rb`, `.sh`/`.bash` and C/C++ (`.c`, `.h`, `.cpp`, `.hpp`, `.cc`, `.hh`); each sees only column-0 declarations, so a method inside a class body, or a decorator or attribute line between the comment and its declaration, is not seen. The Lua row:

  ```js
  comment: /^\s*--(?!\[=*\[)(.*)$/,
  decl: /^(?:local\s+)?function\s+([A-Za-z_][\w.:]*)\s*\(|^(?:local\s+)?([A-Za-z_][\w.]*)\s*=(?!=)/,
  ```

  A project adds any other language as a row keyed by extension in `code.languages`, and may override a shipped row; a `code.globs` file whose extension has a row from neither is a configuration error, `no language for .kt in code.globs; add code.languages[".kt"] = { comment, decl }`. `comment` is matched line by line, so a block-only comment syntax needs a line prefix inside the block.
- **Statuses.** A code row is `ok`, `uncovered` (no entry for the id), `unattached`, or `stale` with its reason: `(time)` for an unpinned link whose entry is past its volatility window, or a pinned link to a `volatile` entry; `(superseded by <id>)` for an entry with `status: superseded`; `(<key> <pinned> -> <declared>)` for a pin that differs from the declared version; `(no key <key> in code.versions)`. A pin selects the version rule over the time rule; an unpinned link follows the entry's window as prose does. `check --check` exits 1 on any `stale`, `uncovered` or `unattached` row, or when a glob matches no file.
- **Gate.** Each linked declaration is a unit, `sym:<name>`, hashed from its leading comment block to the line before the next column-0 declaration's comment block, with pin values stripped, so moving the block, editing a neighbour or moving a pin reopens nothing and editing the body does. Code files with an attached link are gated like `gates.globs` files; `gate evidence <file> --changed` adds one line per changed unit, `unit sym:<name> <file>:<start>-<end> <status>`, which the `claims-reviewer` reads as its line range. Unless a binding or versions file is refused, the post-edit hook reports a code file's non-`ok` rows and, after an edit to a `versions` file, every link whose pin differs from the version now declared. The Stop hook also blocks a turn in which a `versions` file changed and a link is still pinned to another value, naming the link and the two versions; if a binding or versions file is refused, it reports a skipped gate and does not block.

## Extending the controlled vocabulary

The schema enums are small on purpose. A vault that needs its own terms (a lab recording `lab-run` as a verification method, a team with an extra `domain`) adds them in `.research-vault.json`:

```json
{
  "vault": "research",
  "taxonomy_extensions": {
    "verification_method": ["experiment", "lab-run"],
    "verification_result": ["partial"],
    "topic_aliases": { "k8s": "kubernetes" }
  }
}
```

- **Additive only.** You can add values, never remove or redefine a built-in, so entries stay portable between vaults.
- **Extensible fields:** `domain`, `confidence`, `outcome`, `question_state`, `verification_method`, `verification_result`. `volatility` and `stage_by_folder` are not extensible, and `topics:` already accepts any tag.
- **`topic_aliases`** is a map of vault pairs, alias to canonical topic, merged after the built-in pairs; a pair whose key is a built-in alias is refused. `capture`, `lint`, `advise`, `search` and `teach path candidates` all read the merged map, and `lint --fix --topics` rewrites existing entries.
- **Keyed on the vault**, not your shell's working directory, so the vocabulary is the same wherever a command runs.

To change the built-in vocabulary itself, edit `schema/taxonomy.json`. The linter, `capture`, the generated `AGENTS.md` and each vault's copied `taxonomy.json` all derive from it.

## Freshness

Each entry has a `volatility` tier with a review interval. An entry is stale when its last confirming verification is older than the interval.

| tier | covers | interval |
|---|---|---|
| `stable` | fundamentals, algorithms, classics | 3 years |
| `slow` | established practices, mature frameworks | 1 year |
| `fast` | specific tool APIs, framework versions, LLM capabilities | 90 days |
| `volatile` | pricing, rate limits, current best model, availability | always re-check |

A note or synthesis is only as fresh as its evidence; `advise` reports conclusions whose source chain reaches a stale or replaced entry.

## Versions and replacements

These are different things:

- **A new version of a tool is new knowledge, not a correction.** `vcluster 0.19` and `0.20` are two active entries sharing a `series`. Record this with `verify --succession` on the older entry, then capture the newer version as its own source with `--subject-name`, `--subject-version` and `--series`.
- **A replacement is for an entry that is wrong or obsolete.** Capture the corrected entry first, then `verify --id OLD --method <method> --result outdated --superseded-by NEW`. The old entry stays on disk with `status: superseded`; `search` hides it unless `--include-superseded`, and `related` still shows it so the evidence trail stays visible.

## Entry types and the graph

| Folder | Holds | Create one when |
|---|---|---|
| `sources/` | Raw captures of external material, as-is | you clip something worth keeping |
| `notes/` | Your distilled take on one or more sources: the load-bearing claims and how you'd use them | you read a source and want a durable, skimmable version |
| `synthesis/` | Conclusions drawn across several entries | you see a pattern worth stating once |
| `snippets/` | Reusable code or prompt fragments | you have a fragment you'll reuse |
| `experiments/` | Logged trial runs with task, parameters and outcome | you run a trial worth recording |
| `questions/` | Open questions (`open → investigating → answered`) | you hit something to track and answer over time |

Distillation (source → note → synthesis) is a deliberate step; nothing auto-promotes. A synthesis usually cites notes, and may also cite sources, experiments, questions and snippets directly; a factual rollup (a release-note matrix, a version diff) may skip notes if it declares `synthesis_basis: primary-rollup`.

Stored references point from the declaring entry to what it references:

```mermaid
flowchart LR
  note -->|"sources"| source
  synthesis -->|"contributing_ids"| note
  snippet -->|"source_id"| source
  experiment -->|"prompt_id"| snippet
  question -->|"contributing"| any
  any -->|"related"| any
  any -->|"superseded_by"| any
```

`.vault-manifest.json` lists every reference as a typed edge and inverts the backlink-forming ones. Each vault's generated `AGENTS.md` §5 documents the fields and §5.2, Asking the graph.

### Reading the graph from outside

A project that keeps its own graph (a code dependency map, a Neo4j load, a Graphviz script) does not need the plugin's view of it. Two outputs carry everything, both plain JSON, neither stored in git, so run the command first:

- **The vault graph**: `lint` writes `<vault>/.vault-manifest.json` with `generated`, `entries`, `edges` and `backlinks`. An entry row has `id`, `type`, `title`, `summary`, `domain`, `topics`, `source_url`, `content_hash`, `volatility`, `last_verified`, `status`, `subject`, `series`, `stage`, `state`, `confidence`, `outcome`, `authority_tier`, `authority_basis`, `superseded_by`, `related`, `contributing_ids` and `sources`; an absent field is `null` or `[]`, never missing (`status` defaults to `active`). An edge is `{ from, rel, to }` with `rel` one of the reference fields above, sorted by `from`, `rel`, `to`. `backlinks` maps an id to the sorted ids that reference it through a backlink-forming field. Bodies are not included: the id is the filename under the type's folder.
- **The code edges**: `check --json` from the repo root prints `generated`, `summary`, `rows`, `skipped` and, with a `code` block, `versions`. A code row has `file`, `type`, `value`, `symbol`, `line`, `key`, `version`, `status` and, when covered, `id` and `volatility`, plus `reason` when stale; a prose row has `file`, `type`, `value`, `status` and, when covered, `id` and `volatility`. Join a row's `id` to an entry's `id` and the code side of the graph is complete.

These keys are the integration contract: `test/contract.test.mjs` pins them, and a change is a breaking one in the CHANGELOG. `examples/graph-dot.mjs` is the join written out as Graphviz DOT, and `examples/blast-radius.mjs` is the other direction: given the manifest, one entry id and one or more `check --json` outputs, it walks the `sources` and `contributing_ids` edges inward and prints the entries that rest on the id and every row that cites one of them, which is what to re-check when the entry is superseded; [ADOPTING.md](ADOPTING.md) is the ordered walkthrough for a new project.

Two facet tiers keep retrieval clean as a vault grows: **`domain`** is a small controlled set of broad areas (`software-engineering`, `systems-infrastructure`, `data-ml`, `security`, `learning`, `llm-assisted-dev`, `meta`, `natural-science`, `humanities`, `business-finance`, `health-fitness`, `language-learning`, `arts-crafts`); **`topics`** is freeform and is where specific tech lives.

## Commands

Run as `node bin/research-vault.mjs <command>` from a clone, or `research-vault <command>` if you've put it on your PATH. Every command takes `--vault <path>`. For example:

```text
research-vault capture --type source --title "vcluster sleep mode" \
  --url https://example.org/sleep-mode --domain systems-infrastructure \
  --topics kubernetes,vcluster --subject-name vcluster --subject-version 0.20
research-vault search --topic vcluster
research-vault verify --id <id> --method refetched-source --result confirmed
```

These guarantees are about the CLI. The agent hosting it may search or fetch the web on its own; that is governed by the agent, not by this tool.

- The path checks in this document have the conditions and limits in [SECURITY.md](../SECURITY.md#threat-model-in-one-line). The ingest writes entries, and the fill, which also needs `--ack-data-egress`, writes a page's text into an existing source. `refresh` fetches a source URL, compares content hashes and never stores the page; `verify --quotes` compares a fetched page in memory and writes verification rows, plus `updated` when it adds a row for a quote found on the fetched page; the body and `content_hash` are never changed. **`gate evidence --packet <dir>`** opens no connection and writes a copy of the listed entries into a directory outside the vault, in which the stored text of each source over 8,000 bytes that holds quote rows of the run is cut to excerpts and every other entry is copied whole. **`export`** writes JSONL to stdout or to `--out`; titles and summaries export freely, full bodies need `--include-bodies --ack-data-egress`. Neither `refresh` nor `export` modifies entries. **`teach serve`** listens on `127.0.0.1` only and writes nothing but attempt files and `.teach-serve.json`, checking their resolved destinations in the teaching workspace it serves. With `--labs` it also runs the lab scripts the workspace pins, which write wherever they write, and with `--terminal` it serves a shell, whose commands write wherever they write.

The full contract, including SSRF hardening, is in [SECURITY.md](../SECURITY.md).

## Team use

## Design notes

- **Cache, not source of truth.** The design treats staleness as the main risk of agent research; the vault makes it visible and actionable.
- **Lint is the guarantee, not the hook.** Correctness lives in `lint`, which runs anywhere on any writer. The plugin's four Claude Code hooks (a post-edit lint-fix, a session-start summary (`research-vault: N entries; M stale; <path> (<origin>)`, with `project` for the binding, `env` for `RESEARCH_VAULT_PATH`, `config` for the config pointer and `default` for the default folder; control and format characters in the path are escaped), a pre-web-fetch vault lookup that hands matching entries to the model before it searches and names a blocklisted URL's reason before a fetch, and a Stop gate that blocks a turn leaving a changed gated draft without a verdict, or reports a skipped gate without blocking when a binding or versions file is refused) are conveniences. Session-start and pre-web stay silent and write nothing when the selected folder has neither a vault marker nor an entry; an empty initialized vault still gets its summary.
- **The vault's agent-facing files are generated.** `AGENTS.md` and each vault's `taxonomy.json` come from the schema at `init`; CI checks the generator against `schema/AGENTS.golden.md`.
- **Orchestration is a reference implementation with a contract.** `research-orchestrate` drives vault-first research with eager source capture and a batch for the distilled layers; other orchestrators compose the same way. See [ORCHESTRATOR-INTEGRATION.md](ORCHESTRATOR-INTEGRATION.md).
- **Migrating existing notes?** See [MIGRATION.md](MIGRATION.md).

## Resumable capture (opt-in)
<!-- evidence: 2026-11-17-capture-operation-lines-research-vault-issue 2026-11-17-probe-capture-verify-capture-operation-gate 2026-11-17-second-probe-log-capture-verify-writes -->

Use `capture --batch <absolute-plan.json> --operation-id <key> --vault <absolute-vault>` for an immutable JSON-array batch. Retain the original plan, referenced files and key; resolve relative `contentFile` paths against the plan directory. Keys contain 1–128 ASCII letters, digits, underscores or hyphens. This mode rejects ingest inputs and `--continue`; source-body consent still requires `--ack-data-egress` when a spec requests `storeBody`.

Receipts live in `.capture-operations/<key>.json`. The output is one JSON object with `created`, `skipped`, `errors`, `recoveryStateCreated`, and operation metadata when available. Exit 0 means complete persistence (or historical replay), 1 means a validation/conflict/storage/finalization failure, and 2 means an invalid CLI combination. Persistence does not certify research verification or a claims verdict.

Replay incomplete operations with the identical plan, inputs, semantic options and key. The writer freezes the date and prepared fingerprints; changed inputs/schema fail. Completed receipts return `replay=true, historical=true` without checking current artifacts: validate current artifacts separately before claiming current completion. See [recovery details](RELIABILITY.md). Legacy capture remains available to external orchestrators; adopting operation keys is optional.
