# Orchestrating research into the vault
<!-- evidence: 2026-11-17-document-lines-research-orchestrate-skill-names -->

The reference implementation of `docs/ORCHESTRATOR-INTEGRATION.md`. Durable conclusions land as atomic vault entries — sources, notes, questions, snippets, experiments, synthesis — never as a monolithic report. Reports are views; the vault is the system of record.

## Invariants

Keep these after a compaction; the section named holds the detail.

- Check the vault first: search it before any web research, and when fresh entries cover the question and no covering `source` is unverified, answer from the vault and stop (§1).
- Append `--vault <absolute vault>` to every CLI call, including reads (§0).
- The Recon and Research workers write no entry; only the Write step writes to the vault, one command at a time. Run no two captures at once on one vault (§0, §2).
- Run `capture --fill` only if the user agreed to store page text (§1, §2, §3).
- A returned id is not evidence that anything was captured: confirm each id is a file in the vault, then run `lint` with the explicit vault: clean, or explain every warning (§4, Close out).
- Run the `research-claims-gate` skill on the synthesis entry file before you present it to the user (§4, Close out).
- Close a question with `verify --id <question> --answered-by <synthesis id>` only after the gate records `PASS` or `MERIT`; if the gate does not pass, show its verdict and leave the questions open (§4, Close out).
- Offline or fetch-blocked, do not fabricate: answer from the vault and record what could not be verified as open `question` entries (§4, Close out).

## 0. Resolve paths once
<!-- evidence: 2026-11-17-cli-lines-behind-research-orchestrate-skill 2026-11-17-document-lines-research-orchestrate-skill-names 2026-11-17-probe-cli-behaviour-research-orchestrate-skill 2026-11-17-third-lines-behind-research-orchestrate-skill -->

- CLI: `node "${CLAUDE_PLUGIN_ROOT}/bin/research-vault.mjs"`. Resolve `${CLAUDE_PLUGIN_ROOT}` to an absolute path now — do not rely on workers inheriting it.
- Resolve the selected vault to an absolute canonical path once. Pass both CLI and vault explicitly to every worker; append `--vault <absolute vault>` to every CLI call, including reads. Vault path resolves in order: `--vault` flag → the repo's `.research-vault.json` binding (which outranks the env var) → `$RESEARCH_VAULT_PATH` → the global config pointer → the OS default (see "Where the vault lives" in `docs/REFERENCE.md`). A binding can name a vault outside its folder when acknowledged with `research-vault trust` (`init --project` acknowledges the binding it writes), or when it matches the user's `RESEARCH_VAULT_PATH`, config pointer or OS default under the [binding rule](../../SECURITY.md#repository-bindings). If discovery refuses the binding (exit 2), report it and stop before dispatching workers; do not copy its raw vault value into `--vault` or set `RESEARCH_VAULT_PATH` to bypass the refusal.
- Make a run key now, new for every run and reused only to resume that run: `run-` and six or more letters or digits, for example `run-apfk3x`. It names the run's plan files and capture operations. It is not shaped like an entry id, and it never appears in an entry's body: the citation check reads a `<date>-<slug>` in prose as an entry id.
- Today's date for `args.today` is the UTC date, `YYYY-MM-DD`: the CLI dates entries in UTC, and the Write step builds ids from it.

You, the session running this skill, are the controller: the Recon and Research workers search, fetch and read, and return what they found without writing an entry; only the Write step writes to the vault, one command at a time. Source captures run outside the capture lock, so run no two captures at once on one vault.

## 1. Clarify, then check the vault first
<!-- evidence: 2026-11-17-cli-lines-behind-research-orchestrate-skill 2026-11-17-document-lines-research-orchestrate-skill-names 2026-11-17-probe-cli-behaviour-research-orchestrate-skill 2026-11-17-third-lines-behind-research-orchestrate-skill -->

1. If the question is underspecified (no version, environment, or success criterion), ask 2–3 narrowing questions before researching.
2. Search the vault (`search --topic`, `--text`, `--body`). If fresh entries (per §2 of research-vault-usage) already cover the question and no covering `source` is unverified (`advise` lists it under unverified sources, or every method in its `verifications` is `captured` or `quote-matched`), answer from the vault and stop; otherwise treat it as partial coverage. If coverage is partial, note the gap — it becomes a `question` entry or the workflow's focus.
3. Interview the user once, before any agent starts, in one set of questions:
   - **Kinds of source** (`args.lanes`, any number; each kind chosen is one lane). Offer every kind that could bear on the question and recommend the widest set that fits it: official documentation and standards; published style guides, books and long-form writing by recognised practitioners; community posts, practitioner writeups and critiques; release notes and changelogs; issue trackers and bug reports; peer-reviewed empirical studies. Add a kind the question calls for that is not in this list.
   - **Breadth** (`args.pagesPerLane`): two pages a lane, or four. Say that the wider run costs more: every further page is read by a lane agent and its quotes are checked and judged by the Write agent.
   - **Page text** (`args.storeText`): may this run store the text of the pages it reads in their source entries? Stored text lets the claims gate read the page, and it is a copy of someone else's page in the vault.

   Word `args.question` to ask what those kinds of source say. Do not add a requirement the user did not state, such as that a practice must rest on a measurement: what a style guide, a book or a tool's documentation recommends is a finding, reported with who makes it. With no user to ask (a subagent, a headless run), pass every kind listed above, two pages a lane, and `storeText` `false`.

## 2. Run the workflow

Use the Workflow tool with the reference script below, adapted to the question. Pass absolute paths and the run key via `args` — never rely on env vars inside the script. A returned object that matches a schema is not evidence that anything was captured or checked: ids come from the capture output, and section 4 checks them.

A run that reaches the Write step starts two agents plus one per lane. Every `agent()` call in the script names its model, `model: 'opus'`, the model the claims reviewer is pinned to; keep it on every call when you adapt the script.

| Phase | Does |
|---|---|
| Recon | Map existing vault coverage, gaps and open questions |
| Research | One agent per lane, a lane being one kind of source the user chose in section 1: search, read up to `args.pagesPerLane` pages of the lane's own kind, and return each page's fields and up to eight claims, each with one whole sentence quoted exactly from the page. No writes |
| Write | One agent, told to run one command at a time: capture each `source`, a page marked `maybeSameAs` only when the quote check says it is another document or the page the mark names has no source or failed; store its page text if the user agreed; check every quote with `verify --quotes`; judge each claim against the lines around its quote; search the stored text for a sentence that answers each question it would leave open, and add it as a quoted claim; walk the §2.6 four prompts; `capture --batch` the plan with `--operation-id`; `lint` |

A program, not an agent, confirms that each quoted sentence is on its page. A quote found is recorded on the source as a `quote-matched` row, which says the words are on the page and no more: the Write agent is the one reader that judges whether a claim says what its quote says there.

```javascript
export const meta = {
  name: 'research-orchestrate',
  description: 'Vault-conformant research: one reader per lane, quotes checked by a program, one writer',
  phases: [{ title: 'Recon' }, { title: 'Research' }, { title: 'Write' }],
}
// args: { question, cli, vault, today, runKey, storeText, lanes, pagesPerLane } — lanes = the kinds of source chosen in section 1; cli = absolute path to research-vault.mjs, vault absolute.
const CLI = `node "${args.cli}" `
const V = ` --vault "${args.vault}"`
const RUN = `${args.vault}/.research-tasks/${args.runKey}`
const NET = `RESEARCH_VAULT_ALLOW_NETWORK=1 `
const QUOTE = `Pass every value as one single-quoted shell argument, writing a single quote inside it as '\\''.`
const PAGES = { type: 'object', required: ['pages'], properties: { pages: { type: 'array', items: { type: 'object', required: ['url', 'title', 'domain', 'topics', 'authorityTier', 'authorityBasis', 'summary', 'claims'], properties: { url: { type: 'string' }, title: { type: 'string' }, domain: { type: 'string' }, topics: { type: 'string' }, authorityTier: { type: 'string' }, authorityBasis: { type: 'string' }, summary: { type: 'string' }, subjectName: { type: 'string' }, subjectVersion: { type: 'string' }, claims: { type: 'array', items: { type: 'object', required: ['claim', 'quote'], properties: { claim: { type: 'string' }, quote: { type: 'string' } } } } } } } } }
const WRITTEN = { type: 'object', required: ['status', 'lint'], properties: { status: { type: 'string', enum: ['complete', 'failed'] }, sources: { type: 'array', items: { type: 'object', required: ['i', 'status'], properties: { i: { type: 'integer' }, status: { type: 'string', enum: ['captured', 'reused', 'failed'] }, sourceId: { type: 'string' }, fill: { type: 'string' }, quotesChecked: { type: 'integer' }, quotesFound: { type: 'integer' }, reason: { type: 'string' } } } }, claimsJudged: { type: 'string' }, claimsAdded: { type: 'integer' }, created: { type: 'array', items: { type: 'string' } }, reused: { type: 'array', items: { type: 'string' } }, synthesisId: { type: 'string' }, lint: { type: 'string' }, recovery: { type: 'string' } } }

phase('Recon')
const recon = await agent(`Search the research vault for coverage of: ${args.question}. Read only. Every command you run ends with${V}: a command without it may read another vault, so run none without it, --help included. Run ${CLI}search with relevant --topic/--text facets and${V}, then for each source found run ${CLI}related <id> --depth 2 --direction in --rel sources,contributing_ids${V} so existing notes and syntheses count as coverage. Also list open question entries on the topic (${CLI}search --type question${V}) with their ids. Return the coverage, the gaps needing web research and those question ids.`, { phase: 'Recon', model: 'opus' })

phase('Research')
// The lanes are the user's choice, made in section 1, step 3: the script holds no list of its own to fall back on.
const lanes = args.lanes || []
if (!lanes.length) { log('args.lanes is empty: ask which kinds of source to read, as section 1 step 3 says, and pass them'); return { recon, pages: [], written: null, runDirectory: RUN } }
const PER_LANE = Number(args.pagesPerLane) || 2
const researched = (await parallel(lanes.map(l => () =>
  agent(`Web-search ${l} for: ${args.question}. Known gaps: ${recon}. Pick up to ${PER_LANE} of the most authoritative URLs of that kind, fetch each with your fetch tool and read it; do NOT use curl, wget or any shell command to fetch or process a page. For a file on a code host give the address of the raw file. A PDF may give no text to check (the one PDF probed gave none): where a paper or a report has an HTML page of its full text, read that page and give its address; give a PDF address only when there is none, and its quotes may then stay unchecked. The official reference pages belong to the official documentation lane only; in any other lane return pages of your lane's own kind, or no page if there is none. Run no command that writes to the vault. Return one page object per URL: its url, a concise title specific to this page, domain and topics (comma-separated), authorityTier and authorityBasis, each a value from the matching list in ${args.vault}/taxonomy.json (domain, authority_tier, authority_basis), summary (the one load-bearing claim), subjectName and subjectVersion if the page is about one version of a tool; and claims: the claims on the page that bear on the question, eight at most. For each claim give claim (one sentence, in your words or the page's) and quote: one whole sentence (never a fragment) copied from the page EXACTLY, character for character, with no markup, that the claim rests on. The claim must say no more than its quote says. The quote will be checked by a program against the page text; a quote that is not on the page makes the claim unverified.`, { phase: 'Research', model: 'opus', schema: PAGES, label: `lane:${l}` })
))).filter(Boolean).flatMap(r => r.pages)
// Issue 76: the fetcher is https-only, so an http address with no port and no `user:password@` part is tried in its https form.
// Issue 74: capture --fill answers version-floating for a version on a floating address, so the version is dropped.
// The words are FLOATING in bin/lib/fill.mjs.
const FLOATING = /\/(latest|master|main|stable|current|head|nightly|dev|trunk)(\/|$)/i
for (const p of researched) {
  p.url = p.url.replace(/^http:\/\/(?=[^/?#:]*([/?#]|$))/i, 'https://')
  if (FLOATING.test(p.url.replace(/[?#].*$/, '').replace(/^https:\/\/[^/]*/i, ''))) delete p.subjectVersion
}
// A page returned twice is kept once, with the claims of both.
const byUrl = new Map()
for (const p of researched) { const seen = byUrl.get(p.url); if (seen) seen.claims.push(...p.claims); else byUrl.set(p.url, { ...p, claims: [...p.claims] }) }
const pages = [...byUrl.values()]
// Issue 73: a raw file and its rendered page are one document at two addresses. A page with claims is marked when an
// earlier, unmarked page on another host has the same last path segment, less its extension, and the same version,
// and that name is not empty, index or readme. The Write step tests the mark.
const stem = u => u.replace(/[?#].*$/, '').replace(/^[a-z]+:\/\/[^/]*/i, '').replace(/\/+$/, '').split('/').pop().replace(/\.[a-z0-9]+$/i, '').toLowerCase()
const host = u => u.replace(/^[a-z]+:\/\//i, '').split(/[/?#]/)[0].toLowerCase()
pages.forEach((p, j) => {
  const s = stem(p.url)
  const i = pages.findIndex((q, k) => k < j && q.maybeSameAs === undefined && stem(q.url) === s && host(q.url) !== host(p.url) && (q.subjectVersion || '') === (p.subjectVersion || ''))
  if (i >= 0 && p.claims.length && s && s !== 'index' && s !== 'readme') p.maybeSameAs = i
})
if (!pages.length) { log('no page was returned, so there is nothing to write'); return { recon, pages: [], written: null, runDirectory: RUN } }
let n = 0
const numbered = pages.map((p, i) => ({ i, ...p, claims: p.claims.map(c => ({ n: n++, ...c })) }))
const FILL = args.storeText
  ? `2. Page text. The user has agreed that this run may store page text. For each source from step 1 run: ${NET}${CLI}capture --fill <sourceId> --ack-data-egress --json${V}   It prints one JSON object; keep its result (filled, kept, refused, version-floating, unreachable, no-text or too-large). Never pass --discard, --replace or --content-file.`
  : `2. Page text. The user has not agreed to store page text: run no capture --fill. The fill result of every source is "not stored".`

phase('Write')
const written = await agent(`You are the only writer to the vault right now. Run one command at a time, in this order. ${QUOTE}
1. Sources. Leave out every page that has maybeSameAs: step 3 decides whether it gets a source. For each other page below, one after another, run:
${CLI}capture --type source --title <title> --url <url> --domain <domain> --topics <topics> --authority-tier <authorityTier> --authority-basis <authorityBasis> --summary <summary> [--subject-name <subjectName>] [--subject-version <subjectVersion>]${V}
Pass each of the two only when the page has that field; never make up a version. Never pass --force. Read each result: "created <path>": status captured; the sourceId is the file name without .md. "duplicate of <id> (existing entry with same url ...)": the page is already in the vault; status reused, sourceId is that id. "error: id taken: ...": the TITLE gives the id of another entry; do NOT use that id, make the title more specific and capture again. "blocked source": status failed with the message as reason; do not retry it. An error naming a field and its allowed values: use the closest allowed value and try once more; any other error, or a second failure: status failed.
${FILL}
3. Quotes. For each source from step 1 that is not failed: create the directory ${RUN}, write a file ${RUN}/quotes-<i>.json holding a JSON array of that page's claims as {"n": <n>, "quote": <quote>}, and run ${NET}${CLI}verify --id <sourceId> --quotes ${RUN}/quotes-<i>.json --by-id research-orchestrate --run ${args.runKey}${V}   It prints, per claim, whether the quote is on one line of the source's text, or over adjacent lines with no blank line between them (found), where (foundIn: body is the stored text, page is the page fetched now), every line it starts on, and the lines around the first (context). It records each quote it finds on the source itself and adds nothing for a quote already recorded, so it is safe to run again and you run no other verify command. A claim is VERIFIED only if found is true AND, reading its context, the quote means there what the claim says: if the quote sits in a version-history row, a quoted comment or another section than the claim is about, or occurs on several lines with different subjects, or the claim says more than the quote, then either cut the claim down to what the quote says in that context or treat it as not verified. Keep a list of the claims you cut down or dropped, with the reason. A claim whose quote was not found or was refused is not verified. If NONE of a source's quotes was found, give that source the reason "text unusable"; do not change it, and never run a discard. Then take each page that has maybeSameAs, one after another: it may be the document of page <maybeSameAs>, read at another address. If page <maybeSameAs> has no source, or its status is failed, do steps 1 to 3 for this page as for any other page. Otherwise write this page's quotes file and run the same verify command on it with the sourceId of page <maybeSameAs>; this check gives that source no "text unusable" reason. If more than half of this page's quotes are found, the two pages are one document: run no capture and no fill for this page; its row has status reused, the sourceId of page <maybeSameAs>, the reason "same document as page <maybeSameAs>", no fill result, and quotesChecked and quotesFound from this check; judge its claims from this output, and a claim whose quote was not found is not verified. Otherwise they are two documents: do steps 1 to 3 for this page as for any other page.
3b. Coverage, only for sources whose fill result is filled or kept. Before you plan, write down the questions you would otherwise leave open. For each, search the stored text of this run's sources for a sentence that answers it (for example grep -n -i <word> "${args.vault}/sources/<sourceId>.md"). Where one whole sentence on the page answers it, add a claim with that sentence as its quote, numbered on from the last n, check it with the same verify --quotes command and judge it by the same rule. Add eight claims at most. A claim added in this step appears in the synthesis and in any note ONLY as its exact quote inside quotation marks, introduced by naming the page; never restate it in your own words. A question stays open only if the stored text does not answer it.
4. Plan. Walk AGENTS.md §2.6 for: ${args.question}. Use only the verified claims as support for conclusions. Walk the four prompts: (1) notes distilling load-bearing sources, quoting the verified sentences, (2) questions for every unresolved ambiguity (including every claim that is not verified), (3) experiments only for an empirical run, (4) snippets for reusable fragments. Then ONE synthesis, written for a colleague who reads it once, cold, to decide what to do: the answer first, then what the pages say with each verified claim as a sentence, then the recommendation; summary one sentence; confidence. Its contributingIds name the notes and the source ids, and its body names the source ids it relies on. Sources already exist: reference them, do not recreate them. Every entry carries a body with real prose. An id is ${args.today}-<slug>; the slug is the title in lower case with every character other than a to z or 0 to 9 turned into a break, the words a, an, the, of, to, in, on, for, and, or, with, is, are, be dropped, and the first six remaining words joined by hyphens. Writing rules, for every entry: (a) the title, the summary and the answer of the synthesis state only what a verified quote says; anything you infer is worded as an inference (for example "by inference from ...") or filed as a question, never stated as fact; (b) do not write only, nothing except, always, never or complete, and give no count of things (two exceptions, the one test, three limits), unless a quote says it; where a page gives exceptions to a rule, state them; (c) you checked quotes, not whole pages: say what is missing as "no checked quote says ...", never as "the pages do not say", "no page ..." or "the page is silent"; of a claim whose quote was not found say only that the quote offered did not match a line of the stored text, never that the text lacks the claim; (d) a statement about several people, pages or posts names the quotes it rests on (two repliers, not the repliers); give no reason (because ...) and no ranking (cheapest, best, most) that no quote states; (e) paste each quote exactly as it stands in PAGES, do not retype it; (f) contributingIds of the synthesis lists every entry id that its body names, questions and snippets included; (g) never write the run key in any entry's body. The plan is a JSON array of capture specs with camelCase keys (type, title, body, sources, contributingIds, topics, domain, summary, confidence, state, question, language, tested, synthesisBasis).
5. Persist. The plan files are ${RUN}/plan-1.json, plan-2.json, plan-3.json; plan-<k>.json is always captured with the operation id ${args.runKey}-plan-<k>. Never write over a plan file that exists. If none exists, write your plan to plan-1.json. Take the highest-numbered plan file that exists and run ${CLI}capture --batch "${RUN}/plan-<k>.json" --operation-id ${args.runKey}-plan-<k>${V}. It prints one JSON object, on exit 1 too. Read it in this order:
- errors is empty and operation.phase is complete: done.
- an error has code LOCK_BUSY: another capture holds the lock, or one died holding it. Stop with status failed and recovery set to the lock path the message names.
- an error has code RECEIPT_IO or INPUT_CHANGED: stop with status failed and recovery set to the error text and the path ${args.vault}/.capture-operations/<operation id>.json.
- recoveryStateCreated is true: entries may already be written. Do not change the plan. Run the identical command once more. If it is still not complete, stop with status failed and recovery set to that exact command and the path ${args.vault}/.capture-operations/<operation id>.json.
- otherwise this call wrote nothing: correct every entry the errors name (each has an index; an entry that names a failed entry is reported too), save the corrected plan as the next file and run that one. Three plan files at most; after plan-3.json fails stop with status failed and the last errors as recovery.
6. Lint. Run ${CLI}lint${V} and keep every line that names an entry this run created.
Return status, sources (one row per page with its i, status, sourceId, fill result, quotesChecked and quotesFound for that source, and a reason where one applies), claimsJudged (one line per claim you cut down or dropped, with its n and the reason, joined into one string), claimsAdded (the number of claims added in step 3b), created (ids from the capture output's created rows), reused (ids from its skipped rows), synthesisId and lint.
PAGES: ${JSON.stringify(numbered)}`, { phase: 'Write', model: 'opus', schema: WRITTEN, label: 'writer' })
return { recon, pages: numbered.map(p => ({ i: p.i, url: p.url, claims: p.claims.length, maybeSameAs: p.maybeSameAs })), written, runDirectory: RUN }
```

The script writes nothing itself and takes no id from a worker's memory: source ids come from the Write agent's capture output and are checked again when the plan is captured, which refuses a reference to an id that is not in the vault. A returned id is still only as good as the agent that copied it, so section 4 starts by checking them. A source the result marks "text unusable" is one where none of its quotes was found in its stored text or on its fetched page: the text or the quotes may be at fault, so a person looks before anything is discarded (`capture --fill <id> --discard` is for a person to run). A page marked `maybeSameAs` gets no source of its own when more than half of its quotes are found in the text of the page the mark names, as the Write step is told (a trial run, one agent, did so with three of four quotes found): the Write step is told to file its claims under that page's source, and a source row with the reason "same document as page ..." says so. A PDF source answers `no-text` when its bytes hold a zero byte, as the one PDF probed did: a person who needs its text converts the paper to a `.md` file and runs `capture --fill <id> --content-file <file> --ack-data-egress`.

## 3. Degraded mode and recovery

With no Workflow tool, run the same three steps inline and sequentially, as the only writer: vault search → web search and fetch, keeping for each page up to eight claims with one whole quoted sentence each → then the Write step's numbered steps as written in §2, with the same commands: one `capture --type source` per kept URL, `capture --fill` only if the user agreed, `verify --id <source> --quotes <file> --by-id research-orchestrate` for each source, the judging of each claim against the lines around its quote, the coverage step over stored text, the §2.6 plan under the writing rules, `capture --batch` with `--operation-id <run key>-plan-1` under the Persist rules, and `lint`. The parallelism is lost. The script's address repair does not run here either, so do it by hand: give an `http://` address with no port in its `https://` form, unless it has a `user:password@` part, and pass no `--subject-version` for an address whose path has a floating segment (`latest`, `master`, `main`, `stable`, `current`, `head`, `nightly`, `dev` or `trunk`). The script's mark for one document at two addresses does not run here either: when two kept pages on different hosts have the same last path segment, less its extension, and the same subject version or none on both, and that name is not "index" or "readme", check the second page's quotes against the first page's source before you capture the second. If more than half are found, capture no second source, judge the second page's claims from that output and file them under the first source; otherwise capture the second page as usual.

To resume an interrupted run, use its run key and its plan files: take the highest-numbered plan file that exists and never write a new plan over an existing file.

- **`LOCK_BUSY`** (check this first; by the code, the report also carries `recoveryStateCreated` true when a receipt for that operation id is already there): another `--operation-id` capture holds `<vault>/.capture-operations/writer.lock`, or one died holding it. Read `owner.json` in that directory if it is there and confirm that process is gone; only then remove the lock directory and run the original command again. Never remove a lock because it is old.
- **`RECEIPT_IO` or `INPUT_CHANGED`**: stop, and report the error and `<vault>/.capture-operations/<operation id>.json`.
- **Capture stopped part-way** (neither of those two codes, and `recoveryStateCreated` true, or the receipt `<vault>/.capture-operations/<operation id>.json` exists and its `phase` is not `complete`): run the same command again with the same plan file, the same operation id and the same flags. Do not correct the plan under that id.
- **Capture refused the plan** (neither of those two codes, `recoveryStateCreated` false and no receipt for that operation id): correct the plan and capture it as the next file under the next operation id.
- **Sources, fills and quote checks** are safe to run again with the same values: a URL already in the vault under the same subject version comes back as a duplicate with its id (the same URL with another subject version, or with none where one was recorded, is not a duplicate: it is captured as a new entry when its title gives an id that is free), a fill of a source that already holds text answers `kept`, and `verify --quotes` adds no row for a quote whose hash is already on the source.

If `WARN_SYNTHESIS_NO_NOTE_COVERAGE` or `WARN_SYNTHESIS_MONOLITHIC` fires after persistence, either decompose further or declare `synthesis_basis: primary-rollup`, only if it honestly is a factual rollup. To decompose, capture the added notes as a new plan under a new operation id, then edit the existing synthesis in place with research-authoring; never capture a changed synthesis again under its id. Keep the run's directory under `.research-tasks` until the user asks for cleanup. The lock covers `--operation-id` captures only; nothing here protects against another writer editing the same entries, so stop for review if an entry changed under you.

## 4. Close out
<!-- evidence: 2026-11-17-cli-lines-behind-research-orchestrate-skill 2026-11-17-document-lines-research-orchestrate-skill-names 2026-11-17-probe-cli-behaviour-research-orchestrate-skill 2026-11-17-third-lines-behind-research-orchestrate-skill -->

These are the controller's completion checks. Keep four results apart when you report: what the evidence supports, what was persisted, the lint result, and the claims verdict.

1. Confirm each id the workflow returned is a file in the vault, then run `lint` with the explicit vault — clean, or explain every warning.
2. Run the `research-claims-gate` skill on the synthesis entry file (evidence derives from the entry ids its body cites; that skill lists the sources behind the notes and asks before it stores page text for those that hold none; when this run stored page text, its step 1b can cut the first round's evidence to a packet with this run's key), then present it to the user the way you would tell a colleague: the answer, why, how confident, and what is still open (question ids).
3. Only after the gate records `PASS` or `MERIT`, close each question the synthesis actually resolves: `verify --id <question> --answered-by <synthesis id>`. If the gate does not pass, show its verdict and leave the questions open. List the ids created and reused.
4. Offline or fetch-blocked? Do not fabricate: answer from the vault, record what could not be verified as open `question` entries, and say so.

## Anti-patterns (from ORCHESTRATOR-INTEGRATION.md)

Monolithic report files; source→synthesis with no notes (unless a declared `primary-rollup`); "I don't know" as prose instead of a `question`; reusable fragments inline instead of `snippets/`; stub notes written only to silence the lint.

Keep the normal final answer format. Show a replay command or a resume instruction only when work failed or is unfinished; a successful run needs no receipt dump.
